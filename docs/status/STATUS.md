# 현재 상태

## 라이브 인프라

봇/워커 두 프로세스 구조로 상시 운영 중이다(`docs/decisions/0006-thin-worker.md`).

- **봇(Railway 또는 로컬 PM2)** — 24/7 상시 구동, 디스코드 연결·대화 처리. 모든 턴을 예외 없이
  자신의 SDK 세션으로 직접 실행한다(위임 없음). 워커가 아웃바운드로 붙는 WebSocket 허브(`/worker`)도
  이 프로세스가 연다 — 봇의 첫 공개 네트워크 리스너다. 컨테이너는 무상태(stateless)이며 재배포돼도
  데이터가 사라지지 않는다. 절차는 `deploy/railway-셋업.md` 참고.
- **워커(개인·공유)** — 소유자 PC 또는 동아리 공용 미니PC에서 실행되며, 봇이 모델의 파일/셸
  도구 호출을 원격으로 요청하면 그 도구 하나만 실행해 결과를 돌려준다. 디스코드에도 DB에도
  붙지 않는다. 각 워커는 `workers` 테이블(레지스트리)에 등록된 자기 고유의 id와 해시된
  토큰을 갖는다(`npx tsx src/scripts/registerWorker.ts`로 발급, 토큰은 그 자리에서 한 번만 보인다). 절차는
  `deploy/worker-셋업.md` 참고.
- **Supabase Postgres** — 봇만 접속하는 정본 상태 저장소(유저·대화·기억). `worker_jobs`/
  `worker_heartbeats` 테이블은 옛 위임 모델의 흔적으로 DDL만 남아 있고 미사용이다. 로컬 PM2는
  Railway의 폴백/대체 수단이며, 봇 토큰이 1개라 둘을 동시에 띄우지 않는다(`deploy/PM2-명령어.md`).

## 병합된 주요 기능 (main)

- **멀티유저 런타임** — 대화별 직렬 처리·프라이버시 스코프(DM=사용자별, 서버=공유)·시간당 한도
  (손님: 유저별 20 / 전역 40, 소유자: 무제한)·크래시 복구.
- **원격 개발 워크플로우(얇은 워커, 다중 워커 1단계)** — 워커는 `workers` 테이블(레지스트리)에
  등록된 신원(`id`/`kind`/해시된 토큰)을 갖는다. 대화 위치가 어느 기계를 쓸지 정한다: 소유자
  DM은 그 소유자의 **개인 워커**(`allowed_dirs` 그대로), 소유자의 서버 채널은 동아리 **공유
  워커**의 **루트 전체**(관리자), 손님은 DM·서버 어디서든 같은 공유 워커의 **본인 폴더**
  (`<루트>/<디스코드 userId>/`, 첫 접근 때 자동 생성)로만 좁혀진다. 워커가 연결돼 있을 때만
  원격 도구 11종(`fs_read`/`fs_write`/`fs_edit`/`fs_glob`/`fs_grep`/`fs_tree`/`sh_exec`/
  `proc_start`/`proc_stop`/`proc_list`/`proc_logs`)이 열린다 — 이제 손님과 소유자의 서버
  채널도 포함한다(이전엔 소유자 DM 전용이었다). 마지막 넷(`proc_*`)은 개발서버 같은 장기
  실행 프로세스를 PM2 에 위임하는 도구로, 경로가 아니라 PM2 프로세스 이름으로 소유권이
  갈린다(`docs/security/capability-model.md` "장기 실행 프로세스의 한계" 참고). 경로 검사는
  `fs_*` 기준으로 봇 쪽 1차 필터(허용 폴더를 워커별로 관리 + 손님은 본인 폴더로 재차 스코프)
  + 워커 쪽 최종 판정 두 겹이며, `sh_exec`는 이 스코프의 대상이 아니다 — 경로로 봉쇄되지
  않으므로 폴더 격리는 실수
  방지선일 뿐 의도적 접근의 경계는 아니다(의도된 설계). `allowed_dirs`는 마이그레이션 없이
  `worker_id` 키로 바뀌었다 — 워커 등록 후 `allow_dir`로 폴더를 다시 등록해야 한다. 상세
  위협모델은 `docs/security/capability-model.md`, `docs/security/risk-register.md` 참고.
  셸·프로세스 사용성(2026-07-31): `sh_exec` 는 명령의 종료 코드를 도구 실패로 취급하지 않는다
  (`ok:false` 는 spawn 실패·타임아웃뿐) — `actions.status` 의 `error` 도 그에 맞춰 도구 실패만
  가리키게 됐다. 계속 도는 명령은 도구 설명과 타임아웃 문구가 `proc_start` 로 유도하고,
  `proc_list` 는 `asahi-<userId>` 대신 사람 이름을 보여준다(이름을 모르면 예전 형식으로 폴백한다).
- **캐릭터/페르소나** — 코딩 동아리 '세미콜론'의 16세 부원이라는 고정 인격(이름·외형·말투·소유자/손님/서버별
  어조 차등)과 대화 이력 기반의 가벼운 관계 진화. 대화 중 즉흥으로 지어낸 신상 설정은 `memories` 의
  `scope='character'` 로 확정 저장돼 세션·대화방을 넘어 일관되게 유지된다(실제 기억과는 분리).
  캐릭터 신상은 지어내되 작업 사실(도구 결과·파일·DB 상태)은 지어내지 않는 경계를 프롬프트에 명시했다.
  예약어(`/새세션` 등)로 세션·톤을 초기화할 수 있다.
- **자기인지 DB 조회(조각C)** — 소유자 DM 전용 도구로 스키마 조회·읽기전용 SQL 질의·런타임 정보 제공.
  Postgres READ ONLY 트랜잭션 + 정적 SQL 가드 + 타임아웃으로 다층 방어한다.
- **디스코드 이미지 입력(멀티모달)** — 이미지 첨부를 모델에 직접 전달한다. 과거 이미지는
  재주입하지 않고 마커만 저장한다(비용 방지).
- **표정 이미지** — 모델이 답변에 `[표정:이름]` 마커를 쓰면 해당 표정 이미지를 embed 로 함께 보낸다.
  이미지는 Supabase Storage 에, 카탈로그는 `character_images` 테이블에 있고 `agent/scripts/sync-images.mjs`
  로 갱신한다(기존 감정의 이미지 교체·추가는 재배포 불필요 — 단, 새 감정 폴더는 감정 목록을 기동 시
  한 번만 읽으므로 봇 재시작이 필요하다. `image/README.md` 참고). 감정이 움직일 때만 쓰도록 프롬프트로
  유도하고, 어댑터가 대화별
  120초 하한으로 남발을 막는다(단, 마커만 있고 본문이 없는 답변은 이미지가 곧 응답이라 하한을
  건너뛴다). 이모지 금지 규칙의 감정 표현 수단을 대신하는 장식 요소로, 조회·전송이 실패해도
  텍스트 응답은 항상 나간다.
- **웹 검색** — 모든 대화에서 SDK 내장 `WebSearch` 를 쓴다(`WebFetch` 는 열지 않았다).
- **정기 뉴스 게시** — 매일 KST 7시에 대회 소식·개발 뉴스를 조사해 각 채널에 올린다.
  정각이 아니라 "지났는데 오늘 아직 안 했으면" 실행하므로 재배포로 그 순간을 놓쳐도 그날 안에
  올라간다. 예약어 `/대회`·`/개발뉴스` 로 어느 채널에서든 — 봇을 멘션하지 않고 일반 채널에서
  그냥 쳐도 — 즉시 실행할 수 있다. 결과는 그 주제의 지정 채널로 올라가며(스레드에 갇히지
  않는다), 명령을 친 곳에는 어디에 올릴지만 알린다. 지정 채널이 없으면 친 곳으로 폴백한다.
  **DM 에서 부른 것만 예외로 DM 에 답한다** — 혼자 확인해 보려던 것이 매번 공개 채널에
  게시되지 않도록(공개 채널에 올리고 싶으면 서버에서 부르면 된다). 스케줄의 "오늘 했음" 기록은
  결과가 실제로 그 주제의 지정 채널에 올라갔을 때만 남는다 — 그래야 몇 시간 뒤 07시 스케줄이
  같은 내용을 그 채널에 또 올리지 않는다. DM 으로 답했거나 지정 채널이 없어 친 곳으로
  폴백했을 때는(지정 채널엔 아무것도 안 올라갔으므로) 기록을 남기지 않아, 그날 아침 스케줄은
  평소대로 돈다. 일반 채널에서 예약어를 받아도 그 채널을 봇 대화로 만들지 않으므로, 이후 그
  채널의 잡담에 봇이 끼어들지 않는다. 게시 작업은 공개 채널 계층으로 돌아 PC 도구가 열리지 않는다.
  또한 부팅 시 설정된 지정 채널마다 봇이 실제로 접근할 수 있는지 확인해, 접근할 수 없으면
  env 변수 이름과 채널 ID 를 콕 집어 경고한다(치명으로 취급하지 않음 — 일시적으로 못 보는
  채널 때문에 봇 전체가 멈추면 안 된다).
- **모델**: 기본 Opus 계열 최신 모델로 고정, 환경변수로 재정의 가능.

## 테스트

`agent/` 기준 vitest 44개 파일, **902개 통과 + 3개 skip**(905개, 윈도우에서 측정).

skip 3건의 성격은 서로 다르다. 1건은 Postgres READ ONLY 트랜잭션의 실제 쓰기 거부 동작으로,
테스트용 인메모리 Postgres 구현(pg-mem)의 한계상 유닛 테스트로 재현할 수 없어 실 Supabase
스모크로만 검증 가능하다(`introspectRepo.test.ts`). 나머지 2건은 플랫폼 조건부(`it.skipIf`)라
**실행 플랫폼에 따라 달라진다** — 윈도우에서는 POSIX 전용 케이스가, 리눅스에서는 윈도우 전용
케이스가 건너뛰어지므로 skip 수를 그대로 비교하지 마라.

## 미완 / 미검증

다음은 코드·유닛 테스트로는 검증됐지만, 실제 Supabase·실배포 환경에서의 스모크 테스트가 아직 없다.
체크리스트는 `deploy/smoke-test.md`에서 추적한다.

- Postgres READ ONLY 트랜잭션의 실제 쓰기 거부.
- **봇 ↔ 워커 실 WebSocket 왕복** — 2026-07-28 미니PC(공유 워커) 점검으로 **일부 실증됐다.**
  확인된 것: 인증(`hello`→`ready`, `workers.last_seen_ts` 갱신으로 교차 확인)·자동 재연결·
  `fs_write`/`fs_read`/`fs_edit`/`sh_exec` 왕복·봇 쪽 1차 경로 필터(허용 폴더 밖, `..` 상위
  탈출, 글롭 상위 탈출 전부 도구 원문으로 거부)·손님 폴더 자동 생성과 사용자별 격리. 이 과정에서
  리눅스 봇이 윈도우 워커의 경로를 전부 거부하던 문제가 해소된 것도 처음 실증됐다.
  아직 실환경에서 안 눌러본 것: `denied`(틀린 토큰) 경로, 호출 타임아웃, **워커 쪽 최종 게이트**
  (`WORKER_ROOTS` 기준 `checkPath`) — 지금까지의 시도는 봇 쪽 1차 필터에서 먼저 걸려 워커까지
  도달한 적이 없다. 유닛 테스트(`agent/tests/remoteProtocol.test.ts`,
  `remoteHub.test.ts`, `remoteWorkerClient.test.ts`, `remoteRoots.test.ts`, `remoteExecutors.test.ts`,
  `remoteTools.test.ts`)는 소켓 없이 프로토콜·핸들러 로직만 검증한다.
- **장기 실행 프로세스 관리(`proc_*`)** — 2026-07-31 미니PC 점검으로 **핵심 경로가 실증됐다.**
  확인된 것: 큰따옴표·작은따옴표·공백이 든 명령이 실행 대상까지 원형 그대로 전달되는 것
  (명령이 쓴 파일의 내용으로 판정 — PR #11 의 스크립트 파일 우회가 실사용에서 처음 동작),
  `proc_list` 가 pm2 의 `cmd /c …\asahi-….bat` 을 회원의 원래 명령으로 되읽어 보여주는 것
  (`recoverCommands`), 개발서버가 실제로 서빙하는 것(포트 `LISTENING` 으로 확인 — `online`
  표시만으로는 판정하지 않았다), 1인 1개 상한 게이트가 모델 선점이 아니라 도구에서 발동하는
  것, 한글·공백이 든 작업 폴더가 `--cwd` 로 정상 전달되는 것.
  아직 안 눌러본 것: **재부팅 후 PM2 데몬 독립 기동**(아래 "알려진 한계"와
  `docs/agent-onboarding.md` §9 — 지금 데몬이 워커 재시작을 견디는 것은 확인됐으나 그건 태어난
  경위 덕일 가능성이 크다), 그리고 소유자 개인 워커에서의 동작(`owner-laptop` 은 2026-07-28
  이후 연결된 적이 없고 `allowed_dirs` 가 0행이다).
  **이 검증의 전제**: 원격 도구의 실행기는 봇이 아니라 워커에서 돈다 — 미니PC 를 갱신하지 않은
  채로 한 관측은 옛 코드의 동작이다. 실제로 이 점검 과정에서 4시간 뒤진 워커로 세 번 오진했다
  (`docs/agent-onboarding.md` §3).
- **허브 keepalive 의 실환경 효과** — 유휴 WS 가 중간 프록시에 끊기던 문제를 허브의 주기적
  `ping` 으로 고쳤다(`hub.ts`). 유닛 테스트는 타이머 동작만 검증하므로, 실제로 유휴 30분 이상
  연결이 유지되는지는 `deploy/smoke-test.md` 의 keepalive 항목으로 확인한다.
- 디스코드 이미지 첨부 → 모델 인식(실제 첨부 파일로 확인).
- **표정 이미지 실 배포 검증** — Supabase Storage 실제 업로드, `character_images` 카탈로그 갱신,
  디스코드 embed 렌더링이 실 환경에서 그대로 동작하는지. 유닛 테스트(`characterImagesRepo.test.ts`,
  `expressionSend.test.ts`, `persona.test.ts` 등)는 로직만 pg-mem·모킹으로 검증한다.
- `/새세션` 계열 명령으로 세션을 리셋했을 때 캐릭터 톤이 실제로 체감되는지.
- 손님·서버 채널에서의 한도·프라이버시 스코프 체감(유닛 테스트는 순수 로직만 커버).

## 알려진 한계

- **전송 유실 가능성**: 하드 크래시가 디스코드 응답 전송 도중 발생하면 그 응답 1건은 재전송되지 않는다
  (생성된 텍스트 자체는 이벤트 로그에 보존된다). 정상적인 그레이스풀 종료는 flush로 처리되어 유실이
  없다.
- **워커 토큰 유출**: 각 워커는 `workers` 테이블에 등록된 자기 고유의 토큰을 가지며, 유출되면
  그 워커 하나가 위험에 노출된다 — 유출된 토큰으로는 그 워커의 `WORKER_ROOTS` 안에서(그리고
  `sh_exec`로는 그 밖도 워커 프로세스의 OS 권한이 닿는 한) 파일/셸 작업을 가로챌 수 있다.
  이 토큰만으로는 Postgres·Claude 구독에는 접근하지 못한다(워커는 그 자격증명을 아예 갖지
  않는다). 취급 정책은 `docs/security/risk-register.md` §1(및 `SECURITY.md`) 참고.
- **`sh_exec` 는 사용자별 폴더 격리의 대상이 아니다**: 공유 기계에서 손님은 파일 도구
  (`fs_read` 등)로는 자기 폴더 밖을 볼 수 없지만, 셸 명령은 경로로 봉쇄되지 않으므로 워커
  프로세스의 OS 계정 권한이 닿는 곳은 모두 접근할 수 있다. 경계는 미니PC 의 계정 분리다
  (`docs/security/capability-model.md`).
- **`sh_exec` 출력의 한국어가 깨진다**: 워커가 자식 프로세스의 출력을 UTF-8 로 디코드하는데
  윈도우 내장 명령은 시스템 코드페이지(미니PC 는 cp949)로 한국어 메시지를 내보내므로, 그
  메시지가 mojibake 로 모델에게 전달된다. 실패의 원인 자체는 멀쩡한데 그 설명만 깨지는 것이라
  진단 중 오진을 부르기 쉽다. 자세한 내용은 `docs/agent-onboarding.md` 2절.
- **공유 워커는 한 대만 쓴다**: `workers` 테이블은 여러 대를 표현할 수 있지만 라우팅은
  가장 먼저 등록된 `shared` 워커 하나만 고른다.
- **읽기전용 조회 결과 크기**: 자기인지 SQL 조회 도구는 현재 애플리케이션 단에서 결과를 자르는 방식이라,
  매우 큰 결과 집합에 대해서는 SQL 단 LIMIT 적용 등 후속 개선이 필요하다.
- **정기 게시는 어제 올린 내용을 모른다**: 매번 새 세션으로 조사하므로 같은 소식이 이틀 연속
  올라올 수 있다. 실사용에서 거슬리면 그때 다룬다.
- **정기 게시는 놓친 날을 소급하지 않는다**: 봇이 죽어 있는 동안 KST 7시가 지나갔으면 그날은
  건너뛰고, 다음 날 아침 확인에서 다시 시도한다.
- **정기 게시는 하루 3번까지만 시도한다**: 조사가 실패하면 다음 1분 확인에서 재시도하지만, 같은
  날 3번 실패하면 그날은 포기한다(다음 날 KST 날짜가 바뀌면 초기화). 실패 안내도 그날 첫 실패
  때 한 번만 채널에 나가고, 이후는 로그로만 남는다 — 토큰 만료처럼 지속되는 실패가 채널을
  같은 메시지로 도배하고 가장 비싼 턴을 하루 종일 재시도하는 것을 막기 위해서다.
