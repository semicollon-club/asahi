# 에이전트 온보딩

새 세션에서 이 프로젝트를 이어받는 **에이전트**를 위한 문서다. "무엇을 만들고 있는가"는
다른 문서들이 이미 잘 설명하고 있으니 여기서는 반복하지 않는다. 이 문서가 담는 것은
**어떻게 일해야 하는가**, 그리고 **이 환경이 어떤 식으로 사람을 속이는가**다.

여기 적힌 함정은 전부 실제로 밟아 본 것들이다. 대부분은 한 번에 몇 시간씩 태웠고, 몇
개는 잘못된 원인을 확신한 채로 브랜치 하나를 통째로 날려 먹었다. 추측으로 재발견하지 마라.

## 먼저 읽을 것

이 순서로 읽으면 30분 안에 작업을 시작할 수 있다.

1. [현재 상태](status/STATUS.md) — 라이브 인프라, 병합된 기능, 미완 항목
2. [아키텍처 개요](architecture/overview.md) — 3-프로세스 구조
3. [능력 계층 모델](security/capability-model.md) — **보안 경계의 정본.** 코드를 고치기 전에 반드시
4. [기여 가이드](../CONTRIBUTING.md) — 셋업·테스트·실행
5. 이 문서의 "이 환경의 함정" 절

문서와 코드가 어긋나면 **코드가 이긴다.** 그리고 문서를 고쳐라.

## 30초 요약

디스코드에서 사는 한국어 AI 비서다. 코딩 동아리 '세미콜론'의 부원이라는 고정 인격을 갖고,
부원들이 채팅으로 자기 PC 작업(파일 읽기·쓰기·셸·개발서버)을 시킬 수 있다.

프로세스는 셋이다.

- **봇** — Railway 상시 구동. 디스코드 연결, 모델 세션, DB 접근. 워커가 붙는 WebSocket 허브를 연다
- **워커** — 각자의 PC(소유자 개인 PC / 동아리 공용 미니PC)에서 실행. 봇이 요청한 도구 하나만
  실행해 결과를 돌려준다. **디스코드에도 DB에도 붙지 않는다**
- **Supabase Postgres** — 봇만 접속하는 정본 상태 저장소

핵심 불변식 하나: **미니PC 워커는 `DATABASE_URL` 을 절대 갖지 않는다.** 워커의 유일한
자격증명은 `WORKER_TOKEN` 이다.

## 작업 방식

이 리포는 superpowers SDD 루프를 쓴다. 새 기능이나 비자명한 변경은 이 순서를 따른다.

```
brainstorming → 스펙(docs/superpowers/specs/) → writing-plans → 계획(docs/superpowers/plans/)
   → subagent-driven-development(태스크마다 구현 에이전트 + 리뷰 에이전트)
   → 전체 브랜치 최종 리뷰 → PR
```

- 진행 상황은 `.superpowers/sdd/progress.md` **원장**에 남긴다. git-ignore 되지만 이게
  컴팩션 이후의 복구 지도다. 태스크가 끝날 때마다 커밋 범위와 미해결 Minor 를 한 줄로 적어라.
- 세션이 컴팩션되면 **원장과 `git log` 를 믿어라.** 기억을 믿지 마라. 완료된 태스크를 다시
  디스패치하는 것이 이 워크플로에서 가장 비싼 실패다.
- 브랜치는 항상 새로 판다. `main` 에서 직접 작업하지 않는다.
- 원격에 올린 뒤 GitHub 에서 머지한다.

### 커밋 규약

- Conventional commits + **한국어 제목**
- 본문 끝에 `Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`
- 주석·커밋 메시지·사용자 노출 문자열은 전부 **한국어**
- 사용자 노출 문자열에 **이모지 금지** (진행 표시의 `✓`/`✗` 만 기존 예외)

### 코드 규약

- TypeScript ESM/NodeNext — **상대 임포트는 `.js` 로 끝난다** (소스는 `.ts` 여도)
- TDD. 실패하는 테스트를 먼저 쓰고, **실패를 눈으로 확인한 뒤** 구현한다
- `agent/src/core/paths.ts` 와 `agent/src/remote/roots.ts` 는 **읽기 전용으로 취급**한다.
  경로 판정은 보안 경계이고, 고쳐야 한다면 그것 자체가 하나의 작업이다
- 이 코드베이스의 주석은 *왜* 를 여러 줄로 설명한다. 코드를 옮겨 적는 주석은 쓰지 마라

### 검증

작업을 끝냈다고 말하기 전에 **셋 다** 통과해야 한다. `agent/` 에서:

```
npm test
npm run typecheck
```

리포 루트에서:

```
node scripts/check-docs.mjs
```

`문서 검사 통과` 가 나와야 한다. 이 스크립트는 금칙어 회귀, 아카이브 front-matter,
**내부 상대 링크 존재**를 검사한다 — 문서에 링크를 걸었는데 대상이 없으면 실패한다.

## 증거 없이 완료라고 말하지 않는다

이 프로젝트에서 가장 비싸게 배운 규칙이다.

- **상태를 기억으로 단정하지 마라.** 배포됐는지, 머지됐는지, 무엇이 실제로 실행됐는지는
  명령을 돌려서 확인하고 그 출력을 인용해라. 실제로 "PR 은 아직 머지 안 했다"고 단정했다가
  2분 전에 머지된 것이 드러난 적이 있고, 그 한 줄 때문에 같은 메시지의 나머지 분석까지
  신뢰를 잃었다.
- **실험할 때 변수는 하나씩 바꿔라.** "따옴표가 원인"이라고 결론지은 비교가 알고 보니
  따옴표와 경로 인코딩을 동시에 바꾼 것이었다. ASCII 경로로 변수를 하나만 남기고 나서야
  진짜 원인이 확정됐다.
- **프로세스 목록만 보고 원인을 정하지 마라.** PM2 밖에서 도는 `vite` 를 보고 "`pm2 delete`
  가 손자를 남긴다"고 결론지었는데, 같은 대화에서 비서가 "그래서 셸에서 직접 띄웠습니다"
  라고 이미 적어 둔 것을 놓친 것이었다. 그 오진 위에 브랜치 하나를 통째로 지었다.
- 테스트가 통과한다고 프로덕션 경로가 검증된 게 아니다. 이음매(seam) 뒤의 실제 구현은
  단위 테스트가 절대 지나가지 않는다는 것을 항상 의식해라.

# 이 환경의 함정

여기부터가 이 문서의 본론이다.

## 1. 미니PC 의 두 계정

미니PC 에서 작업할 때 **창이 두 개**다. 이게 "같은 계정의 일반/관리자 모드"라고 생각하면
반드시 틀린다.

`asahi` 는 일부러 **관리자 권한이 없는 표준 계정**으로 만들었다(워커가 손님의 셸을 실행하는
계정이라, 이게 이 설계의 실질적 보안 경계다). 표준 계정은 자기를 승격시킬 수 없으므로,
"관리자 권한으로 실행"을 누르면 Windows 가 **관리자 계정의 자격증명**을 묻고 그 프로세스는
`asahi` 가 아니라 **다른 사용자로** 뜬다. 화면은 같은 데스크톱이지만 프로세스의 주인이 다르다.

**프롬프트 경로로 계정을 판단하지 마라.** `C:\Windows\system32` 프롬프트가 관리자라는 뜻이
아니다. 반드시 `whoami` 로 확인하고, 사용자에게 명령을 줄 때도 어느 창인지 명시해라.

계정별로 갈리는 것들:

| | `asahi` 창 | 관리자 창 |
|---|---|---|
| `%APPDATA%\npm` PATH | 있음 | 없음 |
| npm 전역 패키지 (pm2 포함) | 있음 | 없음 |
| git config, `safe.directory` | 설정됨 | 별도 |
| **`PM2_HOME` 과 데몬** | 워커의 프로세스들 | **완전히 다른 빈 데몬** |

마지막 줄이 특히 위험하다. **관리자 창에서 `pm2 list` 를 치면 아무것도 안 나온다** — 부원들의
프로세스가 죽은 게 아니라 다른 데몬을 보고 있는 것이다. pm2 관련 명령은 **전부 `asahi` 창**
에서 돌려야 한다. 주 1회 `pm2 flush` 를 로테이션 스크립트에 넣을 때도 마찬가지다.

작업 스케줄러 조작(`Stop-ScheduledTask`/`Start-ScheduledTask`)만 관리자 창이 필요하다.

## 2. PowerShell 5.1

미니PC 는 Windows PowerShell 5.1 이다. PowerShell 7 이 아니다.

- **`Get-Process` 에 `CommandLine` 속성이 없다.** PowerShell 6+ 에서 추가됐다. 없는 속성을
  `Select-Object` 로 고르면 **오류 없이 빈 칸**이 나와서 "프로세스 정보를 못 읽는다"고
  오해하기 쉽다. 5.1 에서는 WMI 를 써라:
  `Get-CimInstance Win32_Process -Filter "Name='node.exe'" | Format-List ProcessId,CommandLine`
- **콘솔 코드페이지가 949 다.** 한글이 든 문자열을 PowerShell 명령줄에 직접 타이핑·붙여넣기
  하면 깨질 수 있다. 실제로 그것 때문에 테스트 하나가 통째로 무효가 됐다. 한글 경로가
  필요하면 **타이핑하지 말고 파일시스템에서 읽어와라**:
  `$p = (Get-ChildItem <부모> -Directory | Select-Object -First 1).FullName`
- **파일을 읽을 때 인코딩을 명시해라.** `Get-Content` 는 기본이 cp949 라 워커가 쓴 UTF-8
  로그가 깨져 나온다. 항상 `-Encoding UTF8` 을 붙인다.
- **`--%`(파싱 중단 토큰)가 `.cmd` 배치에는 안 먹는다.** `pm2` 는 `pm2.cmd` 라서 `pm2 --% ...`
  는 `unknown option '--%'` 로 실패한다.
- **PowerShell 이 `--` 를 먹는 경우가 있다.** `pm2 start ... -- /c "..."` 를 PowerShell 에서
  직접 치면 pm2 가 `/c` 를 두 번째 스크립트로 오해해 `Script not found: C:\c` 가 난다. 같은
  명령을 cmd.exe 로 돌리면 정상이다. **워커는 cmd.exe 경로를 쓰므로**, 프로덕션 동작을
  재현하려면 배치 파일에 넣고 `cmd /c <bat>` 로 돌려라.
- Bash 툴로 heredoc 을 쓸 때 `\\1` 같은 시퀀스가 octal escape 로 해석돼 깨진다. 백슬래시가
  든 내용은 파일 쓰기 도구로 직접 써라.
- **`sh_exec` 로 받는 출력의 한국어도 같은 이유로 깨진다.** 워커는 자식 프로세스의 stdout/
  stderr 를 `c.toString()` 으로 모으는데(`agent/src/remote/executors.ts`), 인자가 없으면
  Node 는 **UTF-8 로 디코드**한다. 윈도우 내장 명령은 한국어 메시지를 시스템 코드페이지
  (cp949)로 내보내므로 그대로 mojibake 가 된다 — 2026-07-31 에 `type` 의 "지정된 경로를 찾을
  수 없습니다"와 `timeout` 의 "입력 리디렉션이 지원되지 않습니다"가 둘 다 깨져서 왔다. 두
  번 다 비서가 문맥으로 알아맞혔지만 그건 추론이지 신뢰할 수 있는 경로가 아니다. **깨진
  문자열을 보고 "파일이 잘못됐다"고 오진하지 마라** — 명령이 실패한 이유는 멀쩡한데 그 설명만
  깨진 것일 수 있다. node·npm·vite 처럼 UTF-8 로 출력하는 프로그램은 영향이 없다. 근본
  해결은 `.bat` 인코딩과 같은 cp949 문제라 `iconv-lite` 급 의존성이 필요하다 — 지금은 한계로
  두고 있다.

## 3. 배포 순서 — 워커를 먼저 멈춰라

### 봇 배포와 워커 갱신은 별개다 — `proc_*`·`fs_*`·`sh_exec` 검증의 선행조건

머지하면 Railway 가 봇을 자동 배포한다. 미니PC 워커는 `asahi-worker-update` 작업을
**등록하면** 자동으로 갱신된다 — 등록 후에는 그 작업이 5분마다 `origin/main` 을 확인해 새
커밋을 찾을 때 센티넬 파일로 워커를 스스로 내리고, 작업 스케줄러 재시작 정책이 새 코드로
다시 띄운다(`deploy/update-worker.ps1`, `deploy/worker-셋업.md` "자동 갱신" 절). **이 등록은
미니PC 마다 사람이 한 번 해야 하는 수동 절차라, 병합됐다고 모든 미니PC 에 자동으로 들어가
있는 것이 아니다** — 그 미니PC 의 작업 스케줄러에 `asahi-worker-update` 가 실제로 있는지
먼저 확인한다. 등록해 두었어도 다만 **즉시는 아니다.**
`proc_*`·`fs_*`·`sh_exec` 의 실행기(`agent/src/remote/executors.ts`)는 봇이 아니라 **워커에서
돈다** — 이 도구들의 수정은 미니PC 가 실제로 pull 하고 워커가 재시작되기 전까지 **한 줄도
실행되지 않는다.** Railway 대시보드가 초록색인 것은 이 사실과 아무 관계가 없고, 자동 갱신을
등록해 두었어도 그 창(최대 5분 대기 + 워커가 한가해지는 시간)은 여전히 존재한다.

2026-07-31 에 자동 갱신이 있기 전 이것으로 세 번 헛짚었다. 워커의 마지막 pull 이 07-30
14:40 이었고 PR #11 은 그날 18:26 에 머지됐는데, 그 사실을 모른 채 실사용 결과(`.bat` 파일이
없다, 명령이 죽는다)를 전부 새 코드의 결함으로 해석했다. 전부 옛 코드의 정상 동작이었다 —
자동 갱신은 이 사고의 재발을 줄이려고 만든 것이지, 확인 자체를 생략해도 된다는 뜻이 아니다.

**그러니 원격 도구의 동작을 검증하기 전에 반드시 워커 버전부터 확인한다.** 아래 "배포가
됐는지 확인하는 법" 세 줄이 그 절차이고, 이제 확인 경로가 하나 더 있다 — 소유자 DM 에서
`runtime_info` 를 부르면 지금 붙어 있는 워커의 커밋과 봇 커밋의 일치 여부를 바로 보여준다
(`agent/src/core/tools.ts`). 그 둘이 15분 넘게 어긋나면 자동 갱신이 막혔다는 뜻으로 소유자
DM 에 안내가 한 번 온다(같은 조합에는 다시 오지 않는다, `agent/src/core/staleWorker.ts`).
**그래도 확인 없이 원격 도구 검증을 시작하지 마라** — 자동화도 똑같이 막힐 수 있고, 막혔을
때가 정확히 오늘 같은 오진이 나오는 순간이다. 확인 없이 시작한 검증은 무엇이 나오든 해석할
수 없다.

이 확인은 **미니PC 에서 직접** 한다. 봇에게 `sh_exec` 로 `C:\asahi-worker` 의 git 이력이나
소스를 열어 보게 시키지 마라 — 비서는 부원용 개발 환경이고 워커 소스는 시스템 내부다.
(실제로 시켰다가 비서가 "내 작업 폴더 밖이고 시스템 내부라 선을 넘는다"며 거절했다. `sh_exec`
는 경로 게이트 대상이 아니라 집행 계층이 막은 게 아니므로 능력 경계로 착각하면 안 되지만,
어시스턴트로서는 옳은 행동이었다.)

### 갱신 순서 — 자동화가 막혔을 때 쓰는 수동 경로

평소엔 위 자동 갱신이 이 순서를 대신 밟는다. 이 절이 필요한 순간은 **자동화가 막혔을
때다** — `asahi-worker-update` 작업이 꺼져 있거나 실패를 반복하거나(15분 알림으로
알아챈다), 또는 이 자동 갱신 기능 자체를 미니PC 에 처음 들이는 마지막 한 번(그 기능은
자기 자신을 자동으로 배포하지 못한다). 자동화가 막혔다는 것은 곧 **원인 불명 상태**라는
뜻이므로, 이럴 때일수록 아래 순서를 건너뛰지 말고 그대로 손으로 밟아 워커 상태를 직접
눈으로 확인한다.

미니PC 갱신 순서다. **순서를 지키지 않으면 `npm ci` 가 실패한다.**

워커는 `tsx` 로 실행되고 tsx 는 esbuild 를 쓴다. `npm ci` 는 `node_modules` 를 통째로 지우고
다시 까는데, 실행 중인 워커가 `esbuild.exe` 를 잡고 있으면 unlink 가 거부된다
(`EPERM: operation not permitted, unlink ...esbuild.exe`). 권한 문제가 아니다.

1. 관리자 창: `Stop-ScheduledTask -TaskName asahi-worker`
2. `asahi` 창: `cd C:\asahi-worker; git pull; cd agent; npm ci`
3. 관리자 창: `Start-ScheduledTask -TaskName asahi-worker`

**배포가 됐는지 확인하는 법** — 셋 다 맞아야 한다.

```powershell
# asahi 창
cd C:\asahi-worker; git log -1 --format="%h %s"; (Get-Item .git\FETCH_HEAD).LastWriteTime
Get-CimInstance Win32_Process -Filter "Name='node.exe'" | Select-Object ProcessId,CreationDate
```

- HEAD 가 목표 커밋을 포함하는가
- 바뀐 소스가 실제로 디스크에 있는가 (`Select-String` 으로 새 심볼을 직접 확인)
- **워커 프로세스의 `CreationDate` 가 pull 시각보다 뒤인가** — 워커는 tsx 로 소스를 그대로
  읽으므로 빌드는 필요 없지만, **재시작을 안 했으면 메모리에 옛 코드가 남아 있다.**
  pull 보다 먼저 뜬 워커라면 배포가 안 된 것과 같다

워커 로그는 `C:\asahi-worker\logs\worker.log` 다(리포 루트가 아니다). 타임스탬프가 없어서
연결/재연결이 몇 분 사이인지 며칠 사이인지 구별할 수 없다 — 알려진 관찰성 공백이다.

## 4. PM2

`proc_*` 도구가 PM2 에 위임한다. 다음은 전부 미니PC 실측 결과다.

- **`pm2 delete` 는 프로세스 트리를 통째로 정리한다.** PM2 의 기본 `treekill` 이 윈도우에서
  제대로 동작한다. 손자가 남는다고 생각해서 별도 트리 kill 을 넣었다가 되돌렸다.
- **`pm2` 를 배치 파일 안에서 `call` 없이 부르면 제어가 넘어가고 돌아오지 않는다.** `pm2` 는
  `pm2.cmd` 배치라서 그렇다. 배치에 pm2 호출이 두 줄 이상이면 `call pm2 ...` 로 써라.
  (같은 이유로, 우리가 생성하는 스크립트에 명령 뒤에 무언가를 덧붙이면 그건 실행되지 않는다.)
- **`pm2 logs` 는 신뢰할 수 있는 진단 근거가 아니다.** pm2 의 stdout 캡처는 파이프 버퍼링이라,
  확실히 실행 중인 프로세스가 **0바이트 로그**를 낸다. `ping -t` 로 실증했다. **빈 로그는
  실패의 증거가 아니다.** 실행 여부를 확인하려면 명령이 파일을 쓰게 해서 그 파일을 봐라.
- **`online` 은 "동작 중"이 아니다.** 인자가 잘못 전달돼 대화형 셸이 뜨면 아무것도 안 하면서
  `online` 으로 보인다. 메모리를 함께 봐라 — 실패한 것들은 `0b` 였고 정상은 8mb 대였다.
- **PM2 ecosystem JSON 파일은 이 문제를 해결하지 못한다.** `script`+`args` 배열로 넘겨도
  똑같이 실패했다. 시도해 봤고 안 된다.
- PM2 데몬은 첫 `pm2` 호출 때 뜬다. **누가 먼저 부르느냐에 따라 데몬의 부모가 정해진다.**
  워커가 먼저 부르면 데몬이 워커의 작업 스케줄러 잡 안에서 태어나고, 그러면
  `Stop-ScheduledTask` 가 데몬까지 데려갈 수 있다(윈도우의 `detached` 는 잡을 벗어나지 못한다).
  대처는 [worker-셋업](../deploy/worker-셋업.md) 참고. **`pm2 resurrect` 는 쓰지 않는다** —
  "재부팅하면 전부 사라진다"는 의도된 설계를 깨뜨린다.

## 5. cmd.exe 인용 경계 — 가장 비쌌던 함정

`proc_start` 가 실사용에서 한 번도 성공하지 못했던 원인이다. 두 번의 잘못된 수정을 거쳤다.

`buildPm2CommandLine`(`agent/src/remote/executors.ts`)은 인자를 **MSVCRT 규칙**으로 인용한다 —
따옴표 앞 백슬래시를 `2n+1` 로 늘리고 `"` 를 `\"` 로 쓴다. 이건 `CommandLineToArgvW` 기준으로
정확한 구현이다.

그런데 그 문자열을 `spawn(commandLine, { shell: true })` 이 넘기면 **cmd.exe 가 먼저 파싱한다.**
그리고 **cmd.exe 는 `\"` 를 모른다.** 백슬래시를 그냥 문자로 두고 따옴표 개수만 세므로, 첫
내부 따옴표 이후 토큰 경계가 전부 어긋난다.

명령은 **공백이 있을 때만** 인용된다. 그래서 `ping -t 127.0.0.1` 같은 사소한 테스트 명령은
전부 통과하고 실제 명령만 실패했다.

실측 매트릭스:

| 형태 | 경로 | 결과 |
|---|---|---|
| 명령줄 전달 | ASCII, 공백 없음 / 따옴표 없는 명령 | online |
| 명령줄 전달 | 한글 + 공백 / `\"` 든 명령 | stopped, 0b |
| 명령줄 전달 | **ASCII + 공백** / `\"` 든 명령 | **stopped, 0b** |
| ecosystem JSON | ASCII + 공백 | stopped, 0b |
| **스크립트 파일** | ASCII + 공백 | **online** |
| **스크립트 파일** | 한글 + 공백 (`--cwd` 로 전달) | **online** |

세 번째 줄이 결정적이다 — 한글을 빼고 공백만 남겨도 실패한다. 이걸 확인하기 전까지는
"한글 인코딩 문제"와 "인용 문제"를 구별하지 못했다.

**해법**: 회원 명령을 **스크립트 파일 내용**으로 옮긴다. 파일 내용은 어떤 셸도 파싱하지
않으므로 이스케이프가 통째로 사라진다. 명령줄에는 단순 경로만 나간다.

**내부에 따옴표가 없는 단순 인용(`"C:\경로 with space"`)은 cmd.exe 가 정상 처리한다.** 그래서
`--cwd` 로는 한글·공백 경로를 그대로 넘길 수 있다. 문제는 오직 `\"` 다.

### 배치 파일 인코딩

여기에 두 번째 층이 있다. **cmd.exe 는 배치 파일을 시스템 ANSI 코드페이지로만 읽는다**(이
기계는 cp949).

| 배치 인코딩 | 한글 경로가 든 명령 |
|---|---|
| UTF-8 (BOM 없음) | stopped |
| UTF-8 + `chcp 65001>nul` 첫 줄 | **stopped** — chcp 로는 안 된다 |
| cp949 | online |

`chcp` 를 파일 안에 넣어도 이미 늦다 — cmd 가 그 줄을 읽을 때는 이미 해당 코드페이지로
디코딩한 뒤다. **`chcp` 를 추가해서 "고치려" 하지 마라. 시도했고 안 된다.**

Node 에는 cp949 인코더가 없어서, 현재 설계는 **스크립트를 ASCII 전용으로 제한하고 비ASCII
명령을 거부**한다. 작업 폴더는 `--cwd` 로 나가고 그건 `CreateProcessW` 를 통해 UTF-16 이라
안전하므로, 실무 제약은 좁다 — `npm run dev` 류는 영향이 없고 `node 서버.js` 만 막힌다.

미해결 대안: `.ps1` + UTF-8 BOM. PowerShell 은 BOM 있는 UTF-8 을 제대로 읽으므로 한글이
살아난다. 실행 정책과 기동 비용이 붙고 **하드웨어 검증이 필요하다.**

## 6. 작업 스케줄러

워커는 `asahi-worker` 라는 작업으로 등록돼 있다. 등록할 때 겪은 것들:

- **`-LogonType S4U` 로 다른 사용자 작업을 만들면 `0x80070005`** 가 난다. S4U 는
  `SeTcbPrivilege` 가 필요하다. `-User`/`-Password` 를 써라.
- 등록은 됐는데 `State` 가 `Ready` 이고 **실행이 안 되면서 `LastTaskResult 267011`** 이면,
  그 계정에 **배치 로그온 권한(`SeBatchLogonRight`)이 없는 것**이다. 이벤트 로그에
  `0x80070569 ERROR_LOGON_TYPE_NOT_GRANTED` 가 남는다. `secedit` 로 부여한다.
- 작업이 안 도는 원인을 추측하지 말고 **이벤트 로그를 봐라.** `LastTaskResult` 만으로는
  로그온 실패와 프로세스 실패가 구별되지 않는다.

## 7. 모델과 디스코드의 행동

코드가 아니라 **모델의 행동** 때문에 검증이 무의미해지는 경우가 있다.

- **모델은 실패하는 도구를 우회한다.** `proc_start` 가 실패하자 비서가 `sh_exec` 로 개발서버를
  직접 띄웠다. 겉보기엔 "개발서버 띄워줘"가 성공했지만 **고친 코드 경로는 한 번도 안 지났다.**
  도구를 검증할 때는 **도구 호출을 명시적으로 강제**하고, **새 대화**에서 해라(같은 대화면
  앞선 실패 기억이 남아 또 우회한다).
- **모델이 게이트에 닿기 전에 스스로 거절한다.** 시스템 프롬프트에 "한 사람당 하나만"이
  적혀 있으면, 모델이 도구를 부르지 않고 자기 말로 먼저 거절한다. 그러면 게이트는 검증되지
  않은 것이다. 진행 표시에 `✗ <도구>` 가 남았는지로 판별해라. 요청할 때 이렇게 써라:
  *"네가 미리 판단하지 말고 실제로 도구를 호출해서 돌아온 문구를 한 글자도 바꾸지 말고 보여줘"*
- **디스코드 마크다운이 백슬래시와 별표를 먹는다.** 경로나 glob 을 채팅으로 주고받으면
  원문과 달라진다. 게이트 메시지를 검증할 때 특히 조심해라.

## 8. 진단 — 무엇이 어디에 기록되나

추측하기 전에 여기부터 봐라.

- **`actions` 테이블 (Supabase)** — 모든 도구 호출이 기록된다: `ts`, `tool`, `status`,
  `input`, `result_summary`, `duration_ms`. **실패의 실제 문구가 여기 남는다.** 무엇이 언제
  왜 실패했는지 재구성하는 가장 빠른 길이다. Supabase MCP 로 바로 질의할 수 있다:

  ```sql
  select to_char(to_timestamp(ts/1000) at time zone 'Asia/Seoul','MM-DD HH24:MI:SS') as t,
         tool, status, left(coalesce(input,''),70) as input,
         left(coalesce(result_summary,''),150) as result
  from actions order by ts desc limit 30;
  ```

  프로젝트 ref 는 `list_projects` 로 확인해라(이름이 `Asahi` 인 것).

  **`status` 의 의미는 워커가 갱신된 시점부터 바뀐다.** 이제 `error` 는 **도구가 제 일을 못 한
  것**만 가리킨다(워커 미연결·spawn 실패·타임아웃·게이트 거부). `sh_exec` 가 실행한 명령이 0이
  아닌 종료 코드로 끝난 것은 `status='ok'` 다 — 셸에서 non-zero 는 실패가 아니라 통신 수단이기
  때문이다(`findstr` 의 1 = 매칭 없음).

  **경계는 날짜가 아니라 워커 버전이다.** 이 변경은 워커에서 도는 실행기(`executors.ts`)의
  것이라 봇이 배포된 순간이 아니라 미니PC 를 `git pull` 하고 워커를 재시작한 순간부터
  적용된다(위 3절). 그 사이에 쌓인 행은 여전히 옛 의미다. **경계를 넘어 섞어서 집계하지
  마라** — 옛 행은 두 가지를 뭉뚱그린 값이다. 어느 행이 어느 쪽인지는 워커의 마지막 pull
  시각으로 가른다(3절 "배포가 됐는지 확인하는 법").

  **종료 코드를 `result_summary` 에서 찾지 마라 — 대개 없다.** `result_summary` 는 본문의
  **앞** 200자다(`agent/src/core/agent.ts` 의 `body.slice(0, RESULT_SUMMARY_MAX)`). 종료 코드는
  본문 **끝**에 `(종료 코드 N)` 으로 붙으므로, 출력 전체가 200자 안에 들어가는 짧은 명령에서만
  우연히 같이 담긴다. 긴 명령(`npm run build` 등)의 종료 코드는 이 표에 남지 않는다 — 그 턴의
  디스코드 대화나 워커 로그로 가야 한다.
- **워커 로그** — `C:\asahi-worker\logs\worker.log` (`-Encoding UTF8` 로 읽어라)
- **PM2 로그** — `C:\Users\asahi\.pm2\logs\<name>-out.log` / `-error.log`. 앱이 사라져도
  파일은 남는다. 단 버퍼링 때문에 비어 있을 수 있다(위 4절)
- **Railway 로그** — 봇 쪽. Railway MCP 로 접근
- **`.superpowers/sdd/progress.md`** — 작업 원장. git-ignore 되지만 세션 간 복구 지도다

  아니라 이 문제부터 의심해라.
- **`owner-laptop` 의 `allowed_dirs` 가 0행** — 소유자 PC 에서 DM 으로 `allow_dir` 재등록 필요
- **상시 표시 UI 없음** — 개발서버 상태를 실시간으로 계속 보여주는 수단은 아직 없다.
  디스코드 메시지로는 구조적으로 불가능해서 별도 표면(웹 UI)이 필요하다. 로드맵 항목
- **워커 로그에 타임스탬프 없음** — 위 3절

## 10. 되풀이된 실패 패턴 (요약)

바쁘면 이것만 읽어라.

1. **확인하고 움직여라.** 배포·머지·실행 여부를 기억으로 단정하지 마라
2. **변수는 하나씩.** 두 개를 동시에 바꾼 비교로 원인을 정하지 마라
3. **비서 자신의 말을 읽어라.** 프로세스 목록보다 비서가 남긴 설명이 정확할 때가 있다
4. **`online`·초록색 테스트·빈 로그는 증거가 아니다.** 각각 다른 이유로 거짓말을 한다
5. **도구를 검증할 땐 호출을 강제해라.** 모델은 우회하고, 자기 말로 먼저 거절한다
6. **이음매 뒤의 코드는 테스트가 지나가지 않는다.** `runPm2` 같은 주입 지점 너머의 실제
   구현은 하드웨어에서만 검증된다. 그 사실을 계획 단계에서 의식해라
7. **원격 도구를 검증하기 전에 워커 버전을 확인해라.** 봇 배포는 워커를 갱신하지 않는다 —
   옛 코드로 관측한 결과는 무엇이든 해석할 수 없다 (3절)
8. **판별 명령은 부작용으로 판정해라.** 명령이 파일을 쓰게 하고 그 파일을 봐라. 로그·상태
   표시는 각자의 이유로 거짓말한다 (4절, [스모크 테스트](../deploy/smoke-test.md) 함정 5)
