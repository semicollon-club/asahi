# 위험 등록부 (Risk Register)

알려진 한계를 완화 관점에서 정리한다. 정확한 사칭 절차·재현 페이로드 같은 악용 세부는
싣지 않는다 — 여기서는 위협의 성격과 현재 완화책만 서술한다. 상세 능력 계층은
`docs/security/capability-model.md` 참고.

## 1. 워커 토큰(`workers` 테이블) 취급

각 워커는 `workers` 테이블(레지스트리, `agent/src/store/workersRepo.ts`)에 등록된 자기
고유의 신원(`id`, `kind`: `personal`|`shared`)과 토큰을 갖는다 — 1단계 전체를 통틀어 단일
공유 비밀은 더 이상 없다. 토큰 평문은 저장하지 않는다 — `register-worker`
CLI(`agent/src/scripts/registerWorker.ts`)가 32바이트 랜덤 토큰을 생성해 **stdout 에 한
번만** 출력하고, DB 에는 `sha256` 해시(`hashWorkerToken`)만 남긴다. 허브
(`agent/src/remote/hub.ts`)는 접속마다 `hello` 프레임의 `workerId` 로 이 테이블을 조회해
해시를 대조한다.

이 토큰 하나가 새어나가면, 그 값을 아는 사람이 그 **워커 하나**로 인증에 성공할 수 있다 —
`personal` 워커의 토큰이 새면 그 담당자(대개 소유자)의 개인 기계가, `shared` 워커의 토큰이
새면 동아리 미니PC가 위험에 노출된다(`docs/superpowers/specs/
2026-07-27-multi-worker-design.md` §2 의 라우팅). 등록에 성공한 뒤 할 수 있는 일은 원래
그 워커가 하던 것과 동일하다 — 모델이 그 접속 위로 보내는 `fs_read`/`fs_write`/`fs_edit`/
`fs_glob`/`fs_grep`/`sh_exec` 호출을 전부 받아 실행하고, 결과(`result` 프레임)를 조작해
돌려줄 수 있다(허브는 그 접속이 보낸 결과를 그대로 신뢰한다). 반대로 이 값 하나로는
Postgres(`DATABASE_URL`)에도, 소유자의 Claude 구독(`CLAUDE_CODE_OAUTH_TOKEN`)에도 접근할
수 없다 — 워커는 이제 이 두 자격증명을 아예 갖지 않는다(`docs/decisions/
0006-thin-worker.md`).

**완화**: `.env` 는 저장소에 커밋하지 않는다(`.env.example` 만 형태를 공유). 토큰은 사람이
고르지 않고 `register-worker` 가 32바이트 랜덤으로 생성하며, 빈 토큰은 해시 비교 전에
거부한다(`agent/src/remote/hub.ts` 의 `authenticate`). 허브는 토큰을 상수 시간
비교(`timingSafeEqual`)하고, 등록되지 않은 `workerId` 와 토큰 불일치를 같은 거부 사유로
응답해 인증 오라클을 막는다(`tokensMatch`/`DENIED_REASON`) — 대조값 자체도 프로세스마다
랜덤인 `NOT_FOUND_HASH` 라 "없는 워커" 경로는 어떤 입력으로도 맞출 수 없다. 토큰
재발급(`register-worker` 를 같은 `--id` 로 재실행)은 이전 토큰을 즉시 무효화하지만,
**이미 인증까지 끝나 연결돼 있는 워커는 끊지 않는다** — 허브는 해시를 인증 시점에만 본다.
유출된 토큰으로 이미 붙어 있는 연결을 즉시 끊어야 한다면 봇을 재시작해야 한다
(`deploy/worker-셋업.md` 참고).

## 2. 손님도 공유 워커에 연결된다 — 폴더 격리의 실제 경계

1단계부터 손님도 원격 도구를 받는다 — `role='allowed'`(소유자가 `manage_access` 로 명시적으로
등록한 동아리원)이면, 공유 워커(동아리 미니PC, `kind='shared'`)가 연결돼 있는 한 DM 에서든
서버 채널에서든 `fs_*`/`sh_exec` 가 열린다(`agent/src/core/tools.ts` 의 `allowedToolsFor`).
손님이 자기 PC 에 개인 워커를 두는 것은 여전히 지원하지 않는다 — 소유자의 구독으로 도는
작업이 소유자가 보지 못하는 기계에서 벌어지는 것을 피하려는 의도된 설계다
(`docs/superpowers/specs/2026-07-27-multi-worker-design.md` §2.1).

파일 도구(`fs_read`/`fs_write`/`fs_edit`/`fs_glob`/`fs_grep`)는 `scopeDirs`
(`agent/src/core/workerSelect.ts`)가 손님을 `<루트>/<그 손님의 디스코드 userId>/` 하위로
가둔다 — 다른 손님의 폴더나 그 폴더 밖 경로를 지정하면 봇 쪽 1차 필터에서 거부된다. 하지만
**`sh_exec` 는 이 스코프의 대상이 아니다** — 경로 인자 자체가 없어(§5 참고) `scopeDirs` 가
좁힌 폴더 목록을 아예 거치지 않는다. 셸 명령의 실행 시 작업 디렉토리(cwd)는 그 좁혀진
폴더가 되지만(`remote/executors.ts` 의 `sh_exec` 는 `roots[0]` 을 cwd 로 쓰고, 손님 호출
시 `roots` 는 이미 `scopeDirs` 로 좁혀진 값이다), `cd`·절대경로·PATH 탐색으로 그 밖에
얼마든지 접근할 수 있다. **폴더 격리는 실수를 막는 안전장치이지, 의도적으로 남의 파일을
보려는 손님을 막는 경계가 아니다** — 동아리원이 다른 동아리원의 파일을 보려고 마음먹으면
셸 하나로 충분하다. 실질적 경계는 정확히 하나, 공유 워커 프로세스를 돌리는 미니PC 의 OS
계정 권한이다.

억제 요소는 둘이다.

- `decideRoute`(`agent/src/adapters/discord.ts`)가 role 이 `owner`/`allowed` 가 아닌 사용자의
  메시지를 애초에 무시한다 — 노출 대상은 소유자가 명시적으로 등록한 동아리원뿐이다.
- 페르소나의 외부 콘텐츠 불신 규칙(`agent/src/core/persona.ts` 의 `IDENTITY`) — 다만 이는
  시스템 프롬프트 수준의 지시일 뿐 코드로 강제되는 방어가 아니다.

**완화**: 미니PC 를 관리자가 아닌 표준(비관리자) 로컬 계정으로 운영하고, 그 계정 프로필에
SSH 키·`.env`·저장된 브라우저 자격증명을 두지 않는다(`deploy/worker-셋업.md` "미니PC 셋업"
참고) — 이건 권장이 아니라 이 설계가 요구하는 전제조건이다(`docs/superpowers/specs/
2026-07-27-multi-worker-design.md` §6). 사용자별 토큰·`kind` 구분(§1)으로 워커 신원 자체는
분리돼 있으므로, 이 위험은 "워커를 사칭당하는" 문제가 아니라 "정당하게 인증된 손님이 그
스코프 밖으로 나가는" 문제다.

## 3. 하드 크래시 중 응답 전송 유실 가능성

프로세스가 디스코드 응답 전송 도중 하드 크래시하면, 그 응답 1건은 재전송되지 않는다. 생성된
텍스트 자체는 이벤트 로그에 보존되지만, 사용자에게 다시 보내 주지는 않는다. 정상적인 그레이스풀
종료(SIGTERM 등)는 flush 로 처리되어 이 유실이 없다.

**완화**: 배포 환경(PM2/Railway)은 그레이스풀 셧다운을 우선 사용하도록 운영한다. 완전한
재전송 보장이 필요해지면 응답 전송 자체를 멱등 작업 큐로 옮기는 후속 설계가 필요하다.

## 4. pg-mem 으로 검증 못 하는 보장 — READ ONLY 트랜잭션

자기인지 DB 조회(`db_query`)의 핵심 방어선은 Postgres 의 `SET TRANSACTION READ ONLY` 다
(`agent/src/store/introspectRepo.ts`). 유닛 테스트는 인메모리 Postgres 구현(pg-mem)을 쓰는데,
pg-mem 은 이 구문을 파싱하지 못해(스파이크로 확인) READ ONLY 강제를 흉내조차 내지 못한다.

**완화**: 해당 테스트는 유닛 테스트 스위트에서 명시적으로 skip 처리하고, "실제 쓰기 거부
동작"은 실 Supabase 환경에서의 스모크 테스트로만 검증하기로 문서화해 둔다
(`docs/status/STATUS.md` 참고). 사전검사(`assertReadOnlySql`)는 pg-mem 으로도 정상 검증된다 —
비어 있는 건 DB 단 방어선 하나뿐이다.

## 5. `sh_exec` — 경로로 봉쇄되지 않는 셸 실행

`fs_read`/`fs_write`/`fs_edit`/`fs_glob`/`fs_grep` 는 봇 쪽 `allowed_dirs` 1차 필터와 워커
쪽 `WORKER_ROOTS` 최종 판정, 두 겹을 통과해야 하지만(`docs/security/capability-model.md`
§경로 게이팅), `sh_exec` 는 이 두 겹 어디에도 속하지 않는다 — 셸 명령은 경로 인자 하나로
판정할 수 있는 대상이 아니다(파이프·서브셸·`cd`·PATH 탐색 등으로 인자 검사를 얼마든지
우회한다). `agent/src/remote/executors.ts` 의 `sh_exec` 실행기는 경로 검사를 시도조차 하지
않고 `spawn(command, { cwd: roots[0], shell: true })` 로 그대로 실행한다.

남는 경계는 정확히 두 가지뿐이다 — 실행 시 작업 디렉토리(공유 워커의 손님이면 `scopeDirs`
로 좁혀진 그 사람의 폴더, 그 외엔 `WORKER_ROOTS` 의 첫 번째 폴더)와, 워커 프로세스를 돌리는
OS 계정의 권한. 그 계정이 닿는 곳이라면 셸 명령은 그 cwd 밖도 얼마든지 오갈 수 있다 — 이건
이전 SDK 내장 `Bash` 도구가 가졌던 것과 같은 성격의 한계이며, 얇은 워커 전환으로 새로 생긴
약점이 아니다(`docs/decisions/0006-thin-worker.md`).

**신원 게이팅은 호출 가능한 사람을 좁히지만, 더 이상 "소유자만"이 아니다.** 미등록 사용자는
`decideRoute` 가 애초에 무시하므로 도달조차 못 하지만, 등록된 사용자(`role` 이 `owner`/
`allowed`) 안에서는 워커 연결 여부 하나가 곧 `sh_exec` 접근 여부다 — 소유자·손님 구분 없이
동일하다(Task 7, `docs/superpowers/specs/2026-07-27-multi-worker-design.md`). 손님이
공유 워커에서 이 도구를 받을 때 폴더 격리가 주는 착시와 그 한계는 §2 참고.

**완화**: 잔여 위험은 애플리케이션 코드가 아니라 **운영**으로만 줄어든다 — 워커를 최소
권한(비관리자) OS 계정으로 돌리고, `WORKER_ROOTS` 를 실제로 노출해도 되는 폴더로 좁히는
것이 유일한 실질적 완화다(`deploy/worker-셋업.md` "미니PC 셋업" 참고). 손님에게 `sh_exec`
를 여는 것은 더 이상 미래의 시나리오가 아니라 1단계의 현재 상태다 — OS 수준 격리(별도
계정/컨테이너/VM) 없이 이미 진행됐으므로, 이 문서 §2 가 그 실제 경계를 서술한다.

## 6. 읽기전용 조회 결과 크기 제한

자기인지 SQL 조회 도구(`db_query`)는 현재 애플리케이션 단(`IntrospectRepo.readOnlyQuery`)에서
`maxRows` 로 결과를 자르는 방식이다. 매우 큰 결과 집합에 대해서는 SQL 단 `LIMIT` 적용 같은
후속 개선이 필요하다 — 지금은 잘라내기 이전에 전체 결과를 한 번 받아오므로 메모리 사용량
관점에서 최적은 아니다.

**완화**: `statement_timeout` 을 함께 걸어 두어(§4) 무거운 쿼리가 오래 붙잡히지는 않는다.

## 7. 손님 폴더 안 심볼릭 링크·정션이 `fs_*` 격리를 우회한다

워커의 최종 경로 관문(`checkPath`, `agent/src/remote/roots.ts`)은 대상 경로를
`resolveRealOrNearestAncestor`(`agent/src/core/pathPermission.ts`)로 realpath 정규화한 뒤,
그 결과가 **워커의 `WORKER_ROOTS` 안**에 있는지만 확인한다 — 그 손님의 `scopeDirs` 로
좁혀진 하위 폴더 안에 있는지는 다시 확인하지 않는다. 손님의 폴더 안에 워커 루트 밖(또는
다른 손님의 폴더)을 가리키는 심볼릭 링크나 정션을 만들면, realpath 정규화 후 그 링크가
가리키는 실제 경로가 `WORKER_ROOTS` 안에만 있으면 `checkPath` 를 통과한다 — 즉 `fs_*` 가
광고하는 "자기 폴더 밖은 못 본다"는 격리를 링크 하나로 빠져나갈 수 있다.

**받아들이는 이유**: 이미 §2·§5 에서 서술했듯 같은 손님은 어차피 경로 무제한 `sh_exec` 를
갖는다 — 이 우회는 새로운 권한 상승이 아니라 그 위험에 종속된다. 폴더 격리가 막으려던 건
"의도치 않은 실수"이지 "마음먹은 우회"가 아니었으므로, 별도 대응 없이 문서화만 하고
받아들인다. 코드로 고치려면 `checkPath` 가 워커의 루트가 아니라 호출자별 스코프를 알아야
하는데, 그러면 오늘은 아예 없는 "호출자 인지 경로 관문"을 워커 쪽에 새로 만들어야 한다 —
`sh_exec` 가 이미 그 경계를 무너뜨리는 상황에서 이 비용을 들일 이유가 약하다.

## 8. 워커를 `kind='shared'`로 잘못 등록하는 것을 막는 장치가 없다

`register-worker` CLI(`agent/src/scripts/registerWorker.ts`)도 `WorkersRepo`
(`agent/src/store/workersRepo.ts`)도 어떤 물리적 기계가 실제로 공용인지 검증하지 않는다 —
운영자(소유자)가 실수로, 혹은 다른 이유로 소유자의 개인 노트북을 `--kind shared` 로
등록하면 그 순간부터 `resolveWorkerSelector`(`agent/src/core/workerSelect.ts`)의 라우팅
규칙에 따라 모든 손님이 그 노트북으로 연결된다 — 소유자의 개인 파일이 있는 기계에 동아리
전원의 `sh_exec` 가 열리는 셈이다.

**받아들이는 이유**: 이는 코드로 강제되는 방어가 아니라 순수한 운영 실수다 — "어느 물리적
기계가 공용인가"는 애플리케이션이 판단할 수 있는 사실이 아니다(등록 시점에 `--kind` 를
신중히 확인하는 것 외에 원천적으로 막을 방법이 없다). 1단계에서 실제로 존재하는 워커 행이
소유자 노트북(`personal`)과 동아리 미니PC(`shared`) 둘뿐이라 오분류의 여지가 작고, 오분류가
일어나도 그 결과(개인 기계에 공유 도구가 열림)는 관찰 가능하다 — 워커 등록 목록·`kind` 를
점검하는 것으로 스스로 확인할 수 있다.

## 9. `sh_exec` 환경의 단기 깃허브 토큰(2026-09-05)

부원이 디스코드만으로 동아리 저장소를 clone·push 하고 PR 을 내게 하려고, 봇이 `sh_exec` 호출마다
조직 전체·`contents:write`·최대 1시간짜리 GitHub App 설치 토큰을 그 셸 프로세스의 환경변수로
넘긴다(`agent/src/core/remoteTools.ts` 의 `shellGitArgs`, `agent/src/remote/gitEnv.ts`,
`docs/superpowers/specs/2026-09-05-worker-git-credentials-design.md`). 발행 설계 §11 이 "푸시가
도는 동안의 토큰 관찰"로 받아들였던 위험의 시간 창이 몇 초에서 최대 한 시간으로, 대상이 리포
하나에서 조직 전체로 넓어진 것이다.

`sh_exec` 를 받는 부원은 환경변수를 찍어 그 토큰을 읽고, 한 시간 동안 디스코드 밖에서 조직 리포에
`contents:write` 를 쓸 수 있다 — 브랜치 push·강제 push·브랜치 삭제·비공개 리포 clone. 리포
생성·삭제는 못 한다(그건 `administration` 이고 셸 토큰에는 없다). Postgres·Claude 구독·App
개인키에는 여전히 닿지 못한다.

**받아들이는 이유**: 그 능력은 디스코드 안에서 이미 같은 사람에게 허용하기로 한 것이다 — 운영자의
결정(2026-09-05)이 "부원이 동아리 저장소에 마음대로 git 작업을 하되 main·production 병합만
운영자가 한다"이고, `sh_exec` 는 원래 명령을 가리지 않는다(§5). 토큰을 읽어 밖에서 쓰면 잃는 것은
`actions` 기록(관측)뿐이며, 깃허브 쪽에는 App 이름으로 감사 로그가 남는다. 더 좁히는 설계(push
순간에만 리포별 토큰을 봇에게 요청하는 워커 쪽 헬퍼)는 미니PC 에 깨질 자리를 넷 늘리면서 얻는 것이
"이미 허용한 능력을 조금 더 번거롭게"뿐이라 고르지 않았다(스펙 §5).

**완화**: 토큰은 `contents` 하나·최대 1시간이고, 봇이 만료 10분 전에 새로 발급하며 발급 실패는
60초만 기억한다(`agent/src/github/shellToken.ts`). 디스크·`.git/config`·명령줄에는 남지 않는다
(`agent/tests/gitEnv.test.ts` 의 실제 git 케이스가 CI 에서 지킨다). **브랜치 규칙은 깃허브 쪽
설정이 집행한다** — `production` 은 운영자만 push 할 수 있어 이 토큰으로도 올릴 수 없고(App 은
허용 목록 밖, 2026-09-05 확인), `main` 은 부원이 PR 로 쌓는 통합 브랜치라 일부러 열려 있다(CI
필수·강제 push 금지). 봇 자신이 main 에 직접 push 하지 않는 것은 페르소나 안내
(`agent/src/core/persona.ts`)뿐이며, 셸 명령을 검사해 거르는 시늉은 하지 않는다(§5 의 원칙
그대로). 조직이 Free 플랜이라 비공개 리포에는 어떤 브랜치 보호도 걸 수 없다.

## 10. 부원 세션 전사는 서로 가려지지 않는다 — **가리지 않기로 했다**(운영자 결정 2026-09-07)

하네스 턴의 세션 전사·resume 기록은 부원별 폴더(`<세션 루트>/<디스코드 userId>`, 기본은 워커 계정
프로필 아래 `.asahi-sessions`)에 나뉘어 저장된다. 그런데 **그 폴더 전부가 같은 OS 계정(워커 계정 B)의
것**이고, 하네스 턴의 내장 도구(Read/Glob/Grep/Bash)는 정확히 그 계정 권한으로 돈다. 따라서 한 부원의
세션은 **다른 부원의 대화 전사를 읽을 수 있다** — 그 안에는 상대가 봇에게 한 말, 모델의 답, 그 턴에
읽힌 파일 내용이 그대로 들어 있다.

폴더를 `WORKER_ROOTS` 밖에 둔 것은 얇은 워커의 `fs_*` 를 막을 뿐이고(그쪽은 경로 게이트가 있다),
하네스의 내장 도구에는 그 게이트가 없다(`docs/security/capability-model.md` "하네스 턴" 절).

**이것은 결함이 아니라 결정의 귀결이다.** 설계는 성능을 이유로 **부원별 OS 계정·컨테이너를 두지 않기로**
했고(설계 §5, 운영자 결정 2026-09-05), 계정이 하나면 그 계정 안에서 사람끼리 가리는 방법은 없다 — 세션이
스스로 ACL 을 바꿀 수 있는 권한을 이미 갖기 때문이다.

### 결정: 가리지 않는다 (2026-09-07, [ADR 0009](../decisions/0009-no-member-isolation.md))

**이 문서의 앞선 판은 여는 조건으로 세 갈래 중 하나를 고르라고 했다** — (가) 부원별 OS 계정·컨테이너로
돌아가기, (나) 전사를 안 남기기(resume 포기 또는 봇이 대신 보관), (다) 비공개가 아님을 명시하고 열기.
**그 요구 자체가 잘못 놓인 질문이었다.** 셋 다 "부원끼리는 서로에게 가려져야 한다"를 전제하는데, 이
프로젝트에서 그 전제가 성립한 적이 없다.

아사히는 **부원별 비서를 나눠 주는 물건이 아니라 동아리 작업을 총괄하는 하나의 에이전트**다(운영자
2026-09-07). 그리고 아사히가 도는 곳은 동아리 서버의 채널이고, **거기서 오간 대화는 이미 부원 전부에게
보인다.** 전사가 그 위에 더하는 것도 대부분 이미 열려 있다 — 그 턴에 읽힌 파일은 공용 워크스페이스의
것이고, 손님에게는 봇 허브 MCP(DB 읽기 등)가 열리지 않는다(`core/profiles.ts` 의 `mcpHub`). 남는 차이는
**스크롤을 올리는 대신 셸을 치는 것**뿐이다. 그 차이를 없애려고 지킬 수 없는 벽을 세우지 않는다.

**예외 둘은 따로 처리했다** — 공개 채널 대화가 아닌 것들이다.

- **손님 DM** — 공개가 아니고, DM 턴에는 그 사람의 개인 기억이 컨텍스트로 실린다. 무엇보다 디스코드 DM
  창은 그 자체로 "둘만 본다"는 신호를 주고, 사람은 그 신호를 믿고 **키·비밀번호를 붙여 넣는다.**
  → **통로를 닫았다**(2026-09-07, `decideRoute` 의 `dm-declined`). 안내문으로 신호를 정정하는 대신 문을
  없앴다. 소유자 DM 은 그대로다.
- **소유자 전사** — 소유자 하네스 턴은 지금 공유 워커에서 돈다. 그 전사에는 `db_query` 결과·리포 내용·
  PR 데이터가 들어 있고, 이건 공개 채널 대화가 아니다. → **개인 워커(계정 C)로 분리한다.**
  `resolveTurnWorker` 가 소유자 DM 에 개인 워커를 먼저 찾고 없을 때만 공유로 떨어지므로 **코드 변경이
  없다** — 미니PC 에 계정 하나와 예약 작업을 더해 개인 워커로 등록하면 된다. 아직 하지 않았다(게이트 항목).

**그래서 남는 사실**: 부원끼리는 서로의 하네스 세션 전사를 읽을 수 있다. 이것은 고칠 대상이 아니라
**안내에 적을 대상**이다(게이트의 "손님 안내 정정" 항목).

### 왜 반쪽 격리를 만들지 않았나

계정이 하나면 어떤 격리도 완전할 수 없다 — 세션은 자기가 만든 파일의 ACL 을 바꿀 수 있고, 내장 Bash 는
경로 게이트를 거치지 않는다. 그리고 **완전하지 않은 격리는 없는 것보다 나쁠 수 있다**(운영자 2026-09-07):

- 운영자는 경계가 있다고 믿고 확인을 멈춘다. **§12 가 그 실물이다** — "세션 계정에는 자격증명이 없다"고
  적혀 있었기 때문에, 계정 B 가 계정 A 의 홈에 모든 권한을 갖고 있는 상태를 아무도 확인하지 않았다.
- 사용자는 가려진다고 믿고 더 넣는다 — 위 DM 의 키·비밀번호가 정확히 그 형태다.

그래서 이 리포의 규칙은 이렇다. **지키지 못할 경계는 만들지 않는다. 만든 경계는 실제보다 높게 말하지
않는다.** 얕은 편의(예: §11 의 작업 폴더 스코프)는 둘 수 있지만, 코드 주석과 문서 양쪽에 "OS 경계가
아니다 — 사고를 막을 뿐 공격을 막지 못한다"를 함께 적는다. 해악은 벽의 높이가 아니라 라벨에서 나온다.

## 11. 손님 하네스 턴의 작업 폴더가 좁혀지지 않는다 (풀 하네스 4단계, 2026-09-06) — **닫음(2026-09-06)**

**닫은 방법**: 봇이 `harnessCwdFor`(`core/workerSelect.ts`)로 신원에 맞는 폴더를 정해 보낸다 — 얇은 워커의
`fs_*` 를 좁히는 `scopeDirs` 를 **그대로** 쓰므로 한 사람이 두 경로에서 같은 폴더를 받는다(손님
`<루트>/<userId>`, 소유자 루트). 좁힐 수 없으면(루트 없음·이상한 식별자) `undefined` 를 주고 그 턴은
하네스로 가지 않는다 — 실패가 루트로 넓어지지 않는다. 워커는 받은 값을 그대로 믿지 않고 `checkPath` 로
자기 루트 안인지 다시 판정한 뒤(심볼릭 링크·정션 해소 포함, §7) 그 실경로를 cwd 로 쓰고, 없으면 만든다
(손님의 첫 턴). `send_file` 의 스코프도 같은 값이다. 아래 "완화의 한계"는 그대로 유효하다.

원래 문제: `runHarnessTurn`(`agent/src/core/agent.ts`)은 세션의 작업 폴더를 **워커 루트의 첫 번째 폴더**
(워크스페이스 루트)로 줬다 — 신원과 무관했다. 설계 §6 은 손님을 `<루트>/<디스코드 userId>/` 로 좁히라고
하는데 그 코드가 없었다.

**노출된 적은 없다**: 하네스는 소유자 전용이고(`decideHarnessDispatch` 가 `isOwner` 를 요구), 소유자는
원래 관리자 스코프다. 그래서 이 수정은 **오늘 동작을 바꾸지 않는다** — 5단계에서 손님 프로필을 여는 순간
비로소 값을 갖는 전제조건이다(프로필 표 `core/profiles.ts` 가 손님 값을 미리 정의해 둔 것과 같은 성격).

**완화의 한계**: 이 스코프는 얇은 워커의 `fs_*` 경로 게이트와 달리 **모델에게 주는 작업 폴더일 뿐**
OS 경계가 아니다(§5 의 `sh_exec` 와 같은 성격) — 내장 Bash 로 얼마든지 밖을 볼 수 있다. 그래도 실수를
막는 첫 선이고 "남의 폴더가 기본으로 보이지는 않는다"는 차이가 있으므로, 여는 조건으로 둔다.

## 12. 워커 계정이 봇 계정 홈에 모든 권한을 갖고 있었다 (2026-09-07) — **닫음(2026-09-07)**

**발견**: 미니PC 의 `C:\Users\asahi-bot`(계정 A 의 홈) ACL 에 워커 계정의 항목이 있었다 — 읽기가 아니라
**모든 권한**이고, 그 아래 모든 파일·폴더로 상속되는 형태였다. 계정 B 가 계정 A 의 홈 전체를 읽고 쓰고
지울 수 있었다는 뜻이다.

그 아래에 있는 것: 봇의 `.env`(디스코드 봇 토큰·구독 OAuth 토큰·Supabase 접속 문자열), 봇의 코드, 봇
자기 세션 전사. **쓰기까지 되므로 권한 상승 경로이기도 했다** — 계정 B 에서 봇 소스를 고쳐 두면 다음
재시작에 계정 A 의 권한으로 그 코드가 돈다.

**무엇이 무너져 있었나**: 이 설계의 기둥은 "세션 계정에는 자격증명이 없다"(설계 §3·§7)이고, §5 는
`sh_exec` 에 대해 "남는 경계는 워커 프로세스를 돌리는 OS 계정의 권한뿐"이라고 적어 두었다. **그 마지막
경계가 없었다.** 그리고 `sh_exec` 는 소유자 전용이 아니라 등록된 손님도 쓴다(§5) — 부원을 하네스로 열기
전인 상태에서도 이미 열려 있었다는 뜻이다. 실제로 읽힌 흔적이 있다는 기록은 아니다. 가능했다는 기록이다.

**어떻게 드러났나**: 부원 세션 전사 노출(§10)을 논하다 "계정 B 는 계정 A 를 못 읽는다"는 **전제를 실제로
확인해 보기로** 했다. 소유자 하네스 턴에 A 의 홈 목록을 시켰더니 나왔고, 관리자 창의 `icacls` 가 그 항목을
보여줬다. 같은 기계의 다른 프로필 둘(`asahi-admin`·`s0105`)은 기본 모양 그대로였다 — 기계 전체의 설정이
아니라 그 폴더 하나에 붙은 항목이었다. 붙은 경위는 알 수 없다.

**닫음**: 관리자 창에서 그 항목을 지웠다(`icacls <A 의 홈> /remove:g "<컴퓨터>\<워커 계정>"`). 확인은 세 겹
— ACL 에서 그 줄이 사라졌고, `.env` 에 상속으로도 남지 않았고, 하네스 턴이 실제로 `Permission denied`(종료
코드 2)를 받는다. 워커의 `WORKER_ROOTS` 도 워크스페이스 한 폴더뿐임을 함께 확인했다.

**왜 셋업 검사가 못 잡았나**: `deploy/minipc-단일호스트-셋업.md` 3절에 검사가 **있었다** — B 의 창에서 봇
`.env` 읽기가 거부되는지 보라는 것이다. 설정 때 건너뛴 것인지 그 뒤에 권한이 바뀐 것인지는 알 수 없다.
어느 쪽이든 교훈은 같다: **한 번 보고 끝나는 검사로는 이 경계를 지킬 수 없다.** 그리고 그 검사 자체에도
결함이 있었다 — 성공하면(=격리가 깨져 있으면) 자격증명을 화면에 뿌린다. 확인하는 행위가 곧 유출이 된다.
그래서 계정 B 를 거치지 않고 내용도 건드리지 않는 `icacls` 검사로 바꾸고, 여는 조건으로 올렸다.

**모델의 자기 보고를 경계 검증의 증거로 쓰지 말 것**: 권한을 닫은 뒤 같은 질문을 다시 받자, 하네스 세션은
앞선 두 번의 성공까지 "신뢰할 수 없다"며 철회하고 "실행 환경이 호출마다 달랐을 가능성"을 추측으로 내놨다.
참인 부분까지 같이 버린 것이다 — 바뀐 것은 환경이 아니라 권한이었고, 시각 순서(ACL 확인 → 제거 → 그 뒤
거부)가 그것을 설명한다. 사람이 의심을 표하면 세션은 맞는 관찰도 취소한다. **경계는 계정 B 를 거치지 않는
수단(관리자 창의 `icacls`)으로 검증한다.**

**자격증명 교체는 하지 않았다(운영자 결정 2026-09-07)**: 그 기간에 등록된 사용자가 운영자의 시험 계정뿐이었고
하네스는 소유자 전용이었다 — 닿을 수 있었던 사람이 실제로 없었다. **등록된 부원이 있는 상태에서 같은 것이
발견되면 판단이 달라진다**: 그때는 디스코드 봇 토큰·구독 OAuth 토큰·Supabase 접속 문자열 셋을 교체한다.

## 13. 워커 계정 프로필에 다른 서비스 자격증명이 쌓여 있었다 (2026-09-07) — **닫음(2026-09-07)**

**발견**: `deploy/worker-셋업.md` 의 미니PC 절은 **"그 계정 프로필에 SSH 키·`.env`·저장된 브라우저
자격증명을 두지 않는다"** 를 이 설계의 전제조건으로 적어 두었다. 실제로 보니 둘이 있었다.

- **윈도우 자격증명 저장소**(`cmdkey /list`)에 Docker Hub 토큰 셋(access/refresh/레지스트리)과
  다른 레지스트리 하나. 전부 같은 계정으로 로그인된 상태였다.
- **Edge 프로필**에 `Login Data`·`Web Data`. 타임스탬프가 브라우저 MCP 도입(4단계 4.3)보다 **한 달 이상
  앞서** 있어, MCP 가 만든 것이 아니라 **사람이 그 계정으로 Edge 를 쓴 흔적**이었다(MCP 는 `--isolated`
  로 임시 프로필을 쓴다).

**왜 문제인가**: `sh_exec` 는 소유자 전용이 아니라 등록된 손님도 쓴다(§5). 토큰 **값**을 못 읽어도
상관없다 — 손님이 `docker` 를 부르면 CLI 가 저장된 자격증명을 대신 써 준다. Edge 비밀번호는 DPAPI 로
암호화돼 다른 계정은 못 풀지만, **같은 계정에서 도는 프로세스는 푼다** — 그게 정확히 손님의 셸이다.

**닫음**: 자격증명 넷을 `cmdkey /delete` 로 지우고, Edge 프로필을 관리자 계정 폴더로 **옮겼다**(같은
프로필 안에서 이름만 바꾸면 계정 B 가 그대로 읽는다 — 처음 지시가 그 점에서 불충분했다). 함께 확인한 것:
SSH 키 없음, `gh` 인증 없음, `docker-users` 로컬 그룹 자체가 없음(Docker Desktop 미설치 — 데몬이 없어
자격증명이 있어도 실행은 불가능했다). `WindowsLive:target=virtualapp/didlogical` 하나는 남겼다 — 윈도우가
스스로 만들고 지워도 다시 생기며, 다른 넷과 성격이 다르다.

**§12 와 같은 패턴의 두 번째 실물이다.** 규칙은 문서에 **있었다.** 없던 것은 **그 규칙이 지켜지는지 보는
절차**였다. 그래서 이번에는 규칙 옆에 점검 명령을 함께 적었다(`deploy/worker-셋업.md` 미니PC 절) —
"두지 않는다"는 문장은 아무것도 검사하지 않는다.

**주의 — 점검은 계정 B 를 거치되 값은 묻지 않는다**: 윈도우 자격증명 저장소는 계정별이라 관리자 창에서
보이지 않으므로 `runas` 로 그 계정 창을 띄워 사람이 직접 본다. 세션(모델)에게 시키지 않는다 — 목록이
공개 채널로 나가고, 무엇보다 §12 가 기록한 대로 **모델의 자기 보고는 경계 검증의 증거가 될 수 없다**.
실제로 이번에도 세션은 `cmdkey /list` 를 거부하면서 "이 계정에는 세션 환경으로 붙는 자격증명이 들어
있다"고 했는데, 그것은 확인이 아니라 추론이었고 사실과도 달랐다(git 자격증명은 턴마다 `GIT_CONFIG_*`
환경변수로 주입될 뿐 자격증명 저장소에 저장되지 않는다). 거부라는 결론만 옳았다.
