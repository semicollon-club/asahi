# 스킬 하네스 — 설계

## 1. 무엇을 만드는가

Asahi 가 **외부에서 배포되는 스킬을 설치해 쓸 수 있게** 한다. 첫 목표는 `frontend-design`
같은 문서형 스킬이 실제로 동작하는 것이다.

"우리가 SKILL.md 를 써서 넣는다"는 이 문서의 목표가 아니다. 그건 하네스가 아니라 문서
추가일 뿐이고, 그 방향으로는 공식 스킬도 서드파티 스킬도 영원히 못 쓴다. 만드는 것은
**남이 만든 스킬을 받아들이는 통로**다.

## 2. 지금 상태 (실측)

`@anthropic-ai/claude-agent-sdk@0.3.207` 은 스킬을 이미 지원한다. 만들 필요가 없다.

- `plugins?: SdkPluginConfig[]` — `{ type: 'local', path }` 로 로컬 플러그인 폴더를 읽는다.
  그 폴더의 `skills/<이름>/SKILL.md` 가 스킬로 등록된다.
- `skills?: string[] | 'all'` — 켤 스킬을 고른다. SDK 주석: *"이것이 스킬을 켜는 단일
  지점이며, `allowedTools` 에 `'Skill'` 을 직접 넣을 필요가 없다."*
- 생략하면 SDK 가 아무것도 자동 구성하지 않는다(= 꺼짐이 아니라 CLI 기본값에 맡김).

실제 배포 형식도 확인했다(`~/.claude/plugins/cache/claude-plugins-official/`):

```
frontend-design/unknown/
  .claude-plugin/plugin.json      {name, description, author} 세 항목
  skills/frontend-design/SKILL.md  frontmatter: name, description
```

`plugin.json` 은 세 줄이고 `SKILL.md` 는 frontmatter 두 필드다. **형식 변환이 필요 없다.**

### 2.1 스킬은 두 종류다

| 유형 | 예시 | Asahi 에 필요한 것 |
|---|---|---|
| 문서만 | `frontend-design`(SKILL.md + LICENSE 가 전부) | 로딩 배선만 |
| 스크립트 포함 | superpowers 의 여러 스킬(`.sh` 동봉) | 스크립트가 **실행되는 기계에** 있어야 함 |

이 문서는 **문서형만** 다룬다. 스크립트형은 §7 로드맵의 2단계다.

### 2.2 제약: 실행은 다른 기계에서 일어난다

`query()` 는 **봇**(Railway)에서 돌므로 SKILL.md 도 봇 파일시스템에서 읽는다. 그러나
`sh_exec`/`fs_*` 는 **미니PC 워커**에서 실행된다. 스킬이 "`scripts/x.py` 를 돌려라"라고 하면
그 파일이 실행되는 쪽에 없다.

봇은 SDK 내장 도구(Read/Write/Bash)를 **의도적으로 전부 닫아 두었다**
(`agent/src/core/agent.ts` — *"열면 봇 컨테이너의 파일시스템을 건드리게 된다"*). 이 결정은
되돌리지 않는다. 즉 봇에서 스크립트를 실행하는 선택지는 없다.

**스킬을 리포에 두면 이 문제가 대부분 사라진다.** 봇은 배포 때 받고, 미니PC 는
`deploy/update-worker.ps1` 이 5분마다 당겨온다(2026-08-01 가동). 같은 파일이 양쪽에 있고
루트 경로만 다르다. 2단계는 경로 규약만 정하면 된다 — 파일을 나르는 일은 이미 돌아간다.

## 3. 설계

### 3.1 구조

리포 루트에 `skills/` 를 만들고 **플러그인 하나**로 취급한다.

```
skills/
  .claude-plugin/plugin.json
  frontend-design/SKILL.md
```

외부 스킬 설치 = 그 폴더를 `skills/` 밑에 **그대로 복사**하고 커밋한다. 벗겨내기도 변환도
없다. 이것이 §5 에서 A 안을 고른 이유 그대로다.

`.claude-plugin/plugin.json`:

```json
{
  "name": "asahi-skills",
  "description": "Asahi 가 사용하는 스킬 모음",
  "author": { "name": "semicolon" }
}
```

### 3.2 로딩

`query()` 옵션에 두 줄을 더한다.

```ts
plugins: [{ type: "local", path: skillsDir }],
skills: skillsEnabled ? "all" : [],
```

`skillsDir` 은 봇 프로세스 기준 리포의 `skills/` 절대경로다. `agentCwd` 와 달리 소스 트리
안이지만, 이것은 에이전트의 **작업 폴더가 아니라 읽기 전용 자원 경로**다 — cwd 정책
(에이전트가 소스 트리를 훑지 않게 한다)은 그대로 유지된다.

### 3.3 켜고 끄는 축

`resolveWebToolsEnabled`(`agent/src/core/agent.ts:217`)와 **같은 모양**의 순수 함수를 둔다.

```ts
export function resolveSkillsEnabled(req: { noSkills?: boolean }): boolean {
  return !req.noSkills;
}
```

유휴 요약 턴(`core.ts` 의 `summarizeAndClose`, `noWebTools: true` 를 넘기는 그 자리)에서는
스킬도 함께 닫는다. 그 턴은 사람이 지켜보지 않는 타이머로 돌고 이전 세션에 심겼을 수도 있는
프롬프트 인젝션을 그대로 이어받는데, 요약에 스킬이 필요할 이유가 없다 — 웹 검색을 닫은 것과
정확히 같은 근거다.

그 외에는 **전원에게 열린다.** 신원(소유자/손님)으로 가르지 않으므로 `allowedToolsFor` 는
건드리지 않는다. 스킬을 쓸 수 있는 사람이 아니라 **스킬을 리포에 넣을 수 있는 사람**이
경계다 — 그것이 §3.1 에서 리포 커밋을 고른 이유다.

### 3.4 아사히가 스킬의 존재를 알아야 한다

`persona.ts` 의 능력 안내에 한 줄 더한다. 스킬이 있는데 있는 줄 모르면 쓰지 않는다.
문구는 "쓸 수 있는 스킬이 있으면 먼저 살펴보라"는 정도로 두고, 스킬 이름을 나열하지 않는다 —
나열하면 스킬을 추가할 때마다 프롬프트를 고쳐야 하고, 목록은 SDK 가 이미 모델에게 준다.

### 3.5 오류 처리

스킬 폴더가 없거나 `plugin.json` 이 깨져도 **턴은 그대로 돌아야 한다.** 스킬은 부가 능력이지
동작 조건이 아니다 — 워커 커밋 읽기(`readCommit` 이 실패하면 `undefined` 를 돌려주고 워커는
그대로 뜬다)와 같은 원칙이다. 로딩 실패가 대화를 막으면 부가 기능이 본 기능을 인질로 잡는다.

## 4. 미확정 — 계획의 첫 태스크가 실험으로 확정한다

**Asahi 는 SDK 내장 도구를 전부 닫아 둔다**(`tools: []`, 또는 웹 검색만). 그것이 `Skill`
도구까지 닫는지 타입 선언만으로는 확정할 수 없다. SDK 주석은 `skills` 옵션이 `allowedTools`
쪽을 알아서 처리한다고 하지만, `tools`(내장 도구 목록)와의 상호작용은 그 문장의 범위 밖이다.

**이것을 추측으로 넘기고 계획을 쌓으면 안 된다.** 구현 계획의 첫 태스크는 코드를 쓰는 것이
아니라 **실제로 켜서 스킬이 호출되는지 확인**하는 것이다. 결과에 따라 갈린다.

- 호출되면 → §3 그대로 진행
- 안 되면 → `tools` 에 `"Skill"` 을 더하는 것으로 되는지 확인하고, 그것도 아니면 그 지점에서
  방법을 다시 정한다(이 문서를 고친다)

같은 실험에서 **`skills: []` 가 실제로 끄는지도 함께 확인한다.** SDK 주석은 생략(자동 구성
안 함) / `'all'` / 이름 배열 셋만 설명하고 빈 배열을 따로 말하지 않는다. "빈 목록이니 아무것도
안 켜진다"는 읽기가 자연스럽지만, 생략과 같게 취급돼 CLI 기본값으로 떨어질 여지가 있다.
§3.3 의 유휴 요약 턴 차단이 이 한 줄에 걸려 있으므로 추측으로 두지 않는다 — 끄지 못하는 것으로
드러나면 그 턴에서는 `plugins` 자체를 넘기지 않는 방식으로 바꾼다.

이 프로젝트는 문서·추측을 실측보다 앞세워 이미 여러 번 시간을 태웠다. 같은 실수를 계획
구조로 막는다.

## 5. 고르지 않은 선택지

| | 방식 | 왜 아닌가 |
|---|---|---|
| B | `cwd` 를 리포로 바꾸고 `settingSources:['project']` 로 `.claude/skills/` 자동 탐색 | cwd 를 소스 트리 밖에 둔 것은 "에이전트가 소스를 훑지 않게" 한 의도적 결정이다(`index.ts:121`). 스킬 하나를 위해 되돌릴 수 없다 |
| C | 부팅 때 스킬을 `agent-cwd/.claude/skills/` 로 복사 | 복사 로직이 늘고, 외부 스킬이 플러그인 형태로 배포되는데 그 형식을 벗겨내야 한다. A 보다 나은 점이 없다 |

## 6. 테스트 전략

로딩 자체는 SDK 내부라 유닛 테스트가 닿지 않는다. **닿는 것과 안 닿는 것을 미리 갈라 둔다.**

**유닛으로 고정할 것**

- `resolveSkillsEnabled` — 유휴 요약 턴에서 꺼지고 그 외엔 켜진다. `resolveWebToolsEnabled`
  테스트와 같은 모양
- `skillsDir` 을 만드는 경로 계산 — 봇이 어디서 실행되든 리포의 `skills/` 를 가리킨다

**유닛이 못 잡는 것 → 스모크로 옮긴다**

- 스킬이 실제로 모델에게 보이는가
- `frontend-design` 이 실사용에서 호출되는가
- 스킬 폴더가 없을 때 턴이 정상인가(§3.5)

§4 의 실험이 곧 첫 스모크 항목이다. `deploy/smoke-test.md` 에 항목을 더한다.

## 7. 로드맵 — 이 문서 다음

| 단계 | 내용 | 왜 이 순서인가 |
|---|---|---|
| **1(이 문서)** | 스킬 로딩 하네스 | 나머지 전부의 토대. 이것만으로 문서형 스킬이 실제로 된다 |
| 2 | 스크립트 브리지 — 봇의 SKILL.md ↔ 미니PC 실행. 경로 규약, 미니PC 런타임(python 등) | 1 이 끝나야 "어떤 스킬이 스크립트를 필요로 하는지"를 실물로 안다. 추측으로 설계하면 안 쓰는 것을 만든다 |
| 3 | 외부 스킬 신뢰 정책 — 어떤 출처를 받을지 | 스킬은 **아사히가 따르는 지시문 + 동아리 미니PC 에서 도는 스크립트**라 공급망 표면이다. 다만 스킬 수가 늘어야 정책이 의미를 갖는다. 그전까지는 "소유자가 리포에 직접 넣는다 = 리뷰"가 정책이다 |
| 4 | MCP·커넥터 | 별개 주제. 계정이 실제로 연결되므로 각각을 보안 관리하기 어렵다는 판단에 따라, 동아리 계정 하나로 묶는 방향이 이미 정해져 있다 |

## 8. 이 문서가 다루지 않는 것

- 스크립트를 동반한 스킬의 실행(2단계)
- 서드파티 스킬의 신뢰·검증 정책(3단계)
- MCP 서버, 커넥터(4단계)
- 스킬을 런타임에 추가하는 경로 — 리포 커밋으로 고정했다. 즉시 반영이 필요해지면 그때 다시 본다
- 스킬별 대상 지정(소유자 전용 스킬 등) — 전원 공개로 고정했다. 소유자 전용 절차는 당분간
  스킬로 만들지 않는 것으로 피한다
