# 파일 전달 — 디스코드 ↔ 워커

## 1. 무엇을 만드는가

부원이 디스코드에 올린 파일이 미니PC 워커에 저장되고, 워커의 파일을 디스코드로 돌려받는
통로를 만든다.

지금은 **이미지가 아닌 첨부가 조용히 무시된다**(`agent/src/core/images.ts:21` —
`if (!mt.startsWith("image/")) continue;`). 부원이 PDF 를 올려도 봇은 그런 것이 있었다는
사실조차 모른다. 반대 방향도 없다 — 워커가 만든 파일을 사람이 가져갈 방법이 개발서버로
띄워서 브라우저로 보는 것뿐이다.

## 2. 왜 지금인가

로드맵의 다음 목표는 공식 문서 스킬(`pdf`/`docx`/`xlsx`)이었다. 그 스킬들을 쓰려면 세 조각이
필요한데 조사 결과 하나가 아니라 셋이었다.

| | 조각 | 상태 |
|---|---|---|
| ① | 경로 브리지 — 모델이 받는 것은 봇 경로, 실행은 워커에서 | 작다. 이 문서의 범위 밖 |
| ② | 런타임 — 미니PC 에 파이썬과 라이브러리 | 설치 작업. 코드 거의 없음 |
| ③ | **파일 전달** | **아예 없다. 이 문서** |

①②를 다 해도 pdf 스킬이 열어볼 파일이 없다. 그리고 ③은 스킬과 무관하게 단독으로 쓸모
있다 — 부원이 아사히에게 파일을 건네는 통로 자체가 지금 없다. 그래서 ③을 먼저 한다.

(참고: `pdf`/`docx`/`xlsx` 스킬을 어디서 받아오는지는 아직 확인되지 않았다. 이 리포의 플러그인
캐시에도 SDK 번들에도 없다. ①②를 시작하기 전에 그것부터 확인해야 한다.)

## 3. 실측으로 확정한 제약

### 3.1 SDK 는 모델에게 스킬의 절대경로를 준다

프로브로 확인했다 — 모델이 스스로 스킬 디렉터리의 절대경로를 답했고, 그것으로 실행 명령까지
만들었다. 프로덕션에서는 그 경로가 **봇 컨테이너 경로**(`/app/skill-plugin/...`)이므로 워커에서
쓰면 파일을 못 찾는다. 이것이 ①의 정체다. **조용히 실패하지는 않는다** — "파일 없음"으로
시끄럽게 죽으므로 진단이 쉽다. 이 문서는 ①을 다루지 않지만, 조사에서 나온 사실이라 남긴다.

### 3.2 허브 프레임 상한이 내려받기 방향을 지배한다

`agent/src/remote/hub.ts:54` 의 `MAX_FRAME_CHARS = 1_000_000`, 그리고 초과 시
`terminate()`(`:170`) — 연결을 끊는다. `WorkerResult.content` 는 문자열이므로 파일을 base64 로
실으면 약 700KB 가 상한이고, 넘으면 실패가 아니라 **워커가 튕긴다.**

올리기 방향은 이 제약과 무관하다(§4.1). 내려받기만 걸린다(§4.2).

## 4. 설계

### 4.1 올리기 — 봇은 파일을 옮기지 않는다

부원이 첨부하면 봇이 **디스코드 CDN URL 과 저장 위치**를 워커에 넘기고, **워커가 그 URL 에서
직접 받는다.** 바이트가 허브를 통과하지 않으므로 프레임 상한과 무관하고 봇 메모리도 쓰지
않는다.

**모델은 이 경로에 관여하지 않는다.** URL 은 봇이 실제 첨부 객체(`message.attachments`)에서
꺼낸다 — 모델이 주소를 정하게 하면 워커가 임의 주소를 받아오는 표면이 열리는데, 그 표면이
아예 없다. 워커 쪽에서 호스트가 디스코드 CDN 인지 한 번 더 검증한다(봇이 이미 통제하지만,
워커의 최종 판정은 봇을 신뢰하지 않는다는 이 리포의 이중 게이트 원칙 그대로다).

이것은 **모델 도구가 아니다.** 워커 실행기에는 있지만 `REMOTE_TOOL_NAMES` 에는 넣지 않으므로
모델에게 노출되는 MCP 도구가 되지 않는다 — 모델이 부를 방법 자체가 없다.

저장 위치는 그 사람의 작업 폴더다(`scopeDirs` 와 같은 규칙: 손님은 `<루트>/<디스코드 id>/`,
소유자는 좁혀지지 않는다).

**모델에게는 결과만 알린다.** 기존 이미지 마커(`buildImageMarker`, `[이미지 2장: a.png, b.png]`)
와 같은 방식으로 프롬프트 앞에 붙인다 — 파일명과 **저장된 절대경로**를 담는다. 경로를 담는
것이 중요하다: 그것이 없으면 모델이 `fs_read` 로 열 방법을 모른다.

**어디서 도는가.** 어댑터(`discord.ts`)는 지금 이미지에 대해 하는 것과 같은 일만 한다 — 첨부
목록을 분류해 `Incoming` 에 실어 보낸다. 실제 받아오기는 **`core.ts` 의 턴 처리**에서 한다:
그 자리가 `resolveTurnWorker` 로 "이 턴이 어느 기계를 쓰는가"를 이미 정하는 곳이고, 받아오기는
그 워커에 대고 해야 하기 때문이다. 어댑터에는 허브가 없다.

어댑터가 거르는 것은 **무시 판정 뒤**여야 한다(표시 이름 갱신과 같은 자리) — `decideRoute` 가
걸러낸 메시지의 첨부까지 받아오면 아무나 미니PC 에 파일을 놓을 수 있다.

### 4.2 내려받기 — 모델 도구, 프레임 상한을 올린다

어느 파일을 보낼지는 모델이 정해야 하므로 이쪽은 모델 도구다(`file_send(path)`). 경로는
`fs_read` 와 **똑같은 게이트**를 탄다(봇 쪽 1차 필터 + `scopeDirs` + 워커 쪽 최종 판정).
새 경로 권한을 만들지 않는다.

파일은 **워커 → 봇 → 디스코드** 로 실제로 이동해야 한다. 그래서 §3.2 의 상한이 걸린다.
세 선택지를 놓고 골랐다.

| | 방법 | 판정 |
|---|---|---|
| A | 700KB 상한을 두고 넘으면 거절 | **탈락.** 가장 단순하지만 PDF 결과물은 대개 넘는다 — 이 문서의 목적에 못 미친다 |
| B | 프레임을 나눠 보내고 봇에서 합침 | 크기 문제는 사라지지만 프로토콜에 청크 개념이 생기고 조립·유실·순서를 다뤄야 한다. 같은 목적에 복잡도를 훨씬 많이 쓴다 |
| **C** | **인증된 워커의 결과 프레임에 한해 상한을 올린다** | **채택** |

C 를 고른 이유: `MAX_FRAME_CHARS` 의 존재 이유가 코드 주석에 명시돼 있다 — *"인증조차 안 된
클라이언트가 보낸 거대한 프레임"* 을 막는 것이다. 우리가 필요한 것은 **인증을 마친** 워커의
결과 프레임뿐이므로 그 취지와 어긋나지 않는다.

- 인증 **전** 상한은 지금 값(1,000,000자)을 그대로 둔다. 이 방어를 약화하지 않는 것이 C 의 전제다
- 인증 **후** 상한은 **12,000,000자**로 둔다. 파일 상한을 **8MB** 로 잡고 거기서 역산한 값이다
  (base64 는 원본의 약 4/3 이라 8MB → 약 10.7MB 문자, 여유를 더해 12MB)
- 8MB 인 이유: 디스코드의 첨부 한도는 서버 부스트 등급에 따라 다르고 시기에 따라 바뀌어 왔다.
  8MB 는 **모든 등급에서 확실히 통과하는 값**이고, 이 문서가 목표하는 용도(채워진 PDF, 생성된
  문서)에는 넉넉하다. 확실하지 않은 상한에 맞춰 크게 잡았다가 전송 단계에서 거절당하는 것보다,
  확실한 값으로 시작해 필요해지면 올리는 편이 낫다
- 봇 메모리: 12MB 문자열 + 디코드된 8MB 버퍼가 한 전송 동안 동시에 존재한다. 동시 전송이
  많지 않은 규모라 문제되지 않지만, 이 값을 올릴 때는 그 곱을 함께 봐야 한다
- 상한을 넘는 파일은 **거절한다.** 거절 문구가 실제 크기와 상한을 함께 말해야 한다 — "안 된다"만
  말하면 사람이 원인을 못 찾는다
- `ws` 의 `maxPayload` 도 함께 맞춘다(`index.ts` 가 허브 상수와 맞추고 있다는 주석이
  `hub.ts:50` 에 있다). 한쪽만 올리면 다른 쪽에서 조용히 끊긴다

봇은 받은 base64 를 디코드해 디스코드에 첨부로 보낸다. 지금 어댑터에는 **첨부를 보내는 경로가
없다**(이미지는 `EmbedBuilder.setImage` 로 URL 만 싣는다) — `AttachmentBuilder` 경로를 새로
만든다.

### 4.3 보안 — 새로 생기는 것과 아닌 것

**새 능력이 아니다.** 부원이 미니PC 에 임의 바이트를 놓게 되지만, `sh_exec` 는 이미 경로
게이트의 대상이 아니라 지금도 셸로 파일을 만들 수 있다(`docs/security/capability-model.md`
"경로 게이팅"). 실행 파일도 마찬가지다. 진짜 경계는 그대로 **미니PC 의 비관리자 계정**이다.

**그래도 달라지는 것은 난이도다.** 셸 명령으로 바이너리를 만드는 것과 파일을 끌어다 놓는 것은
같은 능력이지만 후자가 훨씬 쉽다. 이 문서는 그 사실을 인정하고, 대신 다음을 지킨다.

- 무시 판정을 통과한 메시지의 첨부만 받는다(§4.1)
- 저장 위치는 그 사람의 폴더로 강제된다 — 모델이 정하지 않는다
- 크기 상한과 개수 상한을 둔다(이미지의 `IMAGE_LIMITS` 와 같은 형태)
- 받아오는 주소는 디스코드 CDN 으로 제한한다(봇·워커 양쪽에서)

**확장자 차단은 하지 않는다.** `.exe` 를 막아도 `.txt` 로 올려 셸로 이름을 바꾸면 그만이라
막는 시늉만 된다. 시늉하는 방어를 넣으면 다음 사람이 그것을 진짜 경계로 착각한다 — 이 리포가
폴더 격리에 대해 이미 명시적으로 피해 온 실수다.

### 4.4 오류 처리

- 받아오기 실패(URL 만료·네트워크·디스크)는 **대화를 막지 않는다.** 모델에게 실패 사실을
  마커로 알리고 턴은 그대로 진행한다 — 이미지 다운로드 실패(`downloadImages` 의 `failed`)와
  같은 원칙이다
- 워커가 연결돼 있지 않으면 첨부를 조용히 버리지 않고 **그렇게 말한다.** 지금 동작(조용한
  무시)이 바로 이 문서가 고치려는 것이라, 같은 침묵을 다른 자리에 다시 만들지 않는다
- 내려받기에서 파일이 상한을 넘으면 크기와 상한을 함께 말한다(§4.2)

## 5. 테스트 전략

**유닛으로 고정할 것** — 전부 순수 함수로 뽑는다.

- 첨부 분류: 이미지/일반 파일/거절(크기·개수 초과) 갈래
- 저장 경로 계산: 손님은 자기 폴더로, 소유자는 좁혀지지 않음. 파일명에 든 경로 구분자·`..` 가
  폴더를 벗어나지 못하는 것
- CDN 호스트 검증: 디스코드 호스트는 통과, 그 밖은 거절. **비슷하게 생긴 호스트**(예:
  `cdn.discordapp.com.evil.test`)가 거절되는 것을 직접 단정한다
- 크기 판정: 인증 전 상한은 그대로, 인증 후 상한만 올라간 것
- 마커 문구: 파일명과 절대경로가 들어가는 것

**유닛이 못 잡는 것 → 스모크**

- 실제 첨부 → 미니PC 저장 왕복
- 실제 `file_send` → 디스코드 첨부 도착
- 상한 근처 크기의 파일이 실제로 오가는 것(프레임 상한과 `ws.maxPayload` 가 양쪽 다 맞는지는
  실물로만 확정된다)

## 6. 이 문서가 다루지 않는 것

- 경로 브리지(①) — 별도 스펙
- 미니PC 파이썬 런타임(②) — 설치 절차이고 코드가 거의 없다
- `pdf`/`docx`/`xlsx` 스킬을 어디서 받는지 — ①②보다 먼저 확인해야 할 미해결 항목(§2)
- 파일 보관 정책(오래된 업로드 정리) — 지금 워크스페이스에도 그런 정책이 없다. 같이 다룰 일이
  생기면 그때 함께 본다
- 확장자·내용 기반 차단(§4.3 에 안 하는 이유를 적었다)
