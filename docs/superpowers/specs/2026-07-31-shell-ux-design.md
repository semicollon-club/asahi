# 셸·프로세스 사용성 — 실패로 보이는 것 없애기

## 1. 배경 · 목표

부원 오픈을 앞두고 `actions` 테이블의 실사용 기록을 훑었더니, 문서의 계획과 다른 그림이
나왔다. 도구 호출 50건의 분포는 이렇다.

| 도구군 | 호출 | 실패로 기록됨 |
|---|---|---|
| `proc_*` (프로세스) | 28 | 5 |
| `sh_exec` (셸) | 16 | **8 (50%)** |
| `fs_*` (파일) | 6 | 1 |

**부원이 실제로 하는 일은 "개발서버 띄우고 상태 보기"다.** 파일 도구는 거의 쓰이지 않는다.
그런데 셸 호출의 절반이 실패로 기록되고, **그중 7건은 진짜 실패가 아니다.**

- **5건** — `netstat -ano | findstr :5173` 이 `(종료 코드 1)` 로 끝났다. `findstr`·`grep` 의
  exit 1 은 "매칭 없음"이라는 **정상적인 답**이다. 셸에서 non-zero 는 실패 신호가 아니라
  통신 수단이다(`diff` 의 1 은 "차이 있음", `test` 의 1 은 "거짓").
- **2건** — `cd "..." && npm run dev` 가 15초 타임아웃으로 죽었다. 계속 도는 명령이므로
  `proc_start` 를 썼어야 했다. 15초를 태우고 실패한다.
- **1건** — 윈도우 내장 명령의 한국어 메시지가 cp949 로 깨져 왔다(이번 범위 밖, §6).

원인은 코드에 정확히 짚인다.

**첫째, 종료 코드를 무조건 도구 실패로 취급한다.** `agent/src/remote/executors.ts` 의
`sh_exec` 는 `code === 0` 이 아니면 전부 `ok: false` 를 돌려준다. 그 `ok` 는
`agent/src/core/tools.ts` 의 `remoteResult` 에서 그대로 `isError` 가 되므로, 모델은 `<error>`
태그로 감싼 응답을 받는다. 출력이 비어 있으면 모델이 받는 것은 `\n(종료 코드 1)` 이 전부다.
같은 값이 `actions.status` 로도 기록되어 실패율 지표까지 부풀린다.

**둘째, `sh_exec` 의 도구 설명에 `proc_start` 이야기가 없다.** 전문이 "워커 PC 에서 셸 명령을
실행합니다. 강력한 도구이니 신중히 쓰세요." 다. 모델이 `npm run dev` 를 `sh_exec` 로 시도할
이유가 충분하다.

**셋째, `proc_list` 가 사람 이름을 모른다.** 목록이 `asahi-<디스코드 userId>` 로 나온다.
워커는 디스코드를 모르므로 이름을 해석할 수 없고, 신원 해석은 봇만 할 수 있다.

목표는 **부원을 더 들이기 전에, 셸·프로세스 경로에서 "실패로 보이는 것"을 없애는 것**이다.

## 2. 범위

**안**

1. `sh_exec` 의 도구 실패와 명령 종료 코드 분리 (§3)
2. 계속 도는 명령을 `proc_start` 로 유도 (§4)
3. `proc_list` 의 사람 이름 표시 (§5)

**밖** — 각각 별도 과제다.

- **`sh_exec` 출력의 cp949 디코딩.** 근본 해결에 `iconv-lite` 급 의존성이 필요하고, 정확한
  코드페이지는 기계마다 다르다. 현재는 한계로 문서화되어 있다(`docs/agent-onboarding.md` 2절).
- 웹 대시보드(상시 표시), 능동성(2E), 백업(2D) — 로드맵의 별개 항목이다.

## 3. 조각 1 — 도구 실패와 명령 종료 코드를 분리

### 결정

`sh_exec` 의 계약은 "셸 명령을 실행하고 결과를 돌려준다"이다. 명령이 exit 1 을 냈어도 **도구는
제 일을 했다.** `ok: false` 는 도구가 실제로 그 일을 못 한 경우로 좁힌다.

| 상황 | `ok` | 본문 |
|---|---|---|
| 명령이 끝남 (exit 0) | `true` | 출력 그대로. 비었으면 "출력 없음"을 명시 |
| 명령이 끝남 (exit ≠ 0) | **`true`** | 출력 + 종료 코드 명시. 비었으면 "출력 없음"도 함께 |
| spawn 실패 | `false` | 지금과 같음 |
| 타임아웃 | `false` | 지금과 같음 (§4 에서 문구만 보강) |

**해석은 넣지 않는다.** "`findstr` 이라면 매칭 없음을 뜻합니다" 같은 안내는 이 설계에 포함하지
않는다 — 셸 명령은 무한하고, 파이프라인이면 마지막 명령의 코드라 어떤 목록도 정확할 수 없다.
전달할 것은 사실(종료 코드가 N 이다, 출력이 없다)이고 판단은 모델의 몫이다.

### 왜 이 방향인가

대안 둘을 검토했다.

- **문구만 개선(`ok:false` 유지)** — 변경은 가장 작지만 모델은 여전히 `<error>` 를 받는다.
  실패율 지표도 그대로다. 증상만 가린다.
- **명령별 화이트리스트** — `findstr`/`grep`/`diff` 를 알아보고 해석한다. 유지보수할 목록이
  끝없이 자라고 파이프라인에서 무너진다. YAGNI 위반이다.

### 파급 — `actions.status` 의 의미가 바뀐다

앞으로 `status='error'` 는 **"도구가 못 했다"만** 가리킨다. 명령의 non-zero 종료는 `status='ok'`
로 기록되고 종료 코드는 `result_summary` 에 남는다.

이는 관측성의 개선이다 — 지금은 "워커가 죽었다"와 "매칭이 없다"가 같은 `error` 로 보인다.
다만 **이 변경 이전의 행과 이후의 행은 의미가 다르므로 섞어서 집계하면 안 된다.**
`docs/agent-onboarding.md` 8절(진단)과 `docs/status/STATUS.md` 에 이 경계를 남긴다.

### 건드리지 않는 것

`proc_*` 와 `fs_*` 의 `ok` 판정은 그대로 둔다. 그것들의 `ok` 는 도구 자신의 성패이지 남의
프로세스가 낸 종료 코드가 아니다. `proc_start` 가 "띄우긴 했는데 상태가 정상이 아니에요
(stopped)" 로 `ok:false` 를 내는 것은 계속 옳다 — 그건 그 도구가 하려던 일(띄우기)이 실패한
것이다.

## 4. 조각 2 — 계속 도는 명령을 `proc_start` 로 유도

두 곳 모두 문구 변경이다.

1. **`sh_exec` 도구 설명**(`agent/src/core/tools.ts`) — 명령이 끝날 때까지 기다린다는 사실과,
   계속 도는 명령은 `proc_start` 라는 것을 한 줄로 덧붙인다.
2. **타임아웃 문구**(`agent/src/remote/executors.ts`) — 지금은 "…안에 끝나지 않아 중단했어요"
   로 끝난다. 계속 도는 프로그램이라면 `proc_start` 를 써야 한다는 안내를 잇는다.

**주의: 문구를 넓게 쓰지 않는다.** `docs/agent-onboarding.md` 7절이 기록한 실패 모드의 반대
방향이 여기서 위험하다 — 설명이 겁을 주면 모델이 **정당한 `sh_exec` 까지 피한다.** 한정어는
"계속 도는(장기 실행) 명령"으로 좁히고, 일회성 명령을 위축시키는 표현은 쓰지 않는다.

## 5. 조각 3 — `proc_list` 의 사람 이름

세 단계이고, 각 단계는 이미 있는 이음매·관례를 그대로 쓴다.

### 5.1 어댑터가 이름을 잡는다

**전제 확인**: `users.display_name` 컬럼은 이미 있고 `UsersRepo.upsert` 도 `displayName` 을
받는다. 그런데 **현재 네 명 전부 `null` 이다** — 그 값을 넘기는 코드가 어디에도 없다.

`DiscordAdapter` 는 이미 `UsersRepo` 를 들고 있고 메시지마다 `this.users.getRole(...)` 을
부른다(`agent/src/adapters/discord.ts`). 같은 자리에서 표시 이름을 함께 upsert 한다.
이벤트버스(`UserMessageEvent`)는 건드리지 않는다.

**어느 이름인가**: 디스코드 계정의 **전역 표시 이름**을 쓴다(없으면 `username` 으로 폴백).
서버 별명(길드 닉네임)은 쓰지 않는다 — 별명은 서버마다 다르고 DM 에는 아예 없으므로, 같은
사람이 DM 에서 말했느냐 서버에서 말했느냐에 따라 `proc_list` 의 이름이 달라진다. 프로세스
목록은 길드에 속한 화면이 아니므로 한 사람에게 하나의 이름이 대응하는 편이 옳다.

`upsert` 는 `COALESCE` 로 기존 값을 보존하므로, 이름을 못 얻은 경우에도 이미 저장된 값을
지우지 않는다.

### 5.2 봇이 이름을 실어 보낸다

`agent/src/core/remoteTools.ts` 가 `proc_list` 호출에 `onlyUserId` 를 주입하는 바로 그 자리에서
`labels` 맵(`userId → 표시 이름`)도 주입한다. 이 값은 **모델이 정하지 않는다** — 기존 `name`·
`cwd`·`onlyUserId` 와 같은 이유로 도구 스키마에 열지 않는다.

범위는 기존 스코프를 그대로 따른다.

- **손님** — 자기 것만 본다(`onlyUserId` 가 이미 그렇게 좁힌다). 따라서 자기 이름만 실어 보낸다.
- **소유자** — 전원을 보므로 전원의 이름을 실어 보낸다.

프라이버시 경계가 새로 생기지 않는다. 손님에게 남의 이름이 가지 않는 것은 `onlyUserId` 가
이미 보장하던 것과 같은 경계다.

### 5.3 워커가 쓴다

`proc_list` 실행기가 `renderProcList(..., { labelOf })` 를 부를 때, `labelOf` 가 주입된 맵을
먼저 보고 **없으면 지금처럼 `procNameFor(id)` 로 폴백**한다. 이 이음매는 이미 그 목적으로
비워져 있다.

폴백은 지워지지 않는다 — 이름을 아직 못 얻은 사용자, 옛 봇과 새 워커가 섞여 도는 배포 중간
상태에서도 목록이 깨지지 않아야 한다.

## 6. 테스트 전략

진행 원장에 **"한 토큰 변이로 전 스위트가 녹색"** 사례가 반복해서 기록돼 있다(워커 쪽
`onlyUserId` 필터에 테스트가 없어 필터를 지워도 868개가 전부 통과한 일 등). 이 설계의 세
조각은 전부 그 함정에 취약하다 — 불리언 하나와 문자열 몇 개가 전부이기 때문이다.

- **조각 1** — exit 0 / exit ≠ 0 / spawn 실패 / 타임아웃 네 갈래를 각각 단정한다. 핵심은
  **"non-zero 가 `ok: true` 로 온다"를 직접 단정하는 테스트**다. 출력이 빈 경우와 있는 경우를
  나눠 본문 문구도 고정한다.
- **조각 2** — 문구의 존재만 단정하면 약하다. `docs/agent-onboarding.md` 7절·진행 원장의
  전례대로 **역전 시험**을 손으로 수행한다: 문구를 반대 뜻으로 바꿔도 스위트가 녹색이면 그
  테스트는 아무것도 지키지 않는 것이다.
- **조각 3** — `labels` 가 없을 때 폴백이 살아 있는지, 손님과 소유자의 주입 범위가 다른지,
  어댑터가 실제로 upsert 를 부르는지. 마지막 항목은 이음매가 아니라 호출 자체가 빠지기 쉬운
  자리다.

세 조각 모두 실 하드웨어 검증이 따로 필요하지는 않다 — `runPm2`·`spawn` 너머가 아니라 그
앞단의 판정·문구·주입만 바꾸기 때문이다. 다만 조각 2 의 실제 효과(모델이 도구를 바꿔 고르는가)
는 코드로 검증할 수 없으므로 배포 후 `actions` 에서 `sh_exec` 타임아웃 건수로 확인한다.
