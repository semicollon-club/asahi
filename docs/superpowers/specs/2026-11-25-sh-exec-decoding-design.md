# 셸 출력 한글 깨짐 해결(N4) — 설계

[사용성 로드맵 설계](./2026-09-22-usability-roadmap-design.md) §3.3 의 N4. 얇은 워커의 `sh_exec` 가 윈도우 내장 명령의
한국어 출력을 깨뜨린 채 모델에게 넘긴다 — 30일 실측에서 부원 셸 호출의 **16%**(하네스 `Bash` 는 1%, 같은 설계 §2.5).
실패의 원인은 멀쩡한데 설명만 깨져 오진을 부른다([온보딩](../../agent-onboarding.md) 2절).

## 1. 원인

워커는 자식의 stdout·stderr 를 청크가 올 때마다 `chunk.toString()`(UTF-8)으로 이어 붙였다. 깨지는 길이 둘이다.

1. **cp949 출력** — 윈도우 내장 명령·PowerShell 5.1·Python 은 파이프로 낼 때 콘솔 코드페이지(미니PC 는 949)를 쓴다.
2. **청크 경계** — UTF-8 로 내는 프로그램이라도 한 글자(한글은 3바이트)가 두 청크에 걸치면 양쪽이 깨진다.

## 2. 실측 (2026-11-25)

개발 PC(콘솔 코드페이지 949)에서 `sh_exec` 와 같은 방식(`spawn(command, {shell:true})`)으로 띄워 줄마다 바이트를 봤다.

| 명령 | 출력 인코딩 |
|---|---|
| `type 없는파일.txt`(오류 문구) | cp949 |
| `echo 한글 출력` | cp949 |
| `dir`·`dir /b`(UHC 확장 글자 `똠` 이 든 파일 이름 포함) | cp949 |
| `ping -n 1 127.0.0.1` | cp949 |
| `powershell -Command "Write-Output '…'"` | cp949 |
| `python -c "print('…')"` | cp949 |
| `node -e "console.log('…')"` | UTF-8 |
| `type 한글파일.txt`(UTF-8 파일) | UTF-8 — 파일 바이트 그대로 |
| `echo 앞줄 & node -e "…"` | **줄마다 다르다** — 앞줄 cp949, 뒷줄 UTF-8 |
| `chcp 65001 >nul & echo 한글` | **여전히 cp949** |

여기서 셋이 정해진다.

- 한 명령의 출력도 줄마다 인코딩이 다를 수 있다. 출력 전체를 한 인코딩으로 볼 수 없으니 **줄 단위로 판정**한다.
- 로드맵 결정 2 가 실측을 맡긴 "라이브러리를 들이지 않는 길"(명령을 UTF-8 출력으로 강제)은 같은 명령줄의 `echo` 에도 듣지
  않는다. 닫는다.
- Node 내장 `TextDecoder('euc-kr')` 는 KS X 1001 만 읽는다. `똠`(0x8C63) 같은 UHC 확장 8,822자는 깨진다 — 파일 이름이면 흔히
  나온다. cp949 전체를 읽는 것은 `iconv-lite` 다. 운영자가 2026-09-22 에 허용했고(로드맵 결정 2), 이미 의존성 트리에 0.7.3 으로
  있어(`@modelcontextprotocol/sdk` → `express` → `body-parser`·`raw-body` 경유) **새로 내려받는 패키지는 없다** — 직접 의존성으로 올리기만 한다.

## 3. 결정

- **줄 단위 판정** — stdout·stderr 를 줄(0x0A)로 끊고, 줄마다 UTF-8 로 온전하지 않으면(`buffer.isUtf8`) 콘솔 코드페이지로,
  3·4바이트 글자가 든 온전한 UTF-8 이면 UTF-8 로 읽는다. 0x0A 는 UTF-8·cp949 어느 쪽에서도 여러 바이트 글자 안에 나오지 않으므로
  줄로 끊어도 글자가 갈리지 않는다.
- **애매한 줄은 같은 출력을 근거로** — UTF-8 로 온전하지만 여러 바이트 글자가 전부 2바이트인 줄은 어느 쪽인지 줄만 봐서는 모른다.
  cp949 한글 중 첫 바이트 0xC2–0xC8·둘째 0xA1–0xBF 인 217자(책·창·천·청·체·카·타·키·칼 등)로만 된 줄이 이렇다 — 실측: cp949
  `카타.txt` 는 UTF-8 로 `īŸ.txt`, `책` 은 `å`, `체크` 는 `üũ` 로 온전하다(2026-11-25 리뷰가 찾았다). 반대로 진짜 UTF-8 인
  `×`(vitest 의 실패 표시)·`café`·`STATUS·ROADMAP` 을 cp949 로 읽으면 `횞`·`caf챕`·`STATUS쨌ROADMAP` 이 되므로 한쪽으로 몰 수 없다.
  그래서 같은 `sh_exec` 출력에 cp949 가 확실한 줄이 있고 UTF-8 이 확실한 줄이 없을 때만 cp949 로 읽고(그렇게 읽어 깨지면 UTF-8),
  그 밖에는 UTF-8 로 둔다 — 예전과 같은 결과라 새로 깨뜨리는 줄이 없다. 다른 줄을 봐야 하므로 디코드는 출력이 다 모인 뒤에 한 번
  한다(모으는 상한은 문자가 아니라 바이트 — `SH_EXEC_RAW_MAX` 120,000).
- **스트림마다 따로 모은다** — 두 스트림이 한 글자 사이에 끼어들어도 깨지지 않는다. 대신 출력 순서가 청크 단위에서 줄 단위로
  바뀐다(끝나지 않은 줄은 끝날 때 나온다).
- **긴 줄** — 끝나지 않은 줄이 상한(스트림마다 120,000바이트)을 넘으면 마지막 "안전한 바이트"(0x00–0x40 — 두 인코딩 모두
  여러 바이트 글자에 쓰지 않는다) 바로 뒤에서 끊어 넘긴다. 그런 바이트가 없으면 덜 온 UTF-8 글자만 남기고 넘긴다 — 갈린 조각은
  UTF-8 로 온전하지 않아 조각 전체가 cp949 로 읽히기 때문이다(같은 리뷰). 줄바꿈 없는 거대한 출력(압축된 JS 를 `type`)에도 메모리
  상한을 지키면서 글자를 자르지 않는다.
- **코드페이지 검출** — 워커가 기동할 때 한 번 `chcp` 를 `sh_exec` 와 똑같이 띄워 묻고, 그 번호와 실제로 쓸 인코딩을 시작 로그에
  남긴다(`셸 코드페이지=949(cp949)`). 숫자만 본다 — 문구가 로캘마다 다르고 그 문구 자체가 그 코드페이지로 인코딩돼 있어서다.
  65001·검출 실패·윈도우가 아님·iconv-lite 가 모르는 번호면 `(대체 없음)` — UTF-8 로만 읽는다(예전 동작에 줄 단위 재조립만 더해진다).
- **범위는 `sh_exec` 하나** — `pm2` 호출(Node, UTF-8 출력)과 `proc_logs` 는 그대로다. 30일 실측에서 깨짐 0 이고, `proc_logs` 는
  pm2 가 로그 파일을 이미 UTF-8 로 읽어 다시 내므로 워커에서 되살릴 바이트가 없다.

## 4. 남는 한계

- **애매한 줄만 있는 출력은 여전히 틀린다** — `echo 책` 이나 이름 하나뿐인 `dir /b` 처럼 근거가 될 다른 줄이 없으면 UTF-8 로
  읽어 조용히 라틴 문자가 된다(`å`). `�` 가 생기지 않으므로 U+FFFD 비율로는 잡히지 않는다. 같은 출력에 UTF-8 이 확실한 줄이 함께
  있어도 그렇다. 문장(오류 문구, `오전`·`오후` 가 든 `dir` 줄)은 217자 밖의 글자가 거의 반드시 섞여 해당이 없다.
- 반대로 cp949 가 확실한 줄과 함께 나온, 2바이트 글자뿐인 진짜 UTF-8 줄(예: UTF-8 파일 안의 `a·b` 한 줄과 cmd 오류 문구)은 cp949 로
  읽혀 틀린다. 예전에는 맞던 줄이지만 같은 출력에 cp949 줄이 섞여야 해서 드물다.
- 한 줄 안에 두 인코딩이 섞이면 그 줄은 한쪽이 깨진다.
- 콘솔 코드페이지와 다른 ANSI 코드페이지로 내는 프로그램 — 한국어 윈도우는 둘 다 949 라 해당이 없다.
- 안전한 바이트가 120,000바이트 동안 하나도 없는 cp949 줄은 상한에서 끊길 때 글자 하나가 갈릴 수 있다(UTF-8 줄은 글자 경계로 물러선다).

## 5. 검증

- 단위: 줄 판정·애매한 줄의 근거 판정·청크 경계 재조립·두 스트림 교차·긴 줄 절단·`chcp` 파싱(`agent/tests/shellOutput.test.ts`),
  `sh_exec` 에 실제 cp949 바이트를 내는 자식을 띄워 본문 확인(`agent/tests/remoteExecutors.test.ts` — 섞인 출력, `dir /b` 모양의
  짧은 이름, 두 갈래(close·hardTimer)가 모두 출력을 모으는지).
- 실환경: [스모크](../../../deploy/smoke-test.md)의 "셸 출력 한글" 절 — 워커 시작 로그의 코드페이지, 부원 계정으로 `dir`·없는 파일
  `type`·`ping` 을 돌린 뒤 `actions.result_summary` 로 판정(모델의 답은 깨진 문구를 문맥으로 고쳐 말할 수 있어 증거가 아니다).
- 30일 뒤: 로드맵 설계 §2.5 의 비율(`actions.result_summary` 의 U+FFFD)을 같은 방법으로 다시 잰다. 기대값은 0 근처다.
