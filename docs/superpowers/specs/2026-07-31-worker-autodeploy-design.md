# 미니PC 워커 배포 자동화 — 버전 가시성과 폴링 갱신

## 1. 배경 · 목표

머지하면 Railway 가 봇을 자동 배포한다. **워커는 자동으로 갱신되지 않는다.** 그런데
`fs_*`/`sh_exec`/`proc_*` 의 실행기(`agent/src/remote/executors.ts`)는 봇이 아니라 워커에서
돌기 때문에, 미니PC 를 손으로 갱신하기 전까지 그 수정은 한 줄도 실행되지 않는다.

2026-07-31 에 이것으로 네 시간을 태웠다. 워커의 마지막 pull 이 07-30 14:40 이었고 PR #11 은
그날 18:26 에 머지됐는데, 그 사실을 모른 채 실사용 결과(`.bat` 파일이 없다, 명령이 죽는다)를
전부 새 코드의 결함으로 해석했다. 전부 옛 코드의 정상 동작이었다.

**비쌌던 것은 명령 세 줄이 아니라 "워커가 낡았다는 것을 몰랐다"는 사실이다.** 자동화해도
실패할 때는 실패하고, 그때 알 방법이 없으면 같은 오진을 반복한다. 그래서 이 설계는 순서를
가진다 — 먼저 **보이게** 하고(조각 A), 그 위에 **자동 갱신**을 얹는다(조각 B). A 없이 B 만
있으면 "조용히 안 도는 자동화"가 되어 지금보다 나쁘다.

### 자동화를 막고 있던 것

게으름이 아니라 권한 분리다. `asahi` 계정은 `git pull`·`npm ci` 는 되지만
`Stop-ScheduledTask`/`Start-ScheduledTask` 가 안 된다(표준 계정). 관리자 창은 작업을 재시작할
수 있지만 `%APPDATA%\npm` 이 PATH 에 없어 npm 이 없다. **어느 한 계정도 전체 순서를 수행할 수
없다.**

그리고 워커가 비관리자로 도는 것은 손님의 셸을 실행하는 계정이라는 의도된 보안 경계다
(`docs/security/capability-model.md`). 그 전제를 풀어서 자동화를 사는 것은 교환이 맞지 않는다.

§4 의 두 결정이 이 매듭을 권한을 건드리지 않고 푼다.

## 2. 범위

**안**

1. 워커가 자기 커밋 SHA 를 `hello` 프레임에 실어 보낸다 (§3)
2. 봇이 그것을 조회 가능하게 하고, 오래 어긋나면 소유자에게 한 번 알린다 (§3)
3. 워커가 센티넬 파일을 보면 진행 중인 호출을 마치고 스스로 종료한다 (§4)
4. 미니PC 의 폴링 업데이터 작업 — 새 커밋 감지 → 센티넬 → `git pull` → 필요 시 `npm ci` (§4)
5. `deploy/worker-셋업.md`·`docs/agent-onboarding.md`·`deploy/smoke-test.md` 갱신 (§7)

**밖** — 각각 별도 과제다.

- **봇이 트리거하는 배포.** WebSocket 이 이미 있어 매력적이지만, 배포가 봇 가용성에 묶이고
  (봇 재배포 중에는 못 한다) "봇이 워커에 임의 코드를 배포한다"는 경로를 정식화한다. 지금도
  봇이 뚫리면 `sh_exec` 로 뭐든 할 수 있으므로 새 경계는 아니지만, 폴링하는 별도 작업이 더
  단순하고 봇과 독립적이다.
- **소유자 개인 워커(`owner-laptop`)의 자동 갱신.** 이 설계는 상시 켜져 있는 공유 미니PC 를
  전제한다. 개인 노트북은 켜지는 시각이 불규칙해 폴링 전제가 다르다.
- **롤백.** 나쁜 커밋이 자동으로 워커에 들어갔을 때 되돌리는 경로. 지금은 `main` 을 되돌리고
  다음 폴링을 기다리는 것이 전부다.

## 3. 조각 A — 버전 가시성

### 3.1 워커가 자기 커밋을 알린다

기동 시 `git rev-parse HEAD` 를 실행해 SHA 를 얻고, `hello` 프레임에 실어 보낸다.

`.git/HEAD` 를 직접 읽는 방법도 있으나 packed-refs 를 따로 다뤄야 한다. 이 워커는 `git pull`
로 갱신되므로 git 이 반드시 존재하고, 이미 `spawn` 을 쓰는 프로세스다 — 명령 하나가 더 단순하고
정확하다. 실패하면(리포가 아닌 곳에서 실행, git 부재) **`undefined` 를 보내고 계속 진행한다.**
버전을 모르는 것이 연결을 못 하는 것보다 낫다.

### 3.2 프로토콜 변경은 선택적이어야 한다

`WorkerHello` 에 `commit?: string` 을 **선택 필드로** 추가한다. 필수로 만들면 옛 워커가 새
봇에 붙었을 때 `parseFrame` 이 `null` 을 돌려주고 허브가 거부한다 — 배포 창에서 워커가 아예
연결되지 않는, 지금보다 나쁜 상태다. 그 창을 좁히자고 만드는 기능이 그 창을 최악으로 만들면
안 된다.

같은 이유로 봇 쪽도 `commit` 이 없는 `hello` 를 정상으로 취급한다.

### 3.3 봇이 비교한다

봇 자신의 SHA 는 `process.env.RAILWAY_GIT_COMMIT_SHA` 다(Railway 가 주입하는 git 변수). 로컬
PM2 폴백에는 없으므로, **없으면 비교를 생략하고 워커의 커밋만 노출한다.** 비교할 기준이 없는
것과 불일치는 다른 상태이며, 전자를 후자로 보고하면 거짓 경보가 된다.

허브(`agent/src/remote/hub.ts`)가 워커별로 `{ commit, connectedAt }` 을 들고 있는다. DB 는
쓰지 않는다 — 조회하는 쪽(`runtime_info`)도 알림을 내는 쪽도 같은 프로세스 안에 있다.

### 3.4 어떻게 드러나는가

**조회 — `runtime_info`**: 연결된 워커별로 `workerId`, 커밋(앞 7자), 연결 시각, 봇 커밋과의
일치 여부를 보고한다. 소유자가 언제든 물어볼 수 있다.

**알림 — 오래 어긋날 때만**: 불일치가 **15분 넘게 지속되면** 소유자에게 한 번 알린다. 같은
`(workerId, 워커커밋, 봇커밋)` 조합에 대해서는 다시 알리지 않는다.

15분 게이트가 이 설계의 핵심 판단이다. **불일치는 정상 상태이기도 하다** — 봇이 배포되고
워커가 갱신되기까지 반드시 어긋난다. "다르면 즉시 경고"는 배포마다 울려 금방 무시당하고,
그러면 정작 오늘 같은 날 보지 않게 된다. 조각 B 가 5분 주기로 돌므로, 15분을 넘겼다는 것은
**자동 갱신이 실제로 막혔다**는 뜻이다. 그때만 울린다.

허브 재시작으로 이 상태가 초기화되는 것은 무해하다 — 봇이 재배포되면 어차피 새로운 비교가
시작된다.

## 4. 조각 B — 폴링 자동 갱신

### 4.1 작업 스케줄러 작업 둘

| 작업 | 계정 | 트리거 | 하는 일 |
|---|---|---|---|
| `asahi-worker` (기존) | `asahi` | 부팅 시 | 워커 실행. **"실패 시 다시 시작" 정책을 켠다** |
| `asahi-worker-update` (신규) | `asahi` | 5분마다 | 갱신 확인·수행 |

### 4.2 업데이터가 하는 일

리포에 커밋하는 PowerShell 스크립트(`deploy/update-worker.ps1`)로 두고, 작업은 그것을 부른다.
스크립트가 리포 안에 있으므로 스크립트 자신도 `git pull` 로 갱신된다.

1. `git fetch origin main` — 로컬 HEAD 와 `origin/main` 이 같으면 아무것도 하지 않고 끝낸다
2. **센티넬 파일을 만든다**
3. 워커 프로세스가 사라질 때까지 기다린다(상한을 둔다 — §4.4)
4. `git pull`
5. **`package-lock.json` 이 바뀐 경우에만** `npm ci`
6. 센티넬 파일을 지운다. 재기동은 하지 않는다

5번이 중요하다. 대부분의 커밋은 의존성을 건드리지 않는데, 19초 걸리는 `npm ci` 가 바로
`esbuild.exe` 잠금 때문에 워커 정지를 강제하는 원인이다. 잠금 파일이 그대로면 건너뛴다.

### 4.3 결정 1 — "한가한가"는 워커가 판단한다

업데이터는 센티넬 파일만 만들고 **워커가 바쁜지 전혀 모른다.** 워커가 그 파일을 보면 진행
중인 도구 호출이 끝난 뒤 스스로 종료한다. 바쁘면 알아서 늦게 끝나고, 업데이터는 프로세스가
사라지기를 기다리기만 한다.

"밖에서 바쁨을 알아내는" 기계가 통째로 사라진다. 그리고 판단이 실제로 그것을 아는 쪽에 있다.

**이 기계는 이미 있다.** `agent/src/worker.ts` 의 `trackInFlight` 가 모든 실행기 호출을 감싸
진행 중 개수를 세고, `idle()` 이 0 이 될 때 resolve 한다. SIGINT/SIGTERM 핸들러가 이미 그것을
쓴다. 센티넬 처리는 같은 경로를 재사용한다.

**다만 현재 순서를 뒤집어야 한다.** 오늘의 `shutdown()` 은 `client.stop()` 으로 소켓을 먼저
닫고 그 다음 `idle()` 을 기다린다 — 그래서 진행 중이던 호출의 결과 프레임이 허브까지 돌아가지
못한다(그 파일의 FIX8 주석이 이 한계를 명시한다). 오늘은 사람이 일부러 멈추는 상황이라 그것으로
충분했지만, 자동 갱신에서는 **부원이 시킨 작업이 조용히 실패**하는 것을 뜻한다. 센티넬 경로는
`idle()` 을 먼저 기다리고 그 다음 소켓을 닫는다 — 그래야 "한가할 때 갱신한다"가 부원 입장에서도
참이 된다.

### 4.4 상한이 필요한 곳 둘

- **워커 쪽**: `idle()` 을 무한정 기다리지 않는다. `sh_exec` 는 기본 120초까지 갈 수 있고,
  `proc_start` 가 pm2 를 기다리는 경우도 있다. 상한을 넘기면 오늘의 순서(소켓 먼저 닫기)로
  떨어져 종료한다 — 갱신이 영원히 막히는 것보다 호출 하나가 실패하는 편이 낫다.
- **업데이터 쪽**: 워커가 사라지기를 기다리는 데도 상한을 둔다. 넘기면 이번 회차를 포기하고
  다음 5분에 다시 시도한다. **강제 종료하지 않는다** — 워커가 안 죽는 상황은 그 자체로 조사할
  일이고, 자동화가 그것을 덮으면 안 된다. 조각 A 의 15분 알림이 이 경우를 잡는다.

### 4.5 결정 2 — 종료 코드가 "돌아올지"를 정한다

워커가 **비정상 종료 코드**로 끝나면 작업 스케줄러의 "실패 시 다시 시작" 정책이 다시 띄운다.
그래서 업데이터는 `Start-ScheduledTask` 를 부르지 않아도 되고, `Stop-ScheduledTask` 도 필요
없다(워커가 스스로 나간다). **`asahi` 의 비관리자 권한만으로 전체 순서가 돈다** — §1 의 권한
매듭이 풀리고 보안 전제는 그대로다.

여기서 종료 코드에 의미를 준다.

| 경로 | 종료 코드 | 뜻 |
|---|---|---|
| SIGINT/SIGTERM (사람이 멈춤) | `0` | 멈추고 **머문다** — 재시작 정책이 반응하지 않는다 |
| 센티넬 (갱신) | 0 이 아닌 값 | 멈추고 **돌아온다** — 재시작 정책이 띄운다 |

이 구분이 없으면 사람이 일부러 내린 워커를 스케줄러가 도로 띄운다. 요구사항은 "0 이 아닐 것"
뿐이고 구체적인 값은 의미를 갖지 않는다 — 계획에서 하나 골라 상수로 고정한다.

### 4.6 센티넬 파일의 위치

**`WORKER_ROOTS` 밖에 둔다.** 안에 두면 `fs_write` 로 회원이 직접 만들 수 있고, 그러면 아무나
워커를 계속 재시작시켜 서비스를 방해할 수 있다. `fs_*` 는 경로로 봉쇄되므로 밖에 두는 것만으로
그 경로가 닫힌다.

**다만 이것을 보안 경계로 착각하면 안 된다.** `sh_exec` 는 경로 스코프의 대상이 아니므로
(`docs/security/capability-model.md` §5) 회원은 셸로 어디든 파일을 만들 수 있고, 애초에 워커
프로세스를 직접 죽일 수도 있다. 센티넬은 **새 능력을 열지 않는다** — 이미 가능한 일에 편한
경로를 하나 더하지 않을 뿐이다. `WORKER_ROOTS` 밖에 두는 것은 실수 방지선이지 방어선이 아니다.

### 4.7 잡 오브젝트 함정

`asahi-worker-update` 는 **별도의 작업 스케줄러 작업**이어야 한다. 워커가 띄운 자식 프로세스로
만들면 워커의 잡 오브젝트 안에서 태어나고, 워커가 종료할 때 함께 죽어 갱신이 중단된다 —
`docs/agent-onboarding.md` 4절이 PM2 데몬에서 실제로 겪은 것과 같은 함정이다.

## 5. 무엇이 남는가

이 설계 뒤에도 사람이 해야 하는 일이 있다.

- **두 작업의 최초 등록** — 작업 스케줄러 등록은 자동화 대상이 아니다. 절차는 문서에 남긴다.
- **첫 회차 감시** — PowerShell 스크립트는 이음매 너머라 유닛 테스트가 닿지 않는다(§6).
- **나쁜 커밋의 롤백** — `main` 을 되돌리고 다음 폴링을 기다리는 것이 전부다(§2 범위 밖).

## 6. 테스트 전략

**유닛으로 덮이는 것**(`agent/`):

- 커밋 읽기 — `spawn` 을 주입 가능한 이음매로 두고, 성공·실패(`undefined` 반환) 양쪽을 고정
- `hello` 의 `commit` 선택성 — `commit` 이 **없는** 프레임이 정상 파싱되는 것을 직접 단정한다.
  이 단정이 옛 워커 호환의 유일한 방어선이다
- 불일치 판정 — 봇 SHA 부재(비교 생략), 일치, 불일치 세 갈래
- 15분 게이트와 중복 알림 방지 — 시계를 주입해 고정한다. 같은 조합에 두 번 알리지 않는 것을
  직접 단정한다
- 센티넬 경로의 순서 — `idle()` 이 소켓 닫기보다 **먼저** 완료되는 것, 그리고 상한을 넘겼을 때
  옛 순서로 떨어지는 것
- 종료 코드 — SIGTERM 은 `0`, 센티넬은 비정상

**유닛이 닿지 않는 것**:

`deploy/update-worker.ps1` 과 작업 스케줄러 설정은 하드웨어에서만 검증된다. `runPm2` 같은 주입
지점 너머와 같은 성격이다 — 계획 단계에서 이것을 의식하고, `deploy/smoke-test.md` 에 항목으로
넣는다. 첫 배포는 사람이 지켜본다.

스모크 항목은 최소한 이 셋을 덮는다: (1) 새 커밋이 머지되면 5분 안에 워커가 갱신되는가,
(2) 도구 호출이 진행 중일 때 갱신이 그 호출을 죽이지 않는가, (3) 갱신이 막혔을 때 15분 뒤
소유자에게 알림이 오는가.
