# 하네스 턴의 기억 도구 — 허브 `memory` 서버 — 설계

2026-11-25 운영자가 정한 다음 순서(배포·확인 → 보안 선결 → **기억 정비** → 동아리 기능 → N3·X6)에서 기억 정비의
첫 조각(3-1)이다. 검색 개선(3-2)과 수정·목록(3-3)은 이 문서의 범위가 아니다.

## 1. 문제

- 소유자 턴은 워커가 붙어 있고 이미지·무인 턴이 아니면 전부 하네스(계정 B 의 Claude Code)로 간다
  (`core/agent.ts` 의 `decideHarnessDispatch`). 그 세션에는 봇의 `remember`·`recall`·`forget` 이 없고, 능력 안내가
  "이 방식의 턴에서는 아직 기억 도구를 쓸 수 없어요"라고 답하게 한다(`core/persona.ts`).
- 결과는 셋이다.
  1. 가장 많이 쓰는 경로(소유자)에서 기억을 저장·검색할 수 없다.
  2. `forget` 은 소유자 전용이라, **공용 기억을 지울 수 있는 경로가 사실상 없다** — 이미지를 붙인 턴이나 워커가
     꺼진 때(봇 자기 세션으로 떨어질 때)만 된다.
  3. 5단계(로드맵 X6)로 부원을 하네스로 옮기면 부원도 기억 도구를 잃는다. 이 서버는 X6 의 선행 조건이다.
- 새 세션을 열 때 기억 목록(6000자 예산)은 하네스 턴에도 실린다(`core/turnPrep.ts` 의 `buildContextBlock` 이 두
  경로 공통). 빠진 것은 **도구**다.

## 2. 결정

### 2.1 허브의 세 번째 서버

비밀이 필요한 MCP 서버를 봇(계정 A)에서 띄우는 기존 허브(`core/mcpHub.ts`, 4단계 4.1)에 `memory` 서버를 더한다
(`mcp/memoryServer.ts`). 도구는 `remember`·`recall`·`forget` 이고, 하네스 세션에는 `mcp__memory__remember` 처럼
보인다. 기억은 봇의 DB 에 있고 DB 접속 문자열은 A 를 떠나지 않는다 — GitHub·Supabase 서버와 같은 이유로 허브다.

### 2.2 핸들러는 봇 세션과 같은 함수

`core/tools.ts` 의 `rememberHandler`·`recallHandler`·`forgetHandler` 를 그대로 부른다. 그래서 두 경로가 갈라질 수
없다:

- 범위는 위치가 정한다(`memoryScopeFor`) — DM 은 개인 기억, 서버 채널은 동아리 공용 기억.
- 공용 기억 상한(제목 100자·내용 4000자), recall 풀(소유자 DM = 전부, 손님 DM = 본인 + 공용, 서버 = 공용만),
  forget 소유자 전용과 여러 건이면 번호 목록, 작성자 표시와 개행 방어.

핸들러가 받는 값을 `MemoryToolCtx`(기억 리포·사용자 리포·위치·소유자 여부·사용자·대화)로 좁힌다. 허브 서버가
`ToolCtx` 전체를 꾸미지 않고 부르기 위해서다. 도구 설명과 인자 모양도 한 곳(`MEMORY_TOOL_SPECS`)에서 두 경로가
함께 쓴다 — 같은 문장을 두 곳에 두면 한쪽만 고치는 드리프트가 생긴다.

### 2.3 신원과 위치는 작업 토큰에서

- 허브 서버 팩토리가 그 요청의 **검증된 클레임**을 받는다(`servers: Record<string, (claims) => McpServer>`). 기존
  두 서버는 인자를 쓰지 않으므로 바뀌지 않는다.
- `userId`·`conversationId` 는 이미 클레임에 있다. **위치(`isPrivate`)를 클레임에 더한다** — `runHarnessTurn` 이
  그 턴의 `context.isPrivate` 로 발급한다. 시스템 프롬프트도 같은 값으로 만들어지므로, 모델이 읽은 안내와 도구가
  보는 위치가 같다. 대화 표(`conversations.is_private`)를 다시 읽지 않는 이유도 이것이다 — 허브 서버가 대화 표를
  몰라도 되고, 턴이 본 값과 어긋날 여지가 없다.
- 소유자 여부는 클레임의 `userId` 를 봇 설정(`DISCORD_OWNER_ID`)과 견준다. 코어(`core.ts`)와 같은 규칙이다.
- **위치가 없는 토큰은 기억 도구를 거부한다**(fail closed). 위치를 모르면 개인·공용을 가를 수 없다.

### 2.4 프로필과 능력 안내

- 소유자 프로필의 허브 목록에 `memory` 를 더한다(`core/profiles.ts` 의 `OWNER_MCP_HUB`). 손님 프로필은 그대로다 —
  부원은 아직 하네스로 가지 않는다. X6 에서 손님 프로필에 더하고 손님 하네스 안내를 쓴다.
- 하네스 능력 블록의 "기억 도구 없음" 줄을 `mcp__memory__*` 안내로 바꾼다. 문장은 위치별이다 — DM 에서는 개인
  기억, 서버 채널에서는 공용 기억(주제별로 나눠 저장, 틀리면 forget).
- 하네스용 기억 블록을 넣는다. 도구 이름은 네임스페이스 이름만 쓴다 — 맨 이름(`remember` 등)은 이 턴에 없는
  도구다. Claude Code 자체 메모 파일(`CLAUDE.md` 등)에 저장하지 말라는 줄을 둔다. 그 파일은 봇의 기억 목록에
  실리지 않아 다른 대화에서 찾을 수 없다.

### 2.5 워커는 바뀌지 않는다

워커는 프로필의 허브 이름마다 루프백 주소와 작업 토큰을 붙일 뿐이다(`remote/sessionRunner.ts` 의
`buildMcpServers`). 이름이 하나 늘어도 워커 코드는 그대로이고, 붙었는지는 워커 로그의
`[runner] MCP 서버: … memory=connected` 한 줄로 판별한다.

## 3. 경계와 위험

- **토큰 허용 목록**: `memory` 는 소유자 토큰에만 실린다. 손님 토큰으로 `/mcp/memory` 를 직접 두드려도 403 이다
  (기존 경계 그대로).
- **무인 턴**: 유휴 요약·정기 게시는 `noRemoteTools` 라 하네스로 가지 않는다. 봇 세션에 있는 `memoryWriteEnabled`
  축(무인 턴에서 remember·forget 을 닫는 것)이 하네스에 따로 필요 없는 이유다. 무인 턴을 하네스로 보내게 되면 그
  턴의 허브 목록에서 `memory` 를 빼야 한다.
- **진행 중인 소유자 작업 토큰이 같은 계정에 보인다**(위험 등록부 §14로 적는다). 하네스 세션과 부원의 `sh_exec` 는
  같은 계정 B 에서 돈다(ADR 0009·0011). Agent SDK 는 허브 MCP 설정(작업 토큰이 든 `Authorization` 헤더 포함)을
  Claude Code CLI 의 명령줄(`--mcp-config`)로 넘긴다. 그래서 소유자 하네스 턴이 도는 동안 같은 계정의 프로세스는
  그 토큰을 읽을 수 있다.
  - 지금도 그 토큰으로 프록시(소유자 모델, 창 상한 면제)와 GitHub·Supabase 읽기를 쓸 수 있다.
  - 이 변경으로 **소유자 이름의 기억 저장과 공용 기억 삭제**가 더해진다. 소유자 이름으로 심은 기억은 새 세션마다
    컨텍스트에 실리고 recall 에서 소유자가 등록한 것으로 보인다 — 소유자의 권위를 빌린, 오래 남는 프롬프트 주입이다.
    읽기(소유자 DM 토큰의 recall 은 모든 사람의 개인 기억까지)는 새 노출이 아니다. ADR 0010 으로 등록된 부원 누구나
    `db_query` 로 `memories` 표 전체를 읽을 수 있기 때문이다(읽기 가드는 표를 거르지 않는다).
  - 완화: 토큰은 2시간짜리이고 루프백에서만 통한다. 삭제는 매일 기억 백업(`core/backup.ts`)과
    `scripts/restoreMemories.ts` 로 되살린다. 허브 서버는 **실제로 일어난 쓰기·삭제**를 봇 로그에 한 줄씩 남긴다(기억
    번호·범위, 누가·어느 대화·어느 작업 토큰 — 제목·내용은 없다). 리포의 쓰기·삭제 지점을 감싸 남기므로, 거절되거나
    아무것도 지우지 않은 호출은 줄이 없다. 막는 길(소유자 턴을 다른 계정에서 돌리기)은 ADR 0011 이 철회한 계정 C 와
    같은 축이라 이 변경의 범위 밖이다.
- **오류 원문**: DB 오류의 원문(접속 호스트·제약 이름 등)은 세션에 돌려주지 않는다. 모델이 그대로 채널에 옮길 수 있기
  때문이다. 세션에는 일반 문구를 주고 원문은 봇 로그에만 남긴다.

## 4. 범위 밖

- 검색 개선(3-2), 기억 수정·목록·부원 본인 삭제(3-3).
- 손님 프로필의 `memory`(X6). 그때 함께 할 일이 둘 있다.
  - **역할을 호출마다 다시 본다.** 지금은 소유자만 이 서버를 쓰고 소유자 여부는 설정에서 오므로 토큰 수명(2시간) 동안
    바뀔 것이 없다. 손님에게 열면, 그 사이 차단된 부원의 토큰이 계속 쓰지 못하게 호출마다 `users` 의 역할을 확인해야
    한다. 봇 세션 경로는 턴마다 확인한다.
  - **안내와 허용 목록을 같은 조건으로 연다.** 하네스 기억 안내(`persona.ts`)는 `isOwner && harness` 일 때만 나가고, 손님
    하네스 턴에는 봇 세션의 기억 블록(맨 이름)이 나간다. 손님 프로필에 `memory` 를 넣는 커밋에서 손님 하네스 안내도
    네임스페이스 이름으로 바꿔야 한다.
- 대화에서 기억을 자동으로 쌓기, 다른 채널 읽기 — 공용 기억 오염(프롬프트 주입)과 프라이버시 설계가 먼저다.

## 5. 검증

- 유닛·통합: 실제 MCP 클라이언트로 허브에 붙어 `memory` 를 왕복한다(pg-mem). DM 토큰의 저장은 개인 기억, 서버
  토큰의 저장은 공용 기억. recall 풀 규칙. forget 은 소유자만. 위치 없는 토큰은 거부. 팩토리가 검증된 클레임을
  받는다. 작업 토큰의 `isPrivate` 왕복과 모양 검사, 프로필, 하네스 디스패치가 발급하는 토큰, 하네스 능력 안내.
- 이음매 뒤(스모크로만): 실제 하네스 세션이 `memory=connected` 로 붙는가, 실제 모델이 맨 이름이 아니라
  `mcp__memory__*` 를 부르는가. 항목은 [스모크 테스트](../../../deploy/smoke-test.md)에 더한다.

## 6. 배포와 되돌리기

봇 코드만 바뀐다. production 반영 뒤 봇이 갱신되면 다음 소유자 하네스 턴부터 붙는다. 되돌리기는 `OWNER_MCP_HUB`
에서 `memory` 를 빼는 것이고, 급하면 봇의 `HARNESS_OWNER` 를 꺼 소유자 턴을 봇 자기 세션(원래의 기억 도구가 있는
경로)으로 보낸다.
