# 동아리 공용 기억 — 설계

## 1. 무엇을 고치는가

아사히는 동아리 '세미콜론'의 마스코트이고 동아리를 잘 알아야 한다. 그런데 **동아리 지식을
쌓을 방법이 없다.**

`memories` 테이블에는 `scope` 가 있고 `shared` 를 **읽는** 쿼리가 세 군데다
(`forUser`·`sharedOnly`·`search`). 서버 채널의 `recall` 은 `sharedOnly()` 만 본다.

그런데 **`scope='shared'` 를 쓰는 코드가 리포 전체에 없다.** `rememberHandler` 는 항상
`scope: 'user'` 로만 저장하고(`tools.ts:79`), 다른 `insert` 호출은
`character_fact`(`scope: 'character'`)뿐이다. DB 확인 결과도 기억 1건, 전부 `user` 다.

결과:

- **서버 채널의 `recall` 은 구조적으로 항상 빈손이다.** 읽을 것이 생길 수가 없다
- 부원이 DM 에서 저장해도 그건 그 사람 개인 기억이라 다른 부원에게 안 보인다
- 동아리 문서를 주고 "기억해"라고 하면 거부된다 — `remember` 가 DM 전용이라서다

공용 기억이라는 개념이 스키마와 읽기 경로에만 있고 **쓰기 경로가 통째로 빠져 있다.**

## 2. 설계

### 2.1 어디서 말하느냐가 스코프를 정한다

새 도구도 스코프 인자도 만들지 않는다. **`remember` 를 서버 채널에도 열고, 위치가 스코프를
결정한다.**

| 어디서 | 스코프 | 뜻 |
|---|---|---|
| DM | `user`(지금 그대로) | 나에 대한 것 |
| 서버 채널 | **`shared`** | 동아리 전체의 것 |

모델이 스코프를 고르게 하면 틀릴 수 있지만 **위치는 틀릴 수가 없다.** 이 리포가 워커 선택에
이미 쓰는 규칙(`workerSelect.ts` — "어디서 말하느냐가 어느 기계냐를 정한다")과 같은 축이다.

부수 효과가 하나 더 있다. 동아리 사실을 **공개된 자리에서 등록하게 되는 것** 자체가
건강하다 — 다른 부원이 그 순간을 본다.

**소유자·손님 모두 쓸 수 있다.** 동아리 지식이 빨리 쌓이는 편이 낫다는 판단이다. 대신
§2.2·§2.3 이 그 대가를 받는다.

### 2.2 공용 기억은 작성자를 보여준다

`memories.user_id` 에 작성자가 이미 저장되는데 `recall` 출력은 보여주지 않는다. 누구나 쓸 수
있게 되면 **누가 넣었는지가 그 정보를 얼마나 믿을지의 근거**가 된다.

```
- [회비] 학기당 2만원 (우성현이 등록)
```

이름은 `users.display_name` 에서 온다(`usersRepo.displayNames()` 가 이미 있다). 이름을 모르면
표시를 생략한다 — 숫자 id 를 보여주면 읽는 사람에게 아무 의미가 없다.

**개인 기억(`scope='user'`)에는 붙이지 않는다.** 본인 것이라 작성자가 자명하다.

### 2.3 지우기는 소유자만

`forget` 도구를 새로 만든다. 넣는 것과 지우는 것은 다른 권한이다 — 넣는 것은 보태는 일이고
지우는 것은 **다른 사람의 기여를 없애는** 일이다.

- **공용 기억만** 대상이다. 남의 개인 기억은 건드리지 않는다
- 제목으로 찾는다. **여러 개가 걸리면 지우지 않고 목록을 보여준다** — 무엇을 지웠는지 모르는
  삭제가 가장 나쁘다
- 하나도 안 걸리면 그렇게 말한다
- 소유자면 DM·서버 어디서든 쓸 수 있다. 기계가 아니라 봇 자신의 데이터에 대한 권한이지만,
  공용 기억은 서버에서 만들어지므로 고치는 것도 그 자리에서 되는 편이 자연스럽다

### 2.4 길이 상한과 문서 쪼개기

`remember` 에는 지금 길이 상한이 없다(`character_fact` 만 200자 상한이 있다). 공용 기억은
누구나 쓸 수 있고 **`recall` 이 걸린 기억의 내용 전체를 돌려주므로**, 문서를 통째로 넣으면
"회비 얼마야"에 회칙 전문이 딸려온다.

- 공용 기억 1건의 내용은 **4000자**로 제한한다. 넘으면 자르지 않고 **거절한다** — 조용히
  잘린 기억은 사실의 일부만 남아 더 위험하다. 거절 문구가 실제 길이와 상한을 함께 말한다
- 프롬프트로 **주제별로 쪼개 저장하도록** 안내한다("회비", "활동 시간", "가입 절차")

**문서 원본이 필요하면 그건 기억이 아니라 파일이다.** 2026-08-01 에 파일 올리기가 들어갔으므로
워커에 두고 `fs_read` 로 읽으면 된다. 기억은 "묻는 말에 바로 답할 수 있는 사실"을 담는 자리다.

### 2.5 프롬프트

`persona.ts` 의 능력 안내가 지금 서버 채널에 대해 이렇게 말한다.

- `:85` — "공개 채널에서는 새 설정을 저장할 수 없다"
- `:184`·`:190`·`:238` — "개인기억 저장 … 은 이 채널에서 할 수 없습니다"

`:85` 는 `character_fact`(캐릭터 신상) 얘기라 **그대로 둔다** — 그건 여전히 DM 전용이다.
나머지 셋은 "개인기억 저장"이 안 된다는 뜻으로 읽히는데, 이제 **공용 기억 저장은 된다**는
사실이 빠져 있어 아사히가 시도조차 하지 않는다. 그 자리에 공용 기억을 더한다.

손님 분기(`:238`)도 함께 고친다 — 손님도 쓸 수 있다.

### 2.6 오류 처리

- 이름 조회 실패는 대화를 막지 않는다. 작성자 표시만 생략하고 기억은 그대로 보여준다 —
  부가 정보가 본 기능을 인질로 잡지 않는다(`proc_list` 의 이름 표시와 같은 원칙)
- `forget` 이 아무것도 못 찾으면 실패가 아니라 사실로 답한다

## 3. 고르지 않은 선택지

| | 방식 | 왜 아닌가 |
|---|---|---|
| A | `remember(scope)` 인자를 모델이 고르게 | 모델이 틀릴 수 있고, 틀리면 개인 얘기가 전원에게 보이거나 동아리 사실이 한 사람에게만 남는다. 위치는 틀릴 수가 없다 |
| B | `remember_shared` 별도 도구 | 도구가 하나 늘고 모델이 둘 중 고르는 부담이 생긴다. A 와 같은 위험을 도구 이름으로 옮긴 것뿐이다 |
| C | 공용 기억도 소유자만 쓰기 | 안전하지만 동아리 지식이 소유자 한 사람의 손으로만 쌓인다. 사용자 판단으로 탈락 — 대신 작성자 표시(§2.2)와 소유자 삭제(§2.3)로 대가를 받는다 |

## 4. 테스트 전략

**유닛으로 고정할 것**

- 스코프 판정: DM → `user`, 서버 → `shared`. 소유자·손님 양쪽
- 도구 노출: 서버 채널에 `remember` 가 열리는 것, 손님 서버에도 열리는 것
- 작성자 표시: 공용 기억에는 붙고 개인 기억에는 안 붙는 것. 이름을 모르면 생략하는 것
- `forget` 권한: 소유자가 아니면 거부. 공용 기억만 지우고 개인 기억은 못 지우는 것
- `forget` 다중 일치: 지우지 않고 목록을 돌려주는 것
- 길이 상한: 4000자 초과 거절, 거절 문구에 길이와 상한이 들어가는 것

**스모크로 넘길 것**

- 서버에서 동아리 사실을 저장하고, 다른 부원 계정으로 `recall` 해서 보이는 것
- 그 출력에 작성자 이름이 붙는 것
- 소유자가 `forget` 으로 지우고 다시 `recall` 하면 사라지는 것

## 5. 이 문서가 다루지 않는 것

- 기억 수정(`edit`) — 지우고 다시 넣으면 된다. 별도 도구를 만들 만큼 자주 쓰이는지 아직 모른다
- 개인 기억의 삭제 — 이 문서는 공용 기억만 다룬다
- 기억 검색 품질(임베딩·순위) — 지금은 부분 문자열 일치다. 기억이 쌓여 그것이 실제로 문제가
  되면 그때 본다
- 문서 원본 보관 — 기억이 아니라 파일이다(§2.4)
