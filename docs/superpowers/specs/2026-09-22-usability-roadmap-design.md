# 사용성 로드맵 2026-09 — 근거·실측·결정

[로드맵](../../status/ROADMAP.md)의 2026-09-22 판이 **왜 그 항목을 그 순서로** 담았는지의 근거 문서다.
로드맵은 "무엇을 다음에 하나"만 적고, 이 문서는 실측 수치·코드상 원인·배제한 대안·운영자가 내려야 할
결정을 적는다. **구현 스펙이 아니다** — Now 항목 하나하나는 착수할 때 자기 스펙을 따로 쓴다
(이 저장소의 관례: 로드맵 항목 → 스펙 → 계획).

## 1. 무엇을 정하는가

운영자가 2026-09-22 에 "사용성 개선을 위한 다음 로드맵"을 요청했고, 대화에서 세 가지가 정해졌다.

1. **두 축을 한 로드맵에 담는다.** 축 A = 쓰는 사람 모두의 마찰(운영자가 1차 보고자지만 같은 진행 표시·
   같은 얇은 워커 경로를 부원도 겪는다), 축 B = 부원의 진입·권한·경로.
2. **운영자가 꼽은 마찰의 순서**: (1) 긴 작업을 진행할 때 봇이 정확히 어떤 작업을 하고 어떤 판단을
   하는지 보여주지 못한다, (2) 작업 제어(취소·이어가기), (3) 출력 품질(한글 깨짐·마크다운·잘림).
3. **부원은 이미 쓰고 있다.** 로드맵의 옛 판(2026-08-07)이 전제한 "소유자 단독 국면"은 사실이 아니다.
   남은 진입 관문은 "DB 허용 목록에 넣은 사람만"이고, 운영자는 그것을 없애기로 했다 — 손님 DM 은
   이미 닫혔고(2026-09-07) 봇은 운영자가 연결한 공개 서버에서만 불린다.

우선순위는 이 저장소의 원칙대로 **추측이 아니라 실측**으로 정했다([관측 설계](./2026-07-28-observability-for-club-open-design.md) §9,
[셸 사용성 설계](./2026-07-31-shell-ux-design.md) §1 이 같은 방법을 썼다). 이번 갱신이 관측 설계가 미뤄 둔
**M2 결정 지점의 첫 실행**이다 — 부원 데이터가 이제 있다.

09-22), 시각은 KST. 개별 발화·파일 내용은 읽지 않았고 표에 남는 것은 집계뿐이다.

### 2.4 긴 작업은 얼마나 긴가

`messages` 에서 사용자 발화 → 바로 다음 봇 답변을 한 턴으로 보고, 그 사이 `actions` 수와 소요를 쟀다
(연달아 온 사용자 발화는 짝이 없어 빠진다 — 약간 적게 센 값이다).

| 역할 | 턴 | 스텝 p50 / p90 / 최대 | 소요 p50 / p90 / 최대 | 2분 초과 | 10분 초과 | 30스텝 이상 |
|---|---|---|---|---|---|---|
| 부원 | 57 | 1 / 10 / 30 | 10 s / 99 s / 6.1 분 | 5 | 0 | 1 |
| 소유자 | 88 | 1 / 9 / **127** | 22 s / 88 s / **13.6 분** | 6 | 1 | 3 |

읽는 법: 턴의 대부분은 한 스텝·수십 초다. **긴 턴은 열에 하나지만 실재한다** — 30일에 열한 번 2분을
넘겼고, 127스텝·13.6분짜리 턴이 있었다. 그 턴에서 사용자가 볼 수 있었던 것은 마지막 12줄뿐이었고
(§3.2), 끝나자 그마저 지워졌다.

### 2.5 출력 품질 — 셸 결과의 한글 깨짐

`actions.result_summary`(본문 **앞 200자**)에 U+FFFD(깨진 문자 대체 기호)가 든 비율.

| 도구 | 호출 | 깨진 문자 포함 | 한글 포함 |
|---|---|---|---|
| `sh_exec`(얇은 워커) | 183 | **29 (16%)** | 62 |
| `Bash`(하네스) | 303 | 3 (1%) | 123 |
| `proc_logs` / `proc_start` | 10 / 7 | 0 / 0 | 0 / 7 |

앞 200자만 본 값이라 **실제는 이보다 많다**. 얇은 워커 경로 고유의 문제이고(원인은
[온보딩](../../agent-onboarding.md) 2절 — 워커가 UTF-8 로 디코드하는데 윈도우 내장 명령은 cp949 로
낸다), 하네스 경로에서는 거의 없다.

### 2.6 측정 자체의 구멍

- **`llm_usage` 는 0행이다.** 3단계 프록시 운영화가 "모델 호출 하나마다 한 행"을 약속했는데
  (`agent/src/core/llmProxy.ts` 의 `recordUsage` — 2xx SSE 의 `message_start`/`message_delta` 에서 읽는다;
  `agent/src/index.ts` 가 `LlmUsageRepo.record` 로 잇는다) 소유자 하네스 턴이 30일에 수백 번 돌았는데도
  행이 없다. 프록시를 타지 않는가, SSE 모양이 다른가는 미니PC 에서만 판별된다. 이 표가 비어 있으면
  (1) 하네스 턴의 모델 호출 수·토큰을 잴 수 없고, (2) 5단계의 부원별 토큰 창 상한이 **조용히 작동하지
  않는다** — 상한이 `sumTokensForUserSince` 로 합을 재기 때문이다.
- `turns` 는 소유자를 세지 않는다(§2.1).
- `actions.result_summary` 는 앞 200자다 — 종료 코드·깨진 문자 모두 적게 센다.

## 3. 여정별 마찰과 로드맵 항목

사용자의 한 번 사용을 네 국면으로 나눠 마찰을 놓는다. 항목 번호는 로드맵의 것이다(N = Now, X = Next).

### 3.1 시키기 전 — 들어올 수 있는가

**N3 · 허용 목록 제거 — 서버 멤버면 누구나** (축 B)

- **문제**: 등록되지 않은 사람이 서버에서 봇을 멘션하면 **아무 일도 일어나지 않는다.** `users` 에 행이
  없으면 `getRole` 이 `blocked` 를 돌려주고(`agent/src/store/usersRepo.ts`), `decideRoute` 가 `ignore` 로
  끝낸다(`agent/src/adapters/discord.ts`). 답도 안내도 없다. 등록은 소유자 DM 의 `manage_access` 로만 된다.
- **운영자 결정**: 관문을 없앤다. 손님 DM 은 이미 받지 않고(`dm-declined`, 2026-09-07), 봇은 운영자가
  연결한 공개 서버에서만 불린다 — 서버 초대가 곧 신뢰 경계다.
- **실체**: "목록에 넣기"를 없애는 것이지 `users` 행을 없애는 것이 아니다. 행은 표시 이름·시간당
  한도(`turns.reserve` 는 `user_id` 로 센다)·작업 폴더(`<루트>/<userId>`)·사용량 기록에 계속 필요하다.
  따라서 **첫 메시지에서 자동 등록**하고, `blocked` 는 **명시적 차단 목록**으로 남긴다(`manage_access` 는
  차단·해제만 하게 된다).
- **같이 가야 하는 것**: 신뢰 경계가 "운영자가 등록한 사람" → "디스코드 서버에 있는 사람"으로 옮겨간다.
  부원의 `sh_exec` 에는 조직 전체 `contents:write` 1시간 토큰이 붙으므로([위험 등록부](../../security/risk-register.md) §9)
  서버에 초대된 누구나 조직 저장소에 push 할 수 있게 된다. 결정 기록(ADR)과 위험 등록부 §2·§9 갱신을
  코드와 같은 PR 에 싣는다.
- **완료 기준**: 목록에 없던 서버 멤버가 멘션하면 답이 온다. 차단은 여전히 된다. `/help` 의 공용 기계
  고지는 그대로 나간다.
- **배제한 대안**: (a) 안내문으로 "등록을 요청하세요" 를 내는 것 — 관문을 설명하는 것이지 없애는 것이
  아니다. (b) 서버 역할(Discord role)로 거르는 것 — 관리 축이 하나 더 생기고, 운영자가 원한 것은 "서버에
  있으면 된다" 다.
- **결정 필요**(§5): 길드 ID 고정을 같이 넣을지.

### 3.2 시키는 중 — 보이는가, 멈출 수 있는가

**N1 · 작업 과정 가시화 — 진행 표시 2.0** (축 A, 운영자 1순위)

- **문제**: 진행 표시가 내보내는 줄은 세 종류뿐이다 — `도구 호출(이름+입력 요약)`, `도구 결과(성패·요약·소요)`,
  `답변 작성 중`(`agent/src/core/sdkEvents.ts` 의 `progressFromMessage`). 모델이 도구 사이에서 하는 말 —
  무엇을 보았고 그래서 무엇을 하기로 했는지 — 는 `text` 블록이 통째로 `answering` 한 종류로 접혀
  **한 줄도 나가지 않는다.** 상태 메시지는 "처리 중" 아래 최근 12줄만 보이고(`PROGRESS_DISPLAY_MAX_LINES`),
  턴이 끝나면 `finishStatus` 가 **메시지를 삭제**한다(`agent/src/adapters/discord.ts`). 하네스 경로도 같은
  매퍼를 쓴다(`agent/src/remote/sessionRunner.ts` 가 `turn.event` 로 같은 모양을 보낸다). 즉 127스텝짜리
  턴(§2.4)에서 사용자가 본 것은 흐르는 12줄이었고, 끝난 뒤에는 ✅ 반응과 최종 답만 남았다.
- **방향**: (a) 도구 호출 사이의 모델 텍스트를 "판단" 줄로 내보낸다(길이 상한, 첫 문장). (b) 턴이 끝나도
  기록을 지우지 않는다 — 요약 한 줄 + 펼침(스포일러 또는 답변 아래 접힌 블록)으로 남긴다. 디스코드
  2000자 한도는 어댑터가 이미 다루는 제약이다. (c) 헤더에 "N번째 단계 · 경과 M분". 편집 폭주 방지의
  800ms 스로틀은 유지한다.
- **완료 기준**: 2분 넘는 턴에서 "지금 뭐 해?"를 묻지 않아도 현재 단계와 이유를 읽을 수 있고, 끝난 뒤에도
  무엇을 했는지 남는다.
- **배제한 대안**: 스트리밍 답변(토큰 단위 편집) — 디스코드 편집 속도 제한과 정면으로 부딪히고, 원한
  것은 "판단이 보이는 것"이지 글자가 흐르는 것이 아니다.

**N2 · 작업 제어 — `/취소` + 턴 도중 메시지 규칙** (축 A)

- **문제**: 진행 중인 턴을 사용자가 멈출 수단이 없다. 프로토콜에는 `turn.cancel` 이 있고 허브가 러너에
  보낼 수 있지만(`agent/src/remote/hub.ts` 의 `startTurn(...).cancel()`), 그것을 부르는 명령이 없다.
  봇 자기 세션 턴(부원 경로)은 취소 경로 자체가 없다. 턴 도중 보낸 메시지는 대화별 체인(`turnChains`)에
  줄을 서서 **다음 턴**이 될 뿐, 진행 중인 작업에 닿지 않는다 — 사용자는 그 사실을 알 수 없다.
- **방향**: 예약어 `/취소`(별칭 `/중지`·`/stop`) — 하네스 턴은 `turn.cancel`, 봇 자기 세션 턴은 SDK 의
  중단으로 잇는다. 취소 뒤 "어디까지 했는지" 한 줄을 남기고, 세션은 이어받을 수 있게 한다(PR #112 의
  실패 턴 세션 보존과 맞물린다). 턴 도중 온 메시지에는 "끝나면 이어서 처리합니다"를 진행 표시에 알린다.
- **완료 기준**: `/취소` 를 치면 몇 초 안에 멈추고 어디까지 했는지 남으며, 다음 턴이 그 자리에서 이어진다.
- **배제한 대안**: 턴 도중 메시지를 진행 중인 세션에 **끼워 넣기**(조향) — SDK 세션 한 턴 안에 사용자
  입력을 주입하는 경로가 없고, 있더라도 "무엇이 반영됐는지"가 보이지 않으면 N1 을 먼저 해야 한다.

**N0 · 측정 복구 — `llm_usage` 0행 진단** (가로축)

- **문제**: §2.6. 이 로드맵의 모든 판단이 `actions` 에 기대는데, 하네스 턴의 모델 호출 수·토큰은 기록이
  없다. N1 의 완료 기준("긴 턴")을 재는 자와 5단계 상한의 전제가 비어 있다.
- **완료 기준**: 소유자 하네스 턴 하나가 `llm_usage` 에 행을 남긴다. 원인이 프록시 우회면 그 자체가
  위험 등록부 항목이다(세션 계정에 자격증명이 있다는 뜻이므로).

### 3.3 끝난 뒤 — 결과를 읽을 수 있는가

**N4 · `sh_exec` 한글 깨짐** (축 A — 실제로는 부원)

- **문제**: §2.5 — 부원 셸 호출 여섯 중 하나가 깨진 채 모델에게 간다. 실패의 원인은 멀쩡한데 설명만
  깨져 오진을 부른다(온보딩 2절이 "진단 중 깨진 문자열을 보면 이 문제부터 의심해라"고 적을 정도다).
  [셸 사용성 설계](./2026-07-31-shell-ux-design.md) §2 가 "의존성 필요"로 범위 밖에 뒀던 것인데, 그때는
  빈도를 몰랐다.
- **방향**: 워커가 자식 프로세스의 코드페이지를 검출해(`chcp`) cp949 면 그에 맞게 디코드하거나, 명령을
  UTF-8 출력으로 강제한다. 라이브러리(`iconv-lite` 등)를 들이면 AGENTS.md 의 "라이브러리 추가는 팀 논의"에
  걸린다 — §5 결정 3.
- **완료 기준**: 윈도우 내장 명령의 한국어 메시지가 그대로 읽힌다. 30일 뒤 §2.5 의 비율이 0 에 가깝다.

**X1 · 편집 도구 헛돎 줄이기** (축 A/B)

- **문제**: §2.3 — `fs_edit` 10%, 하네스 `Edit` 7%. 전자는 모델이 재현한 원문이 파일과 다를 때(공백·
  줄바꿈·마크다운 변형)이고, 후자는 Claude Code 의 "읽지 않고 편집" 가드다.
- **방향**: `fs_edit` 은 공백·줄바꿈 관용 매칭 + 실패 시 근접 후보 줄을 돌려줘 재읽기 없이 고치게.
  `Edit` 은 가드 자체는 옳으므로 하네스 안내문에 "편집 전 읽기" 한 줄만.
- **완료 기준**: 30일 뒤 두 지표가 절반 이하.

**X4 · 마크다운이 경로·명령을 깨뜨리는 문제** (축 A)

- **문제**: 디스코드 마크다운이 백슬래시와 별표를 먹어 경로·glob 이 원문과 달라진다(온보딩 7절 실측).
- **방향**: 출력 쪽은 어댑터가 경로·명령·glob 을 코드 스팬으로 감싸는 **코드 규칙**(모델에게 부탁하는
  규칙이 아니라 — 모델 규칙은 지켜지지 않는 날이 있다). 입력 쪽은 안내.
- **완료 기준**: 경로가 든 답을 복사해 붙여도 원문과 같다.

**X2 · `proc_list` 즉답화** (축 B)

- **문제**: 평균 11.9초·최대 42.7초(§2.2). "뭐 돌고 있어?"는 7/31 분석에서 부원 호출의 절반이었다.
- **방향**: PM2 조회 비용의 원인(`jlist` 의 프로세스 스캔)을 재고 캐시 또는 경량 조회로.
- **완료 기준**: 2초 안에 답.

**X3 · 작업 기록 되짚기 — "아까 뭐 했어?"** (축 A)

- **문제**: 로드맵 옛 Next 5(`actions` 자기조회)는 "소유자의 자기 진단"으로 좁혀 있었다. 사용자 관점으로
  다시 쓰면 N1 이 남기는 접힌 기록의 **사후 조회판**이다 — 물으면 그 대화의 최근 작업을 `actions` 로
  요약해 답한다. ADR 0010 의 축(DB 읽기는 부원 전원)에 맞춰 부원도 쓴다.
- **완료 기준**: 대화 안에서 "아까 뭐 했어?"에 도구 호출 순서·결과·소요가 나온다.

### 3.4 부원의 첫 방문 — 경로와 검증

**X5 · 부원 경로 스모크 소진** (축 B)

- **문제**: [스모크 테스트](../../../deploy/smoke-test.md)는 103건이 미검증이다. 그중 **부원이 매일 타는
  경로**만 고른다 — 파일 올리기·`send_file` e2e(부원이 30일에 12회 썼는데 항목은 비어 있다), 워커 최종
  게이트 `checkPath`, PM2 재부팅 생존. 나머지 스모크는 이 로드맵 밖이다.
- **완료 기준**: 그 항목들에 [x] 와 실측 기록.

**X6 · 5단계 결정 — 부원을 하네스로 옮길 것인가** (축 B)

- **왜 결정 항목인가**: [풀 하네스 설계](./2026-09-05-full-harness-worker-design.md) §11 은 5단계를 "다음"
  으로 적었지만, 그것은 부원이 아직 쓰지 않던 때의 순서다. 지금 부원 마찰의 상당수(N4·X1 의 `fs_edit`)는
  **얇은 워커 경로 고유**라 하네스로 옮기면 사라진다 — 하네스의 `Bash` 는 깨짐 1%, `Edit` 은 다른 종류의
  실패다. 그러나 선행 조건이 무겁다: 동시 실행 상한·대기열(설계 §5), 손님 프로필(Sonnet 5·서브에이전트
  끔), 공유 브라우저, `llm_usage` 복구(N0)와 창 상한 튜닝, 손님 안내문 정정(`persona.ts` 의 `guestPcLine`).
  로드맵은 **결정만** 요구한다. 구현은 기존 설계·계획 문서로 간다.
- **완료 기준**: 한다/안 한다/보류 + 시점의 기록.

**X7 · `list_repos` 권한 오류** (축 A)

- **문제**: 소유자 2건 "The permissions requested are not granted to this installation" — GitHub App 설치
  권한과 토큰 요청 스코프의 불일치. 작지만 표준 절차 1단계(저장소 확인)를 막는다.
- **완료 기준**: 오류 0, 스모크 항목 [x].

## 5. 운영자 결정 필요

1. **N3 의 형태** — (a) 서버 멤버 자동 등록 + `blocked` 유지 / (b) 여기에 **길드 ID 고정**(`DISCORD_GUILD_ID`
   같은 허용 목록) 추가. 권고 (b): 봇 초대 범위가 곧 신뢰 경계가 되므로, 봇이 다른 서버에 초대되는 경로를
   코드로 닫아 두는 편이 싸다. 결정과 함께 ADR 을 쓴다.
2. **X6** — 부원 하네스 이전: 한다 / 안 한다 / 보류, 시점.

## 7. 이 문서가 아닌 것

- 구현 스펙이 아니다 — 항목마다 착수 때 브레인스토밍 → 스펙 → 계획을 따로 쓴다.
- [STATUS.md](../../status/STATUS.md) 를 갱신하지 않았다. 이 조회가 드러낸 사실 중 STATUS 에 반영할 것
  (부원 실사용 수치, `llm_usage` 0행)은 각 항목의 착수 커밋이 옮긴다.
- 조회한 SQL 은 집계뿐이고 저장하지 않았다 — 재현은 §2 의 서술(창·표·조건)로 충분하다. `actions` 의
  `status` 의미가 2026-07-31 워커 갱신 뒤 바뀐 것(온보딩 8절)은 이 창(08-23 이후)에 영향이 없다.
