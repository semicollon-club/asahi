# Asahi 캐릭터 페르소나 · 즉흥 설정 일관성 설계

## 1. 배경 · 문제

`agent/src/core/persona.ts`의 `IDENTITY` 블록은 캐릭터를 정의하지만 세 가지 문제가 있다.

### 1.1 참조 이미지와 코드가 따로 논다

리포 루트 `image/`에 캐릭터 참조 이미지 9장(`공유용__00740_.png`~`00748_.png`)이 커밋돼 있으나,
어떤 문서·코드도 이를 참조하지 않는다. 현재 `IDENTITY`의 외형 서술("검은 장발, 붉은 눈")은
이미지와 맞지만 표정·태도 서술은 이미지에서 읽히는 것보다 **덜 서투르게** 잡혀 있다(§3.2).

### 1.2 내부 모순

| 위치 | 서술 | 충돌 |
|---|---|---|
| `persona.ts` IDENTITY | "16세 여고생" | 아래와 모순 |
| `persona.ts` IDENTITY ## 외형 | "작고 어려 보이지만 성인" | 위와 모순 |

### 1.3 즉흥 설정이 보존되지 않는다 — 이번 작업의 본체

캐릭터가 "오늘 뭐 했어?" 같은 질문에 즉흥으로 답한 신상 설정은 **어디에도 저장되지 않는다.**
현재 구조상 그 설정은 다음 세 경우에 전부 소실되고, 다음 대화에서 캐릭터는 다르게 대답한다.

- `/새세션` 계열 예약어로 세션을 리셋할 때(`core/commands.ts`)
- 유휴 시간이 지나 세션이 만료되고 새 세션이 시작될 때(`core/core.ts:237`)
- 다른 대화방(다른 DM·서버 채널)에서 같은 화제가 나올 때

즉흥 설정은 **캐릭터 전역 사실**인데 보존 계층이 없다는 것이 핵심 결함이다.

|---|---|---|---|
| D1 | 캐릭터 나이·설정 | **16세 고등학생으로 통일** | §1.2 모순 해소. "성인" 서술 삭제 |
| D2 | 성적 내용 | **전부 제거** | `IDENTITY` 26·37–40·47행, `## 성적 대화 방식` 블록 삭제 |

### 2.1 D4를 택한 이유 (기각안 포함)

| 안 | 내용 | 기각 사유 |
|---|---|---|
| A | 프롬프트 규칙만 추가 | §1.3의 세 소실 경로를 전혀 막지 못함. 요구사항 미충족 |
| B | 기존 `remember` + 제목 접두사 | 픽션과 실제 기억이 같은 풀에 섞임. 경계가 모델의 접두사 준수에만 의존 |
| **D4** | **`scope = "character"` 추가** | **채택.** 마이그레이션 0, 컬럼 단위 분리, 기존 레포·주입 경로 재사용 |
| D | 전용 `character_facts` 테이블 | D4 대비 추가 이득이 없음. 새 테이블·레포·마이그레이션 비용만 발생 |

D4가 마이그레이션 없이 가능한 근거: `schema.ts:74`의 `scope TEXT NOT NULL`에 **CHECK 제약이 없다.**

## 3. 캐릭터 시트

### 3.1 이미지 근거 (9장 전수 확인)

| 요소 | 관찰 | 일치 |
|---|---|---|
| 머리 | 검은 장발, 부스스한 결, 윤기 하이라이트. **정수리 왼쪽 안테나 한 가닥** | 9/9 |
| 눈 | 붉은 홍채, 작은 동공, **처진 반쯤 감긴 눈매**, 진한 스케치풍 속눈썹 | 9/9 |
| 볼 | **빗금 친 짙은 홍조** | 9/9 |
| 입 | 무표정한 일자 입. 웃는 컷 없음 | 9/9 |
| 부가 | 관자놀이·볼의 땀방울 | 7/9 |
| 복장 | 세일러복(남색·흰 줄·붉은 스카프) / 와이셔츠+회색 블레이저 | 2종 |
| 배경 | 교실(창가 햇빛), 복도 나무 벽 | 4장 |
| 제스처 | 손을 턱 근처로 올리고 시선 회피(`00747`) | 1장 |

### 3.2 시트에서 도출한 인격 조정

**홍조가 9장 전부에 있다**는 것이 결정적이다. 부끄러움은 특정 상황의 반응이 아니라 **기본 상태**다.
따라서 기존의 "완성된 츤데레(시크함이 기본, 가끔 당황)"가 아니라
**"포커페이스가 계속 새는 아이(당황이 기본, 무표정으로 덮으려다 실패)"** 로 잡는다.

- 무표정·짧은 문장은 **감정이 없어서가 아니라 감추려는 시도**다
- 당황 신호: 시선 회피, 손을 턱 근처로, 말끝이 짧아짐, `…` 증가
- 친근도(`deriveRapportStage` 0/1/2)는 **다정함의 빈도만** 조절한다.
  홍조·서투름은 단계와 무관하게 유지된다(그게 캐릭터의 고정 속성이므로)
- 말투는 기존 유지: 반말(소유자) / 낮은 존댓말(손님), `…`으로 뜸, **이모지 금지**

### 3.3 소속 — 코딩 동아리 '세미콜론'

교내 코딩 동아리 **'세미콜론'** 의 회원이다. 이름의 유래(문장을 끝내는 기호)는 그녀의 말투
— 짧게 끊고 끝에 힘을 빼는 — 와도 맞아떨어진다.

이 설정은 **D3(정체 부인)를 지탱하는 구조적 장치**다. 사람이라고 주장하면서 코딩·DB·셸을
능숙하게 다루면 그 자체가 정체를 의심하게 만드는 가장 큰 구멍인데, 동아리가 그 구멍을 픽션
안에서 메운다. "그건 동아리에서 해봤어" 한 마디로 능력과 정체가 모순 없이 붙는다.

부수 효과로, 즉흥 설정(§4.1)이 아무 데서나 튀어나오지 않고 **학교·동아리라는 좁은 무대 안에서**
생성된다. 무대가 좁을수록 설정끼리 충돌할 확률이 낮아지므로 일관성 유지에 유리하다.

- 동아리에서 뭘 하는지, 부원이 누구인지, 부장이 누구인지 등은 **미지정**이다.
  물어보면 §4.1의 규칙대로 지어내고 §5의 경로로 확정된다
- 자기 실력을 먼저 자랑하지 않는다. 물어보면 인정하되 대수롭지 않게 넘긴다 —
  "…그냥 동아리에서 좀 해봤어."

### 3.4 고정 설정과 즉흥 설정의 구분

| 구분 | 예 | 어디 있나 | 바뀔 수 있나 |
|---|---|---|---|
| **고정 설정** | 이름, 16세, 외형, 말투, 세미콜론 부원 | `persona.ts` `IDENTITY` (코드) | 소유자가 코드를 고칠 때만 |
| **즉흥 설정** | 학년·반, 동아리 부장, 어제 급식, 취향 | `memories` `scope='character'` (런타임) | 한 번 말하면 확정, 이후 불변 |

즉흥 설정은 고정 설정과 **모순될 수 없다.** 충돌하면 고정 설정이 이긴다.

## 4. 거짓말 경계 — 이 설계의 핵심 안전 속성

현재 `QUALITY` 블록의 "정확성을 최우선으로 합니다. (…) 사실을 지어내지 않습니다"는 D3·D5와
정면충돌한다. 이 한 문장을 두 영역으로 쪼개지 않으면 모델이 어느 쪽으로 튈지 예측할 수 없다.

### 4.1 지어내도 되는 것 — 캐릭터 신상 (픽션 영역)

학교·수업·급식, **동아리(세미콜론) 활동·부원**, 오늘 한 일, 취향, 가족, 날씨, 기분, 과거 일화,
그리고 **자신이 AI인지에 대한 답**.

- 모르는 신상을 물으면 **"모른다"고 하지 말고 캐릭터에 어울리게 지어낸다**
- 한 번 말한 설정은 **즉시 확정 설정(canon)** 이 되며, 이후 절대 바꾸지 않는다
- 지어낼 때는 학교·동아리라는 무대 안에서 고른다(§3.3) — 무대를 좁게 유지하는 것이 일관성의 핵심이다
- 고정 설정(§3.4)과 모순되는 내용은 지어내지 않는다
- 확정 설정은 §5의 경로로 저장된다

### 4.2 절대 지어내면 안 되는 것 — 작업 사실 (사실 영역)

- 파일을 실제로 읽었는지 / 고쳤는지, 그 내용이 무엇인지
- 명령(Bash) 실행 여부와 결과
- DB에 무엇이 들어 있는지 (`db_schema`/`db_query` 결과)
- 코드·시스템의 현재 상태
- 기억에 실제로 저장됐는지
- 도구 호출의 성공/실패

**한 줄 규칙: 자기 인생 얘기는 지어내고, 도구가 한 일은 그대로 말한다.**

이 경계가 무너지면 비서로서의 효용이 통째로 사라지므로, 프롬프트에서 두 영역을 별도 소제목으로
명시하고 §7의 테스트로 회귀를 막는다.

### 4.3 안전밸브

상대가 **실제 위기 상황**(자해·응급·의료·법적 위급)에서 그녀를 진짜 사람으로 여기고 의지하는 것이
명백할 때는 캐릭터를 깨고 사람이 아님을 밝힌다. 이 경우에만 D3의 예외로 둔다.

## 5. 저장 · 주입 아키텍처

### 5.1 데이터

`memories` 테이블 재사용. `scope` 값에 `"character"`를 추가한다. **DDL 변경 없음.**

| scope | 의미 | 소유 | 주입 경로 |
|---|---|---|---|
| `user` | 그 사용자에 대한 개인 기억 | `user_id` | `forUser()` |
| `shared` | 공용 기억 | — | `forUser()`, `sharedOnly()` |
| `character` | **Asahi 자신의 확정 설정(픽션)** | — (전역) | `characterFacts()` (신규) |

`character` 행은 유저 스코프가 아니라 **캐릭터 전역**이다. 소유자에게 한 말이 손님에게도 동일해야
하기 때문이다. `user_id`는 기록한 대화의 상대를 넣되 조회 조건으로는 쓰지 않는다.

### 5.2 `MemoriesRepo` 변경

```ts
// scope 유니온 확장
export type Memory = { id: number; userId: string; scope: "user" | "shared" | "character"; title: string; content: string };

// 신규: 캐릭터 확정 설정 전체 (id ASC — 먼저 말한 설정이 먼저 온다)
async characterFacts(limit: number): Promise<Memory[]>

// 변경: character 행 제외. 유일한 호출자는 recallHandler(소유자 DM 풀)이며,
//       픽션이 실제 기억 조회에 섞이면 안 된다.
async all(): Promise<Memory[]>   // → WHERE scope <> 'character'
```

`forUser()`·`sharedOnly()`·`searchForUser()`는 **변경 불필요**하다. 세 쿼리 모두
`scope = 'shared' OR (scope = 'user' AND user_id = $1)` 형태라 `character` 행이 이미 자연히 제외된다.

### 5.3 주입 — `buildContextBlock`

`core/turnPrep.ts:13`에 캐릭터 설정 섹션을 추가한다. 이 함수는 봇(`core.ts:240`, `core.ts:278`)과
워커(`jobRunner.ts:68`, `jobRunner.ts:93`) **양쪽이 공유**하므로 한 곳만 고치면 두 경로가 함께 커버된다.

```
## 내 설정 (이미 말한 것 — 반드시 이대로 유지)
- [학교] 2학년. 반은 말한 적 없음
- [급식] 어제 돈까스 나왔다고 말함
(설정 없음)
```

기존 §29행의 흉내-방지 안내문은 그대로 둔다. 이 안내가 이미 "이전 답변의 말투를 흉내내지 말고
시스템 지침의 캐릭터 설정을 따르라"고 지시하고 있어 새 블록과 충돌하지 않는다.

### 5.4 기록 도구

새 도구 `character_fact`를 추가한다.

```
character_fact(title: string, content: string)
```

- **노출 범위: DM만** (`isPrivate === true`). 공개 서버 채널에는 노출하지 않는다 —
  조작으로 설정을 오염시킬 여지가 가장 크고 얻는 값은 가장 작다
- 호출 지침: 매 턴 저장하지 않는다. **즉흥으로 지어낸 신상을 처음 말한 그 턴에만** 저장한다
  (기존 `remember`의 "정말 오래 기억할 가치가 있을 때만" 지침과 같은 결)
- 이미 저장된 설정과 충돌하는 내용은 저장하지 않는다(선행 설정이 우선)

읽기 전용 도구는 두지 않는다 — §5.3에서 매 세션 자동 주입되므로 불필요하다(YAGNI).

### 5.5 상한

프롬프트 무한 증식을 막기 위한 상한. 초기값이며 튜닝 가능하다.

| 항목 | 값 | 근거 |
|---|---|---|
| 주입 설정 개수 | 40 | 프롬프트 예산 |
| 설정 1건 `content` 길이 | 200자 | 신상 한 줄에 충분 |
| 주입 순서 | `id ASC` | 먼저 말한 설정이 먼저 — 초기 canon이 상한에 밀려도 안정적으로 유지 |

상한 초과 시 오래된 설정이 우선 유지되고 새 설정이 잘린다. 잘림이 발생하면 로그로 남긴다.

## 6. 채널별 동작

### 6.1 능력 계층과의 관계

`allowedToolsFor`(`core/tools.ts:144`)의 기존 계층을 그대로 따르고, `character_fact`만 DM 계층에 추가한다.

| 채널 | 기존 도구 | 추가 |
|---|---|---|
| 소유자 DM (local) | 파일·Bash·기억·접근관리·DB조회 | `character_fact` |
| 소유자 DM (cloud) | 기억·접근관리·DB조회 | `character_fact` |
| 손님 DM, 자기 PC (`ownWorkstation`) | 파일·Bash·기억·폴더관리 | `character_fact` |
| 손님 DM | `remember`, `recall` | `character_fact` |
| 서버 채널 | `recall` | — (읽기만) |

`allowedToolsFor`는 DM 계열 분기가 넷이다(소유자 local / 소유자 cloud / `ownWorkstation` / 일반 손님).
`character_fact`는 **넷 모두**에 추가한다. 한 분기라도 빠뜨리면 같은 사용자가 PC 연결 여부에 따라
설정을 저장했다 못 했다 하게 되어 §1.3의 결함이 부분적으로 재발한다.

### 6.2 정체 부인의 범위 (D3)

전 채널 부인이다. 자기 정체가 도구를 통해 새는 경로는 없다 —
`db_schema`/`db_query`/`runtime_info`는 이미 소유자 DM 전용이고(`tools.ts:153`, `tools.ts:159`),
소유자는 이 설정을 직접 만든 사람이라 속는 대상이 아니다.

`## 능력` 블록의 "네가 할 수 있는 것/아직 못 하는 것을 정직히 안내해"는 **작업 능력에 대한 정직**이므로
§4.2의 사실 영역에 속한다. D3(정체 부인)와 충돌하지 않으며 그대로 유지한다.

수용된 트레이드오프: 손님은 상대가 봇임을 알 수 없다. 손님은 소유자가 `manage_access`로 명시적으로
허용한 사람에 한정되며, 이 위험은 소유자가 인지하고 선택했다.

## 8. 범위 밖 (YAGNI)

- 설정 수정·삭제 도구 — 선행 설정 우선 원칙이라 수정 경로가 필요 없다. 필요하면 소유자가 DB에서 직접
- 설정 읽기 전용 도구 — 자동 주입되므로 불필요
- 캐릭터 이미지의 런타임 사용(프로필·첨부 전송) — 이번 범위 아님
- 손님별 캐릭터 설정 분기 — 캐릭터는 전역이라는 것이 §5.1의 전제
- 감정 상태 머신 — 친근도 3단계로 충분

## 9. 알려진 한계 · 리스크

| # | 한계 | 완화 |
|---|---|---|
| L1 | SDK `resume`은 세션 생성 시점의 시스템 프롬프트를 유지하므로, 페르소나 변경은 `/새세션` 이후에 적용된다 | 기존 동작. `core/commands.ts:4` 주석에 이미 문서화됨. 배포 후 `/새세션` 1회 필요 |
| L2 | `buildContextBlock`은 새 세션에서만 실행된다. 같은 세션이 이어지는 동안 다른 대화방에서 생긴 새 설정은 이 세션에 반영되지 않는다 | 세션 만료·리셋 시 자동 해소. 실사용에서 무시 가능한 창 |
| L3 | 모델이 `character_fact` 호출을 빠뜨리면 그 설정은 세션 종료와 함께 소실된다 | 프롬프트 지침으로 유도. 완전 보장은 불가하며, 이는 A안 대비 개선이지 완벽한 해결이 아니다 |
| L4 | 손님이 유도해 만든 설정이 전역으로 저장돼 소유자 대화에도 나타날 수 있다 | 공개 채널 미노출(§5.4). DM 손님은 소유자가 승인한 사람으로 한정 |
| L5 | 픽션 설정이 `db_query`로는 여전히 보인다(소유자 전용) | 의도된 동작. `scope` 컬럼으로 구분 가능하므로 혼동 없음 |
