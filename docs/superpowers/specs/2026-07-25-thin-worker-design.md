# 얇은 워커 — 판단은 Railway, 실행만 워커 (1단계)

## 1. 배경 · 문제

### 1.1 지금 워커는 명령 실행기가 아니라 두 번째 에이전트다

이름은 "워커"지만 실제로는 봇과 동등한 두 번째 두뇌다. `agent/src/worker/jobRunner.ts`가 하는 일:

| 단계 | 코드 | 하는 일 |
|---|---|---|
| 큐잉 | `core.ts` `delegateToWorker` | 명령어가 아니라 **사용자 메시지 원문**을 `worker_jobs` 에 넣는다 |
| 컨텍스트 | `jobRunner.ts:68` | 워커가 `buildContextBlock` 으로 DB에서 대화 이력·요약·기억을 직접 읽는다 |
| 페르소나 | `jobRunner.ts:78` | 워커가 `buildSystemPrompt` 로 시스템 프롬프트를 직접 조립한다 |
| 추론 | `jobRunner.ts:87` | 워커가 `runTurn` → SDK `query()` 를 직접 호출한다. **모델 호출이 워커에서 일어난다** |
| 기록 | `jobRunner.ts:109` | 워커가 `messages` 테이블에 직접 쓴다 |

Railway 봇은 위임을 결정한 뒤 손을 떼고, job 결과만 폴링해 디스코드로 흘려보낸다.

### 1.2 그래서 워커에 자격증명 두 개가 필요하다

- **`DATABASE_URL`** — 대화·기억·요약을 읽고 쓰기 위해. Supabase 전체 접근권이다.
- **`CLAUDE_CODE_OAUTH_TOKEN`** — SDK `query()` 를 호출하기 위해. 소유자의 Claude 구독 자격증명이다.

이게 다중 워커를 막는 결정적 장벽이다. 동아리원에게 워커를 돌리게 하려면 이 둘을 건네야 하는데,
`DATABASE_URL` 만으로도 워커 사칭이 가능하다는 건 이미 문서화돼 있다
([worker-셋업.md](../../../deploy/worker-셋업.md) "보안" 절, [risk-register.md](../../security/risk-register.md)).

### 1.3 세션이 두 기계에 쪼개져 있다

위임된 대화의 SDK 세션은 워커 PC에 있어 봇이 resume 할 수 없다 — `core.ts` 에 리뷰 #4(MED)로
주석이 남아 있는 알려진 문제다. 두뇌가 하나가 되면 이 문제는 성립 자체를 하지 않는다.

## 2. 목표 · 비목표

**목표:** 워커에서 SDK와 DB를 걷어내고, Railway 봇이 턴 전체를 붙든 채 파일·셸 작업만 워커로
원격 호출하게 만든다.

**이 단계에서 사용자가 체감하는 기능 변화는 없다.** 소유자 DM에서 PC 작업을 요청하면 지금과
똑같이 동작해야 한다. 그게 이 단계의 완료 기준이다.

**비목표(2단계):** 워커 토큰 발급, 사용자별 워커 라우팅, 공개 서버용 공유 워크스페이스,
공유 워커 직렬화. 1단계가 끝난 뒤 별도 스펙으로 진행한다.

## 3. 확정된 결정

| # | 결정 | 선택 | 근거 |
|---|---|---|---|
| D1 | 두뇌 위치 | **Railway 단독** | 워커에서 모델 호출 제거 → Claude 토큰 불필요 |
| D2 | 워커의 DB 접근 | **완전 제거** | `DATABASE_URL` 불필요 → 2단계의 전제 |
| D3 | 전송 | **WebSocket, 워커가 아웃바운드로 연결** | 워커는 NAT 뒤라 인바운드 불가. 턴당 도구 호출이 수십 번이라 폴링 지연이 누적된다 |
| D4 | 도구 입도 | **도구별 원격 MCP 도구** (`remote_exec` 단일 도구 아님) | 어떤 경로를 건드리는지 구조적으로 알 수 있어야 경로 게이팅이 의미를 유지한다 |
| D5 | 경로 검사 최종 권한 | **워커** | realpath·심볼릭 링크·존재 여부를 아는 건 워커뿐이다. Railway는 1차 필터 |
| D6 | `worker_jobs` 기계장치 | **사용 중단** | 비동기 2차 에이전트 모델의 산물이라 존재 이유가 사라진다(§7) |
| D7 | 워커 온라인 판정 | **살아있는 WS 연결** | DB 하트비트 대신. 더 정확하고 DB 접근이 필요 없다 |

### 3.1 기각한 전송 방식

| 안 | 기각 사유 |
|---|---|
| HTTP 롱폴링 | 에이전트 턴 하나에 도구 호출이 수십 번 일어난다. 파일 하나 읽을 때마다 폴링 주기만큼 기다리는 체감이 된다 |
| DB를 우편함으로 쓰되 권한만 제한 | 없애려던 DB 의존을 축소된 형태로 도로 들인다. 도구 호출마다 DB 왕복도 추가된다 |

## 4. 아키텍처

### 4.1 현재

```
디스코드 ──▶ Railway 봇 ──[사용자 메시지 원문]──▶ worker_jobs ──▶ 워커
                 │                                    ▲             │
                 └────────── Supabase ────────────────┴─────────────┘
                                        워커가 직접 읽고 쓴다
```

워커 보유 자격증명: `DATABASE_URL`, `CLAUDE_CODE_OAUTH_TOKEN`

### 4.2 제안

```
디스코드 ──▶ Railway 봇 (유일한 SDK)
                 │  ▲
                 │  └── Supabase (Railway만 접근)
                 │
                 └──[도구 호출 하나]──▶ 워커 (실행만)
                    ◀──[결과]─────────
```

워커 보유 자격증명: `WORKER_TOKEN` 하나

### 4.3 턴 하나의 흐름

1. 디스코드 메시지 → `AgentCore.ingest` (기존 그대로)
2. 봇이 `buildSystemPrompt` + `buildContextBlock` 으로 프롬프트 구성 (기존 그대로)
3. 봇이 `runTurn` → SDK `query()` 실행 (기존 그대로)
4. 모델이 파일·셸 도구를 호출하면, 그 도구가 WS로 워커에 요청을 보내고 결과를 기다린다 **(신규)**
5. 진행 표시는 SDK의 `onProgress` 를 그대로 쓴다 — 위임 전용 진행 경로가 없어진다
6. 턴이 끝나면 봇이 `messages` 에 기록하고 디스코드로 발행 (기존 그대로)

위임이라는 개념 자체가 사라진다. 모든 턴이 봇에서 실행되고, 일부 도구만 원격일 뿐이다.

## 5. 전송 계층

### 5.1 연결

Railway 봇 프로세스에 HTTP 서버를 추가하고 `/worker` 경로에서 WebSocket 업그레이드를 받는다.
**이것이 이 단계에서 새로 생기는 유일한 외부 표면이다.** 지금 봇은 디스코드 클라이언트일 뿐
HTTP 서버가 없다.

워커가 아웃바운드로 접속한다. 워커 쪽에는 열린 포트가 없다.

### 5.2 인증

워커는 접속 직후 `hello` 프레임으로 `workerToken` 과 자신이 담당하는 `userId` 를 보낸다.
Railway는 토큰을 검증하고, 실패하면 즉시 연결을 끊는다.

1단계에서는 토큰이 **환경변수 하나**(`WORKER_TOKEN`)로 양쪽에 설정된 고정값이다. 발급·회전·
사용자별 토큰은 2단계 몫이다(§10 비목표).

`hello` 의 `userId` 는 1단계에서 선언적 값이다 — 토큰이 하나뿐이라 신원을 구분하지 못한다.
봇은 이 값이 `DISCORD_OWNER_ID` 와 일치하는지 확인하고, 다르면 연결을 거부한다. 사용자별
토큰이 생기는 2단계에 가서야 이 필드가 실제 의미를 갖는다.

### 5.3 프레임

| 방향 | 타입 | 페이로드 |
|---|---|---|
| 워커→봇 | `hello` | `{ token, userId, roots: string[] }` |
| 봇→워커 | `ready` \| `denied` | `{}` \| `{ reason }` |
| 봇→워커 | `call` | `{ id, tool, args }` |
| 워커→봇 | `result` | `{ id, ok, content }` |
| 양방향 | `ping` / `pong` | `{}` |

`roots` 는 워커가 노출을 허용하는 디렉토리 목록이다(§6.3). 봇은 이걸 1차 필터와 사용자 안내에
쓴다.

### 5.4 재연결 · 타임아웃

- 워커는 연결이 끊기면 지수 백오프로 재접속한다.
- 봇은 `call` 마다 타임아웃을 둔다. 기본 120초, `Bash` 계열은 별도 상한.
- 타임아웃되면 그 도구 호출만 실패로 모델에 돌려준다. 턴 전체를 죽이지 않는다 — 모델이
  실패를 보고 다른 방법을 시도하거나 사용자에게 알릴 수 있다.
- 턴 도중 연결이 끊기면 진행 중인 모든 `call` 을 실패로 정리한다.

## 6. 원격 도구

### 6.1 도구 목록

기존 SDK 내장 6개를 대체하는 인프로세스 MCP 도구를 만든다. 이름은 기존 도구와 구분되게 짓는다.

| 도구 | 대체 대상 | 인자 |
|---|---|---|
| `fs_read` | `Read` | `path`, `offset?`, `limit?` |
| `fs_write` | `Write` | `path`, `content` |
| `fs_edit` | `Edit` | `path`, `oldString`, `newString`, `replaceAll?` |
| `fs_glob` | `Glob` | `pattern`, `path?` |
| `fs_grep` | `Grep` | `pattern`, `path?`, `glob?` |
| `sh_exec` | `Bash` | `command`, `timeoutMs?` |

### 6.2 SDK 내장 도구 대비 손실 — 인지하고 수용한다

내장 `Read`/`Edit` 는 부분 읽기·줄번호·정확한 문자열 치환 검증 같은 동작이 잘 다듬어져 있다.
원격 구현은 그만큼 정교하지 않다. 1단계에서는 위 표의 인자 수준으로 충분히 동작하는 것을
목표로 하고, 부족한 점은 실사용에서 드러나는 대로 보완한다.

이건 이 설계의 실질적인 비용이며, 다른 방법이 없다 — Railway 컨테이너의 파일시스템과 워커의
파일시스템은 다른 기계이므로 내장 도구를 그대로 쓸 수 없다.

### 6.3 경로 검사 — 두 겹

**워커 쪽(최종 권한).** 워커는 `WORKER_ROOTS` 환경변수로 자신이 노출할 디렉토리를 고정한다.
모든 `fs_*` 호출은 realpath 정규화 후 이 루트 안인지 검사하고, 벗어나면 거부한다. 기존
`pathPermission.ts` 의 `resolveRealOrNearestAncestor`·`isPathWithinAny` 를 그대로 재사용한다.

**봇 쪽(1차 필터).** 기존 `allowed_dirs` 테이블과 `allow_dir`/`revoke_dir`/`list_dirs` 도구는
그대로 둔다. 사용자가 대화 중 관리하는 편의 계층이다. 봇은 호출 전에 이 목록으로 한 번 거른다.

경로는 **양쪽을 모두 통과해야** 한다. 봇 쪽 목록이 틀려도 워커가 막고, 워커 루트가 넓어도 봇이
좁힌다.

`sh_exec` 는 경로 검사가 성립하지 않는다(기존 `Bash` 와 동일한 한계). 워커 루트를 작업
디렉토리로 삼되, 그 밖으로 나가는 걸 기술적으로 막지는 못한다 — 이 한계는 2단계의 컨테이너
격리로 다룬다.

## 7. 삭제되는 것

`worker_jobs` 기계장치는 "워커가 비동기로 대화 턴을 통째로 처리한다"는 모델의 산물이다. 그
모델이 사라지면 전부 존재 이유가 없어진다.

| 대상 | 위치 |
|---|---|
| `delegateToWorker` | `core.ts` |
| `deliverPendingJobResults` + 유휴 타이머의 그 호출 | `core.ts`, `index.ts` |
| job 진행 폴링 → `progress` 이벤트 변환 | `core.ts` |
| 위임 타임아웃 후 지연 배달 · `markDelivered` 경합 처리 | `core.ts`, `jobsRepo.ts` |
| `processJob` 전체 | `worker/jobRunner.ts` (파일 삭제) |
| 워커의 폴링 루프 · 하트비트 · `failStaleRunning` | `worker.ts` |
| 워커의 모든 레포 조립 · `openDb` · `makeRunAgentTurn` | `worker.ts` |
| `JobsRepo` 대부분 | `jobsRepo.ts` |

`worker_jobs` **테이블 자체는 남긴다.** DDL 변경은 하지 않는다 — 쓰지 않는 테이블이 남는
비용보다 마이그레이션 위험이 크다. 미사용임을 `schema.ts` 주석에 명시한다.

이 삭제가 이 단계의 순 코드량을 줄인다. 새로 쓰는 전송·원격도구 코드보다 지워지는 쪽이 크다.

## 8. 능력 계층에의 영향

### 8.1 `ownWorkstation` 이 단순해진다

지금 `ownWorkstation` 은 "워커가 그 사용자 자신의 PC에서 이 턴을 실행 중이므로 손님이라도 파일·
Bash 전권"이라는 개념이다. 실행 위치가 능력을 좌우하는 구조라 판정이 두 군데로 갈려 있다
(`allowedToolsFor` 와 핸들러 내부 `canManagePc`).

새 구조에서는 실행이 항상 봇에서 일어나고 워커는 도구 하나를 대신 실행할 뿐이다. 능력 판정이
전부 `allowedToolsFor` 로 모이고, 워커는 자기 루트만 안다.

**1단계에서는 `ownWorkstation` 의 동작을 바꾸지 않는다.** 소유자 전용이라는 현재 정책도 그대로다.
개념 정리는 2단계에서 사용자별 워커를 도입할 때 함께 한다 — 지금 건드리면 "기능 변화 없음"이라는
완료 기준이 흐려진다.

### 8.2 원격 도구 노출은 연결 여부에 달린다

위임이 사라지므로 "워커 온라인" 판정은 **라우팅**이 아니라 **도구 노출**에 쓰인다.

- 그 사용자의 워커 연결이 살아 있으면 → `allowedToolsFor` 가 `fs_*`/`sh_exec` 를 포함한다
- 연결이 없으면 → 원격 도구를 아예 노출하지 않고, 능력 블록이 "PC 작업은 워커 연결 후 가능"
  이라고 안내한다

턴 시작 시점의 연결 상태로 판정한다. 턴 도중 끊기면 개별 도구 호출이 실패로 돌아온다(§5.4).

### 8.3 cloud 배포에서 PC 작업이 가능해진다 — 이 설계의 핵심 효과

지금 `deployTarget="cloud"` 는 owner DM이라도 파일·Bash 도구를 통째로 뺀다. Railway 컨테이너에는
소유자 PC가 없기 때문이다. 능력 블록의 안내 문구가 이미 이 상황을 예고하고 있다 —
"지금은 클라우드에서 실행 중이라 PC 파일·셸 작업은 할 수 없습니다. **로컬 워커가 연결되면 그때
PC 작업이 가능해집니다.**"

원격 도구는 정확히 그 문장을 실현한다. 판정 축이 "어디서 실행 중인가"에서 **"워커가 붙어
있는가"** 로 바뀐다.

| 조건 | 지금 | 이후 |
|---|---|---|
| cloud + 워커 연결됨 | PC 도구 없음 (위임으로 우회) | 원격 도구 열림 |
| cloud + 워커 없음 | PC 도구 없음 | 원격 도구 없음 (동일) |
| local + 워커 연결됨 | 내장 파일·Bash (봇 자신의 PC) | 원격 도구 열림 |

`agent.ts` 의 cloud 이중방어(`canUseTool` 이 경로 게이팅 대상 도구를 무조건 거부)는 원격 도구
이름에는 걸리지 않는다. 이중방어의 기준을 "cloud 인가"에서 **"워커 연결이 있는가"** 로 바꿔
같은 역할을 유지한다 — 연결이 없는데 원격 도구가 호출되면 즉시 거부한다.

### 8.4 `capability-model.md` 갱신

능력 계층표의 "열리는 도구" 열에서 파일 도구·Bash 항목이 원격 도구 이름으로 바뀐다. 경로 게이팅
절도 두 겹 구조를 반영해 다시 쓴다.

## 10. 범위 밖 (YAGNI)

- 워커 토큰 발급·회전·사용자별 토큰 (2단계)
- 사용자별 워커 라우팅, 공유 워크스페이스, 공유 워커 직렬화 (2단계)
- 워커 도커화 (2단계)
- 원격 도구를 SDK 내장 도구 수준으로 정교하게 만드는 것 (§6.2 — 실사용 후 보완)
- 여러 워커 동시 연결 (1단계는 소유자 워커 하나)
- 워커에서 이미지·멀티모달 처리 (현재도 위임 대상이 아니다)
