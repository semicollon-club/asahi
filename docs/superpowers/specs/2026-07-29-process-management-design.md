# 장기 실행 프로세스 관리 — PM2 위임

## 1. 배경 · 목표

부원이 미니PC에서 개발서버를 띄우려 하면 지금은 **구조적으로 불가능하다.** `sh_exec`
(`agent/src/remote/executors.ts`)는 `spawn` 후 `close` 이벤트까지 기다렸다가 결과를 한 번에
돌려주고, 기본 120초(`SH_DEFAULT_TIMEOUT_MS`)에 SIGTERM → SIGKILL 로 프로세스를 **죽인다.**
개발서버를 `sh_exec` 로 띄우면 2분 뒤 죽고, 그동안 출력도 보이지 않는다.

실사용에서 나온 통증은 그다음이다 — **무엇이 돌고 있는지 알 방법이 없다.** 지금은 사람이
기억해 뒀다가 모델에게 "아까 띄운 개발서버 꺼줘"라고 직접 지시해야 정리된다. 잊으면 그대로
남는다.

목표는 **장기 실행 프로세스를 시작·중지·조회·로그 확인할 수 있게 하고, 그것이 워커의 수명에
끌려다니지 않게 하는 것**이다.

**설계의 중심 결정: 감독자를 새로 만들지 않고 PM2 에 위임한다.** PM2 는 이미 이 프로젝트의
프로세스 감독자다(`deploy/ecosystem.config.cjs` 가 `asahi-assistant`·`asahi-worker` 를 정의하고,
`deploy/PM2-명령어.md` 가 있다). 감독·자동 재시작·로그 파일·상태 조회를 직접 만들면 그건 전부
PM2 가 이미 하는 일을 다시 만드는 것이다.

**Airflow 는 쓰지 않는다.** 원하는 것("여러 프로세스를 한눈에")은 맞지만 모양이 다르다 —
Airflow 는 배치 DAG 오케스트레이터로 태스크가 *끝나는 것*을 전제하고, UI 도 "이 실행이
성공했나"를 보는 화면이지 "이 서버가 지금 떠 있나"를 보는 화면이 아니다. 게다가 Python +
스케줄러 + 웹서버 + 메타DB 가 워크스페이스를 겸하는 미니PC에 얹힌다. `pm2 list` 가 정확히 그
"한눈에 보는 표"다.

## 2. 범위

**안**

1. 원격 도구 넷: `proc_start` · `proc_stop` · `proc_list` · `proc_logs`
2. 프로세스 이름·작업 폴더를 봇이 계산해 주입(모델이 정하지 않는다)
3. 1인 1프로세스 상한(이름 충돌로 표현)
4. `pm2 jlist` 파싱과 표 렌더링(순수 함수)
5. PM2 CLI 호출을 주입 가능한 이음매로 분리
6. `persona.ts`·`capability-model.md`·`smoke-test.md` 갱신
7. 미니PC 설치 절차와 주 1회 `pm2 flush`

**밖** — 각각 별도 과제다.

- **상시 실시간 표시**(디스코드 메시지가 아닌 곳에 살아 있는 상태를 계속 띄우기). 보여줄 상태가
  실제로 생긴 뒤에 설계해야 공중에 뜨지 않는다. 로드맵의 웹 UI(4단계)와 겹치므로 그쪽과 함께 본다.
- 폴더 트리를 박스 문자(`├──`·`└──`)로 그리기 — `renderTree` 출력 형식만 바꾸는 별개의 작은 일
- 자원 상한(메모리·CPU) — 윈도우에는 리눅스 cgroup 같은 수단이 없다
- 재부팅 후 프로세스 복원(§5 에서 일부러 하지 않기로 했다)

## 3. 도구 넷과 신원 주입

`REMOTE_TOOL_NAMES` 에 넷을 추가하고, 워커 실행기가 PM2 CLI 를 부른다.

| 도구 | 모델이 주는 인자 | 봇이 주입하는 것 | 실제 호출 |
|---|---|---|---|
| `proc_start` | `command` | `name`, `cwd` | `pm2 start <command> --name <name>` (cwd 지정) |
| `proc_stop` | (소유자만 `name`) | `name` | `pm2 delete <name>` |
| `proc_list` | — | 필터 기준 | `pm2 jlist` |
| `proc_logs` | `lines?` | `name` | `pm2 logs <name> --nostream --lines <n>` |

**핵심: 이름과 작업 폴더는 주입이지 검증이 아니다.** 모델이 `name` 을 넘길 수 있게 두면 부원 A 가
부원 B 의 프로세스를 죽이라고 시킬 수 있다. `fs_glob` 의 FIX1 에서 이미 겪은 구조다 — 검사한
값과 실제로 쓰이는 값이 다르면 검사 자체가 무의미해진다. 그래서 손님의 `name`·`cwd` 는 모델이
무엇을 주든 **덮어쓴다.**

`proc_start` 는 `sh_exec` 와 같은 등급의 권한이다(임의 명령 실행). 경로 인자가 없으므로 1차 경로
필터의 대상이 아니고, `ctx.remote` 존재만 확인한다 — `sh_exec` 와 정확히 같은 취급이다.

## 4. 1인 1프로세스

**이름이 곧 소유권이자 상한이다.** `asahi-<디스코드 userId>` 가 PM2 안에서 유일하므로, 같은
사람이 두 번째를 띄우려 하면 이름이 충돌한다.

**충돌하면 거절한다 — 조용히 교체하지 않는다.**

```
이미 돌고 있는 게 있어: asahi-1517…650 (npm run dev, 2시간 12분째)
먼저 멈춰야 새로 띄울 수 있어.
```

교체를 기본으로 두면 부원이 자기도 모르게 돌던 서버를 죽이게 된다. 바꾸고 싶으면 모델이
`proc_stop` → `proc_start` 를 부르면 되고, 그 편이 명시적이다.

**소유자는 예외다.** 서버 채널의 소유자는 그 기계의 관리자이므로 `proc_list` 에서 전원의
프로세스를 보고, `proc_stop` 에 이름을 지정해 남의 것도 정리할 수 있다. `scopeDirs` 가 소유자를
좁히지 않는 것과 같은 규칙이다.

## 5. 작업 폴더와 PM2 데몬 수명

**작업 폴더(cwd)**

- **손님**: `scopeDirs` 결과(`<루트>/<디스코드 userId>`)로 **무조건 덮어쓴다.**
- **소유자**: `cwd` 인자를 허용하되 1차 경로 필터를 태운다(`allowed_dirs` 밖은 거부). 생략하면
  `allowed[0]`.

**PM2 데몬**

첫 `pm2` 호출 때 자동으로 뜬다. 별도 기동 장치가 필요 없다.

**재부팅 후 복원하지 않는다.** `pm2 save` + `pm2 resurrect` 로 복원할 수 있지만 일부러 하지
않는다 — 부원이 켠 것을 잊었는데 재부팅 후에도 되살아나는 것은 놀라운 동작이고 "방치"를 오히려
늘린다. **재부팅 = 전부 초기화**가 이해하기 쉽고 상한 역할도 겸한다.

원래의 요구("워커 재시작에 끌려다니지 않는다")는 그대로 지켜진다 — 워커 재시작·주 1회 로그
로테이션·배포 갱신은 PM2 프로세스를 건드리지 않는다. 기계가 꺼질 때만 사라진다.

**PM2 로그도 무한히 커진다.** 이미 있는 주 1회 로테이션 작업
(`C:\ProgramData\asahi-maintenance\rotate-worker-log.ps1`)에 `pm2 flush` 를 더해 같은 주기로
정리한다. 별도 장치를 만들지 않는다.

## 6. 상태 조회와 발견성

이번 범위는 **"물어보면 안다"까지**다.

`proc_list` 출력 형태:

```
지금 도는 것 (2개)

우성현    npm run dev        online   2시간 12분   184MB   재시작 0
너        vite preview       online   14분         96MB    재시작 1
```

- 손님은 자기 것만, 소유자는 전원
- `pm2 jlist` 의 JSON 파싱과 표 렌더링은 **순수 함수**로 뗀다(§7)

**발견성이 진짜 통증이었다.** "무엇이 돌고 있는지 모른다"를 푸는 것은 조회 도구가 아니라
**언제 알려주느냐**다.

1. `proc_start` 성공 응답에 **멈추는 법을 그 자리에서** 넣는다 — 시작한 순간이 가장 기억하기 좋다
2. `/help` 에 한 줄
3. 공짜로 얻는 것: `proc_start`·`proc_stop` 이 `actions` 에 자동 기록된다(2026-07-28 관측 기반).
   소유자는 "누가 언제 무엇을 띄웠나"를 SQL 로 볼 수 있다

## 7. 테스트 이음매

PM2 는 외부 CLI 다. 테스트가 실제 설치를 요구하면 안 된다.

**순수 함수** (`agent/src/remote/proc.ts` 신규):

| 함수 | 하는 일 |
|---|---|
| `procNameFor(userId)` | `asahi-<디스코드 userId>` — 이름 규칙을 한 곳에 둔다 |
| `parseProcName(name)` | 역변환. 소유자 목록에서 "누구 것인지" 표시용 |
| `parsePm2List(json)` | `pm2 jlist` 출력 → `ProcInfo[]` |
| `renderProcList(procs, opts)` | 표 문자열. `renderTree` 와 같은 자리 |

**CLI 호출을 주입 가능하게 한다.**

```
makeExecutors(roots, opts?: { runPm2?: (args: string[]) => Promise<{ ok: boolean; stdout: string; stderr: string }> })
```

기본값은 실제 `spawn`. **이것은 2026-07-28 최종 리뷰가 잡은 Critical 의 교훈을 그대로 적용한
것이다** — 이음매를 만들지 않으면 그 경로는 테스트에서 한 번도 지나가지 않고, 그래서 실패 신호가
소실되는 버그가 태스크 리뷰 다섯 번을 통과했다.

**이음매 테스트**: 가짜 `runPm2` 를 주입해 `proc_start` 의 이름·cwd 주입 → `proc_list` → 파싱 →
렌더링까지 관통시킨다. 손님이 남의 `name` 을 넘겨도 무시되는지도 여기서 고정한다.

**단위 테스트로 못 잡는 것을 명시한다** — `pm2 jlist` 의 JSON 형태가 PM2 버전에 따라 바뀌면
가짜는 통과하고 실제만 깨진다. `deploy/smoke-test.md` 항목이 그것을 덮는다.

## 8. 설치와 문서

**미니PC 설치**(`asahi` 계정): `npm i -g pm2`. 전역 설치가 `asahi` 프로필에 들어가므로 다른
계정에선 보이지 않는다 — 워커가 `asahi` 로 도니 문제없다. 워커가 `spawn` 으로 `pm2` 를 부르므로
**`asahi` 의 PATH 에 npm 전역 bin 이 있는지 확인**해야 한다.

**문서 갱신 — 빠뜨리면 안 된다.**

- **`persona.ts` 능력 안내에 도구 넷 추가.** 2026-07-28 에 `fs_tree` 에서 이것을 빠뜨려 리뷰가
  Important 로 잡았다. 이 저장소는 "안내와 실제 도구가 어긋남"을 결함 유형으로 다룬다.
- **`docs/security/capability-model.md`** — 새 도구와 그 한계(§9)
- **`deploy/smoke-test.md`** — 실제 PM2 왕복, 그리고 **워커를 재시작해도 프로세스가 살아있는지.**
  이것이 이 설계의 핵심 주장이므로 반드시 눈으로 확인한다.

## 9. 위험 · 한계

**봇 쪽 1인 1개 상한은 강제가 아니다.** 손님은 이미 `sh_exec` 로 임의 셸을 돌릴 수 있으므로
`pm2 start --name asahi-<남의id>` 를 직접 칠 수 있고, `pm2 delete` 로 남의 것을 죽일 수도 있다.
이 상한은 **실수 방지선이지 작정한 접근의 경계가 아니다** — 폴더 격리와 정확히 같은 성격이고,
실제 경계는 여전히 워커를 돌리는 `asahi` OS 계정 하나다(`docs/security/capability-model.md`).

**자원 상한이 없다.** 윈도우에는 리눅스 cgroup 같은 수단이 없어, 한 프로세스가 미니PC 의 메모리를
전부 먹을 수 있다(RAM 16GB 로 증설했으나 성질이 바뀌지는 않는다). 1인 1개 상한이 "여러 개가
쌓이는 것"만 막는다.

**재부팅하면 전부 사라진다.** §5 의 의도된 선택이다. 부원에게 그렇게 안내해야 한다.

**`pm2 jlist` 형식 의존.** PM2 버전이 올라가며 필드가 바뀌면 파싱이 깨진다. 단위 테스트는 가짜를
쓰므로 잡지 못하고, 스모크 테스트가 유일한 검증 경로다.

## 10. 순서

1. 순수 함수(`proc.ts`)와 그 테스트
2. 실행기 넷 + `runPm2` 이음매
3. 봇 쪽 주입(이름·cwd)과 게이팅, 이음매 테스트
4. `persona.ts`·`/help`·문서
5. 미니PC 설치 + `pm2 flush` 추가 + 스모크

배포는 워커 코드를 바꾸므로 **미니PC 갱신이 필요하다** — 빠뜨리면 이 도구 넷만 조용히 실패한다.
