# 풀 하네스 워커 — Claude Code 를 도구가 있는 기계에서 통째로 돌리고, 자격증명은 봇에 둔다 — 설계

## 1. 무엇을 고치는가

운영자의 목표는 "디스코드에서 Claude Code 처럼 막힘 없이 개발하고, 개발 밖의 일도 하네스로 한다"이다.
지금 asahi 는 부원별 워크스페이스에서 **하나의 개발 사이클**(파일·셸·git·PR)만 돈다. 이미지 생성, 만든
파일을 디스코드로 돌려주기, 서버·DB 에 MCP 로 직접 붙기, 브라우저 호출, 화면 캡처, 문서 작성 같은 개발
밖 스킬 — 전부 없고, 하나 더하려면 매번 원격 도구를 새로 짜야 한다.

원인은 하나다. **하네스와 도구가 다른 기계에 있다.** 얇은 워커 설계([ADR 0006](../../decisions/0006-thin-worker.md))는
Claude Code(Agent SDK)를 Railway 에 두고 내장 도구를 전부 끈 뒤(`builtinTools=[]`), 파일·셸을 자체
프로토콜(`remote/protocol.ts`·`executors.ts`)로 미니PC 에 보낸다. 그래서 Claude Code 가 원래 갖고 있는
것들 — 내장 Read/Write/Edit/Bash/Glob/Grep/WebFetch, `mcpServers` 설정 한 줄로 붙는 MCP 서버, 스크립트가
든 스킬·플러그인, 서브에이전트, 훅 — 이 **도구가 실행되는 기계에 없다.** 능력 하나 = 원격 도구 하나 =
프로토콜·실행기·1차 필터·테스트·문서 한 벌이 되는 구조다. 2026-08 이후 더한 능력(발행·되받기·proc_*·
파일 올리기·git 자격증명·PR·저장소 목록·리뷰 읽기·PR 추적) 전부가 그 값을 치렀다.

이 설계를 택했던 이유도 하나였다. **구독 자격증명을 부원의 셸이 닿는 기계에 두지 않는다.** 이 제약은
그대로 지킨다. 바꾸는 것은 "자격증명을 지키려면 하네스도 Railway 에 있어야 한다"는 결론이다 — 그 둘은
분리할 수 있다.

## 2. 목표와 비목표

**목표**
- 부원(과 운영자)이 자기 워크스페이스에서 Claude Code 의 도구·MCP·플러그인·서브에이전트를 그대로 쓴다.
  새 능력은 코드가 아니라 **구성**(MCP 서버·플러그인 설치·프로필)으로 더한다.
- 워커 기계에는 지금처럼 `WORKER_TOKEN` 하나만 있다. Claude 자격증명·DB 접속 문자열·외부 서비스 키는
  Railway 를 떠나지 않는다.
- 신원·위치 기반 정책(소유자 DM / 소유자 서버 / 손님, [능력 계층 모델](../../security/capability-model.md))·
  한도·기록·페르소나는 봇이 계속 맡는다. 병합은 여전히 사람이 한다.

**비목표**
- 웹 UI(디스코드의 첨부 크기·메시지 길이·실시간 표시 한계는 채널의 한계라 여기서 풀지 않는다 — 이벤트
  버스가 어댑터를 분리해 둬서 나중에 붙일 수 있다).
- OpenClaw·Hermes 같은 외부 하네스로의 교체(§10).
- 무인 턴(정기 게시·유휴 요약)의 변경 — 그 둘은 지금처럼 봇 안에서 도구 없이 돈다.

## 3. 구조

```
디스코드 ──▶ 봇(Railway) ──────────────────────────────────────────┐
             ├ 어댑터·코어·페르소나·한도·기록·DB (지금과 같다)          │
             ├ 인증 프록시   /llm/v1/*   워커의 요청에 진짜 자격증명을 끼운다 │
             ├ MCP 허브      /mcp/<이름>  Supabase·Railway·GitHub 등을 HTTP MCP 로 노출 │
             ├ 파일 수신     /files      워커가 올린 산출물을 디스코드 첨부로 │
             └ 워커 허브     /worker     (지금과 같다) + turn.* 프레임          │
                    │ WebSocket                                            │ HTTPS (작업 토큰)
                    ▼                                                      │
             워커(미니PC·운영자 PC·컨테이너 호스트) ◀──────────────────────┘
             ├ 세션 러너: turn.start 를 받아 그 부원의 샌드박스에서 Agent SDK query() 를 돈다
             │   ANTHROPIC_BASE_URL = 봇의 /llm, ANTHROPIC_AUTH_TOKEN = 작업 토큰, CLAUDE_CONFIG_DIR = 부원별
             ├ 내장 도구(Read/Write/Edit/Bash/Glob/Grep/WebFetch/WebSearch)·플러그인·스킬·서브에이전트
             ├ 로컬 MCP(브라우저·화면 캡처) + 허브 MCP(봇이 노출한 것, 신원별)
             └ 샌드박스: L0 없음(개인 PC) / L1 부원별 OS 계정 / L2 부원별 컨테이너 (§5)
```

한 턴의 흐름:

1. 디스코드 메시지 → 봇의 `ingest`·한도·직렬화·컨텍스트 조립은 지금과 같다.
2. 원격 도구가 열리는 턴(워커 연결 + 신원 판정)이면 봇은 `runTurn` 대신 **`turn.start`** 를 워커에 보낸다:
   시스템 프롬프트, 프롬프트(첨부 마커 포함), `resume` 세션 id, 작업 폴더(그 부원의 스코프 폴더),
   도구·MCP·플러그인 **프로필**(§6), 모델·maxTurns, 그리고 **작업 토큰**(§4).
3. 워커는 그 부원의 샌드박스에서 `query()` 를 돌린다. 진행 이벤트(도구 호출·결과·답변 시작)는
   `turn.event` 로 흘려보내고, 봇은 지금의 `progressFromMessage`·`actions` 기록·진행 표시를 그대로 탄다.
4. `turn.result` 로 최종 텍스트와 세션 id 가 온다. 세션은 워커의 `CLAUDE_CONFIG_DIR`(부원별)에 남아 다음
   턴의 `resume` 이 된다 — 봇은 지금처럼 `conversations.session_id` 만 갖는다. 워커가 바뀌어 세션이 없으면
   기존 `isSessionNotFound` 폴백이 그대로 새 세션으로 재시도한다.
5. 워커가 없거나 도구가 닫힌 턴(무인 턴 포함)은 지금의 봇 쪽 `runTurn`(도구 없음)으로 돈다 — 두 경로가
   페르소나·기록을 공유한다.

## 4. 자격증명 — 프록시와 작업 토큰

### 4.1 원칙

워커에는 진짜 자격증명이 **없다.** Claude Code 는 `ANTHROPIC_BASE_URL` 을 봇으로, `ANTHROPIC_AUTH_TOKEN`
을 **작업 토큰**으로 받는다. 봇의 프록시가 그 토큰을 검증하고 진짜 자격증명으로 바꿔 Anthropic 에
전달한다. MCP 허브(§6)와 파일 수신(§8)도 같은 토큰으로 인증한다.

| | 값 | 어디에 | 수명 |
|---|---|---|---|
| Claude 자격증명(API 키 또는 구독 OAuth) | Railway 환경변수 | 봇만 | 영구 |
| 작업 토큰 | 봇이 `turn.start` 마다 발급(HMAC: 작업 id·부원·만료·모델) | 그 세션의 환경변수 | 턴 + 여유(예: 2시간) |
| 워커 토큰 | `WORKER_TOKEN` | 워커 `.env` | 지금과 같다 |

작업 토큰이 새면 그 만료까지 **프록시를 통한 모델 호출**만 가능하다 — 진짜 자격증명은 못 보고, 모델은
프록시가 고정하며, 한도는 그 부원 몫으로 센다. 지금 셸 토큰(1시간·조직 `contents:write`)을 받아들인
것과 같은 성질의 위험이고 더 좁다.

### 4.2 프록시가 하는 일

- 경로 허용 목록: `/v1/messages` 계열만. 나머지는 404.
- 작업 토큰 검증(서명·만료·작업 id 가 진행 중인지). 실패는 401.
- Authorization 교체, 필요한 베타 헤더 보정(구독 OAuth 는 `oauth-2025-04-20` 이 있어야 한다).
- 모델 고정: 요청 본문의 `model` 이 그 작업에 허용된 값이 아니면 400. 부원이 프롬프트로 모델을 바꾸는 경로를 막는다.
- 사용량 기록: SSE 의 `message_start`/`message_delta` 에서 `usage` 를 읽어 부원·작업별로 남긴다 — 지금
  시간당 턴 수 한도 위에 토큰 예산을 더 얹을 근거가 된다(처음엔 기록만).
- 스트리밍 그대로 통과(SSE). 타임아웃은 SDK 의 것을 따른다.

### 4.3 자격증명 종류 — 결정이 필요하다

| | API 키 | 구독 OAuth(`claude setup-token`) |
|---|---|---|
| 프록시 뒤에서 동작 | 표준 패턴(LLM 게이트웨이) — 문제 없다 | **스파이크 미완**(아래) |
| 약관 | 명확하다 | 2026년 초 Anthropic 이 서드파티 하네스의 구독 사용을 금지·차단했다. 클라이언트가 여전히 Claude Code 라는 점에서 이 구조는 그쪽과 다르지만, 한 구독으로 여러 사람을 서비스하는 것 자체가 회색지대다 |
| 비용 | 사용량 비례(Opus 5 입력 $5·출력 $25 / 1M) — 서브에이전트·브라우저를 열면 지금보다 훨씬 늘어난다 | 정액. 대신 5시간 창 한도를 전원이 나눠 쓴다 |

**권장: API 키.** 이 설계가 여는 것(서브에이전트·브라우저·MCP)은 토큰 사용량을 크게 늘리고, 그것을 부원별로
세고 제한하는 자리가 프록시다 — 정액 구독 위에서는 그 계산이 성립하지 않는다. 구독을 쓰려면 아래 프로브를
운영자 PC 에서 돌려 기술적으로 되는지 먼저 보고, 약관을 확인한 뒤 결정한다.

### 4.4 스파이크(2026-09-05, 운영자 PC)

`agent/src/scripts/llmProxyProbe.ts` — 루프백 프록시를 띄우고, 로컬 로그인을 못 보게 한(`CLAUDE_CONFIG_DIR`
빈 폴더) Agent SDK 세션을 `ANTHROPIC_BASE_URL`=프록시, `ANTHROPIC_AUTH_TOKEN`=더미로 한 턴 돌린다.

실측(진짜 토큰 없이, 두 모드):

- **passthrough**(로컬 OAuth 로그인은 그대로 두고 `ANTHROPIC_BASE_URL` 만 프록시로): 이 PC 에
  `~/.claude/.credentials.json` 이 있는데도 CLI 는 프록시에 `HEAD /` 만 보내고 "Not logged in · Please run
  /login" 으로 끝냈다. 즉 **base URL 을 바꾸면 CLI 는 로컬 OAuth 로그인을 쓰지 않는다.** 워커가 자기 로그인을
  가진 채 프록시만 거치는 변형은 성립하지 않고, 자격증명은 반드시 프록시가 끼워야 한다 — 이 설계의 방향과
  같다.
- **inject**(`CLAUDE_CONFIG_DIR` 빈 폴더 + `ANTHROPIC_AUTH_TOKEN=worker-dummy`): CLI 는 `HEAD /` 뒤
  `POST /v1/messages?beta=true` 를 **`authorization: Bearer worker-dummy-token`** 과 `anthropic-beta` 헤더로
  프록시에 보냈다. 프록시가 업스트림의 401 을 돌려주면 SDK 는 예외 없이 `result(success)` 안에 "Not logged in"
  문구를 싣고 끝난다. 즉 **전송 계층은 교체 가능하다** — 자격증명 없는 워커 + 끼워 넣는 프록시 구조의 전제는
  성립한다.

아직 못 본 것은 하나다: 프록시가 끼운 **진짜 자격증명을 업스트림이 받는지** — 특히 구독 OAuth 토큰이 그렇다
(API 키는 표준 게이트웨이 패턴이라 의문이 없다). 이 스크립트는 운영자의 자격증명을 스스로 읽지 않으므로, 남은
한 걸음은 운영자가 직접 한다:

```
cd agent
ASAHI_PROBE_USE_LOCAL_LOGIN=1 npx tsx src/scripts/llmProxyProbe.ts        # 이 PC 의 Claude Code 로그인(OAuth)으로
ASAHI_PROBE_TOKEN=<API 키 또는 setup-token 출력> npx tsx src/scripts/llmProxyProbe.ts   # 또는 토큰을 직접
```

`verdict` 가 "성공" 이면 그 종류의 자격증명으로 §4.1 이 실측된 것이다. 토큰은 메모리에만 있고 스크립트는 헤더
값을 기록하지 않는다. 결과가 "실패(401)" 이면 구독 OAuth 는 프록시 뒤에서 쓸 수 없다는 뜻이고, 그러면 §4.3 의
선택은 API 키 하나로 좁혀진다.

## 5. 샌드박스 — 부원을 어떻게 가르는가

풀 하네스에서는 Bash·WebFetch·서브에이전트가 그 기계에서 그대로 돈다. 지금도 `sh_exec` 는 경로로 봉쇄되지
않으므로([위험 등록부](../../security/risk-register.md) §5) **위협의 종류는 같고 도달하기가 쉬워진다.** 그래서
격리는 폴더가 아니라 **실행 단위**로 올린다.

| 수준 | 무엇 | 어디에 맞는가 |
|---|---|---|
| L0 없음 | 워커 프로세스와 같은 계정에서 세션이 돈다 | **운영자 개인 PC**(개인 워커). 자기 기계에서 자기 세션이라 가를 것이 없다. 1단계의 첫 대상 |
| L1 부원별 OS 계정 | 미니PC 에 부원별 표준 계정, 세션은 그 계정으로 띄운다 | 공유 미니PC 의 중간 단계. 윈도우에서 다른 계정으로 프로세스를 띄우려면 자격증명·작업 스케줄러가 필요해 운영 부담이 크다 |
| L2 부원별 컨테이너 | 부원마다 컨테이너(리눅스), 워크스페이스만 마운트, CPU·메모리 상한 | **공유 기계의 목표 형태.** 지금 문서화된 함정 상당수(PowerShell 5.1·cmd.exe 인용·cp949)가 사라진다. 대가는 호스트 — 미니PC 의 윈도우 에디션·가상화 지원에 따라 WSL2+Docker 가 되거나, 리눅스 기계를 하나 두어야 한다 |

**결정이 필요하다(운영자):** 공유 기계의 격리 수준. 확인할 것 — 미니PC 의 윈도우 에디션과 가상화 활성 여부
(`systeminfo | findstr /i "OS Name Hyper-V"`), Docker Desktop 설치가 가능한지(관리자 필요), 아니면 리눅스
호스트를 따로 둘지. 이 결정이 4단계(§11)를 정하고, 그 전 단계는 결정과 무관하게 진행할 수 있다.

컨테이너의 네트워크는 처음엔 열어 둔다(지금 `sh_exec` 도 그렇다). 봇 프록시·허브만 허용하는 이그레스
정책은 나중에 조일 수 있는 자리로 남긴다.

## 6. 도구·MCP·플러그인 — 프로필

능력은 봇이 `turn.start` 에 싣는 **프로필**로 정한다. 지금 `allowedToolsFor` 가 하는 일이 그대로 프로필 계산이 된다.

| 프로필 | 내장 도구 | MCP | 플러그인·스킬 |
|---|---|---|---|
| 소유자 | 전부 | 허브: Supabase(읽기)·Railway·GitHub / 로컬: 브라우저 | 전부 |
| 손님(공유 기계) | 전부 — 작업 폴더가 그 부원 스코프 | 로컬: 브라우저 / 허브: 이미지 생성 등 부원용으로 연 것만 | 개발·문서 스킬 |
| 무인 턴 | 없음(봇 안에서 돈다) | 없음 | 없음 |

- **MCP 허브(봇)**: 비밀이 필요한 서버(Supabase·Railway·GitHub·이미지 생성 API)는 Railway 안에서 stdio 로
  띄우고 HTTP MCP 로 노출한다. 워커의 Claude Code 는 `mcpServers` 에 `https://<봇>/mcp/<이름>` 을 작업 토큰
  인증으로 붙인다. **비밀은 Railway 를 떠나지 않는다.** 어느 서버를 어느 프로필에 여는지는 봇의 표 하나다.
- **로컬 MCP(워커)**: 브라우저·화면 캡처(Playwright 류)는 그 기계의 localhost 개발서버를 찍어야 하므로
  워커 쪽에 둔다. 비밀이 없다.
- **플러그인·스킬**: 지금은 `agent/skill-plugin/` 에 복사해 커밋한 문서형 스킬만 돈다. 풀 하네스에서는 워커
  기계에 설치된 Claude Code 플러그인이 그대로 쓰이므로, 리포 밖의 공개 플러그인도 프로필로 열 수 있다.
  라이선스가 재배포를 막는 스킬은 리포에 넣지 않고 워커 설치로만 다룬다.
- `git` 자격증명은 지금 방식(`sh_exec` 호출마다 셸 토큰 주입)을 세션 환경변수로 옮긴다 — 세션 시작 때
  `GIT_CONFIG_*` 와 헬퍼를 얹으면 Bash 의 git 이 그대로 인증한다. 토큰 수명·범위는 지금과 같다.

## 7. 봇↔워커 프로토콜

`remote/protocol.ts` 에 프레임 넷을 더한다 — 기존 도구 호출 프레임은 그대로 둔다(전환 기간 동안 두 경로가 공존한다).

| 프레임 | 방향 | 내용 |
|---|---|---|
| `turn.start` | 봇→워커 | 작업 id, 부원 id, 작업 폴더, 시스템 프롬프트, 프롬프트, resume, 프로필(도구·MCP·플러그인), 모델·maxTurns, 작업 토큰, git 환경 |
| `turn.event` | 워커→봇 | SDK 스트림 메시지의 요약(도구 호출·결과·답변 시작) — 지금 `ProgressUpdate` 와 같은 모양 |
| `turn.result` | 워커→봇 | 최종 텍스트, 세션 id, 성패, 사용량 요약 |
| `turn.cancel` | 봇→워커 | 대화 리셋·타임아웃 때 세션 중단 |

- 동시성: 워커는 부원별로 세션 하나. 같은 대화의 재진입 금지는 봇의 `turnChains` 가 지금처럼 지킨다.
- 프레임 상한(1MB)은 이벤트에 충분하다. 큰 것(파일)은 §8 의 HTTP 로 간다.
- 워커 재시작·자동 갱신: 진행 중 작업이 있으면 센티넬이 기다리는 지금 규칙을 그대로 쓴다(`workerShutdown.ts`).
  봇은 끊긴 작업을 실패로 마감하고 사용자에게 알린다.

## 8. 파일 반환

산출물(이미지·PDF·캡처)을 디스코드로 돌려주는 경로다 — 로드맵 7번이고, 풀 하네스와 무관하게 먼저 만든다.

- 봇에 `POST /files`(작업 토큰 인증, 크기 상한) 를 둔다. 워커 쪽 도구 `send_file(path)` 이 그 부원의 폴더
  안 파일을 읽어 올리고, 봇이 그 대화 채널에 첨부로 보낸다. 디스코드 첨부 상한(서버 등급에 따라 다르다)을
  넘으면 그 사실을 말한다.
- 지금 얇은 워커에서는 `send_file` 을 원격 도구로 하나 더 만들어 같은 엔드포인트를 쓴다. 풀 하네스에서는
  워커 쪽 인프로세스 MCP 도구가 된다 — 엔드포인트는 같다.

## 9. 위협 판단

- **자격증명은 워커에 없다** — 유일하게 가는 것은 작업 토큰이고, 그것으로 할 수 있는 일은 만료까지 프록시를
  통한 고정 모델 호출뿐이다. 진짜 자격증명·DB·외부 서비스 키는 Railway 를 떠나지 않는다.
- **프롬프트 인젝션의 도달 범위는 넓어진다** — 내장 Bash·WebFetch·서브에이전트가 손님 세션에서도 돈다.
  종류는 지금 `sh_exec` 와 같다(경로로 봉쇄되지 않는 셸). 완화는 §5 의 실행 단위 격리와 페르소나의 신뢰
  경계 규칙이고, 무인 턴은 여전히 도구 없이 봇 안에서 돈다.
- **MCP 허브**는 신원별 허용 목록이 유일한 경계다 — 손님 프로필에 Supabase·Railway 를 열지 않는다. 열린
  서버의 도구 하나하나가 곧 능력이라, 서버를 추가하는 커밋이 승인 절차다(스킬 하네스와 같은 원칙).
- **작업 토큰 유출** — 만료·부원·모델 바인딩으로 피해가 좁다. 프록시의 사용량 기록이 이상 사용을 드러낸다.
- **격리 없는 공유 기계(L0)에 손님을 올리지 않는다.** 1단계는 운영자 개인 PC 로 한정한다.

## 10. 고르지 않은 것

| | 방식 | 왜 아닌가 |
|---|---|---|
| A | 얇은 워커를 유지하고 원격 도구를 계속 더한다 | 능력 하나마다 프로토콜·실행기·필터·테스트·문서 한 벌. MCP 생태계·플러그인·서브에이전트는 이 길로는 영원히 닿지 않는다 |
| B | 워커에 구독 토큰을 둔다 | 부원의 셸이 닿는 기계에 영구 자격증명. 이 리포가 처음부터 거부한 것 |
| C | 부원마다 API 키를 발급해 워커에 둔다 | 키가 디스코드 밖에서도 쓰이고 회수·한도가 사람 손에 달린다. 프록시가 같은 일을 봇 안에서 한다 |
| D | OpenClaw·Hermes 로 교체하고 구독제로 개조 | 게이트웨이가 도구 기계에서 도는 구조라 자격증명 문제가 같고, 구독 개조는 약관 위험의 정면이다. 신원·스코프·단기 토큰·브랜치 정책을 남의 코드에 다시 심고 포크를 유지해야 한다. 부품·아이디어로만 참고한다 |
| E | 웹훅·실시간 UI | 채널의 몫. 이벤트 버스가 어댑터를 분리해 둔 자리에 나중에 붙인다 |

## 11. 단계

각 단계는 독립적으로 병합·배포되고, 앞 단계 없이도 값이 있다.

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 0 | **파일 반환**(§8): `POST /files` + 얇은 워커의 `send_file` 원격 도구 | 부원이 만든 이미지가 디스코드 첨부로 돌아온다 |
| 1 | **프록시 + 세션 러너, 운영자 개인 PC(L0)**: 인증 프록시·작업 토큰·`turn.*` 프레임·워커 `WORKER_MODE=harness`. 소유자 DM 만 새 경로 | 운영자 DM 에서 내장 도구·서브에이전트·resume 이 도는 턴이 실사용으로 확인된다. 자격증명은 개인 PC 에 없다 |
| 2 | **프록시 운영화**: 모델 고정·사용량 기록·부원별 토큰 예산·장애 시 폴백(봇 쪽 도구 없는 턴) | 프록시 거절·만료·예산 초과가 사용자 문구로 나오고 `actions`·사용량 표에 남는다 |
| 3 | **MCP 허브·브라우저·플러그인**: 소유자 프로필에 Supabase·Railway·GitHub 허브 MCP, 워커에 브라우저 MCP, 공개 플러그인 설치 절차 | 운영자가 디스코드에서 DB 를 조회하고 localhost 화면을 캡처해 첨부로 받는다 |
| 4 | **공유 미니PC(L1 또는 L2)**: §5 결정에 따라 격리를 세우고 손님 프로필을 연다 | 두 부원이 각자 컨테이너/계정에서 동시에 세션을 돈다. 한쪽의 셸이 다른 쪽 폴더·토큰에 닿지 않는 것을 실검증 |
| 5 | **얇은 도구 은퇴**: 원격 `fs_*`·`sh_exec`·`proc_*` 를 걷어내고 ADR 0006 을 대체하는 ADR | 모든 도구 턴이 새 경로로 돈다. 프로토콜의 옛 프레임 삭제 |

1단계를 운영자 개인 PC 로 잡는 이유: 격리 결정을 기다리지 않고 구조 전체(프록시·토큰·프레임·세션)를 실사용으로
검증할 수 있고, 지금까지 `owner-laptop` 워커는 등록만 되고 쓰이지 않았다(`allowed_dirs` 0행).

## 12. 운영자가 해야 하는 것(코드 밖)

1. **자격증명 종류 결정**(§4.3). 구독을 쓰려면 §4.4 프로브를 토큰과 함께 돌려 결과를 본다. API 키면 Railway 에
   `ANTHROPIC_API_KEY` 를 두고 `CLAUDE_CODE_OAUTH_TOKEN` 은 뺀다(둘 다 있으면 API 키가 이긴다).
2. **공유 기계의 격리 수준 결정**(§5) — 미니PC 에디션·가상화·Docker 가능 여부 확인, 또는 리눅스 호스트.
3. 1단계 때 개인 PC 워커를 `WORKER_MODE=harness` 로 다시 등록·기동(절차는 그때 `deploy/worker-셋업.md` 에 더한다).
4. 3단계 때 허브 MCP 에 쓸 서비스 키(Supabase 읽기 전용 등)를 Railway 에 둔다.

## 13. 검증

- 유닛: 프록시(토큰 서명·만료·경로 허용·모델 고정·헤더 교체·SSE 통과)는 가짜 업스트림으로, 세션 러너는 가짜
  `query()` 로, 프레임은 `remoteProtocol.test.ts` 관례로. 프로필 계산은 `allowedToolsFor` 의 기존 테스트를
  프로필로 확장.
- 실환경: `agent/src/scripts/llmProxyProbe.ts`(§4.4), 그리고 단계별 완료 기준을 `deploy/smoke-test.md` 에 항목으로.
- 이 문서의 스파이크 결과는 운영자 PC 실측이다 — 미니PC 에서는 아직 아무것도 실행하지 않았다.
