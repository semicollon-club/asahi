# 풀 하네스 · 미니PC 단일 호스트 — Claude Code 를 도구가 있는 기계에서 통째로 돌리고, 봇도 그 기계로 옮긴다 — 설계

## 1. 무엇을 고치는가

운영자의 목표는 "디스코드에서 Claude Code 처럼 막힘 없이 개발하고, 개발 밖의 일도 하네스로 한다"이다.
지금 asahi 는 부원별 워크스페이스에서 **하나의 개발 사이클**(파일·셸·git·PR)만 돈다. 이미지 생성, 만든
파일을 디스코드로 돌려주기, 서버·DB 에 MCP 로 직접 붙기, 브라우저 호출, 화면 캡처, 문서 작성 같은 개발
밖 스킬 — 전부 없고, 하나 더하려면 매번 원격 도구를 새로 짜야 한다.

원인은 둘이 겹쳐 있다.

1. **하네스와 도구가 다른 기계에 있다.** 얇은 워커 설계([ADR 0006](../../decisions/0006-thin-worker.md))는
   Claude Code(Agent SDK)를 Railway 에 두고 내장 도구를 전부 끈 뒤(`builtinTools=[]`), 파일·셸을 자체
   프로토콜로 미니PC 에 보낸다. Claude Code 가 원래 갖는 것 — 내장 Read/Write/Edit/Bash/Glob/Grep/WebFetch,
   `mcpServers` 한 줄로 붙는 MCP 서버, 스크립트가 든 스킬·플러그인, 서브에이전트, 훅 — 이 도구가 실행되는
   기계에 없다. 능력 하나 = 원격 도구 하나 = 프로토콜·실행기·필터·테스트·문서 한 벌이다.
2. **기계가 둘이다.** Railway 봇과 미니PC 워커의 커밋이 어긋나는 문제, watch path, 1MB 프레임 상한, 리눅스
   봇이 윈도우 경로를 다루는 문제, 배포 순서 — `docs/agent-onboarding.md` 의 함정 절반이 이 얘기다.
   Railway 를 둔 이유([ADR 0002](../../decisions/0002-railway-local-worker-hybrid.md))는 "PC 는 운영자 노트북이라
   항상 켜져 있지 않다" 였는데, 지금은 24시간 켜진 동아리 미니PC 가 있고 이 봇은 인바운드 포트가 하나도
   필요 없다(디스코드·Anthropic·깃허브·Supabase 전부 아웃바운드, 웹훅은 쓰지 않는다).

두 설계를 택했던 이유는 하나였다. **구독 자격증명을 부원의 셸이 닿는 자리에 두지 않는다.** 이 제약은
그대로 지킨다. 바꾸는 것은 "그러려면 하네스도 봇도 다른 기계에 있어야 한다"는 결론이다 — 같은 기계의
**다른 OS 계정**으로 충분하다.

## 2. 목표와 비목표

**목표**
- 부원(과 운영자)이 자기 워크스페이스에서 Claude Code 의 도구·MCP·플러그인·서브에이전트를 그대로 쓴다.
  새 능력은 코드가 아니라 **구성**(MCP 서버·플러그인 설치·프로필)으로 더한다.
- 봇·세션·워크스페이스가 미니PC 한 대에서 돈다. Railway 는 이행 기간에만 남고 그 뒤 내린다.
- 부원의 셸이 도는 계정에는 자격증명이 없다. Claude 토큰·디스코드 토큰·DB 접속 문자열·깃허브 App 키는
  봇 계정에만 있다.
- 신원·위치 기반 정책([능력 계층 모델](../../security/capability-model.md))·한도·기록·페르소나는 봇이 계속 맡는다.
  병합은 여전히 사람이 한다.

**비목표**
- 웹 UI(디스코드의 첨부 크기·메시지 길이·실시간 표시 한계는 채널의 한계 — 이벤트버스가 어댑터를 분리해 둬서
  나중에 붙일 수 있다).
- OpenClaw·Hermes 같은 외부 하네스로의 교체(§10).
- 부원별 OS 계정·컨테이너 격리(§5 — 운영자가 성능 부담으로 제외했다).
- 무인 턴(정기 게시·유휴 요약)의 변경 — 그 둘은 지금처럼 봇 안에서 도구 없이 돈다.

## 3. 구조 — 미니PC 한 대, 계정 둘

```
디스코드 ◀──아웃바운드──▶ ┌─ 미니PC ───────────────────────────────────────────────────────┐
Anthropic·깃허브·Supabase  │                                                                │
                           │  계정 A  asahi-bot (표준 사용자)                                │
                           │   봇 프로그램(agent/src/index.ts)                              │
                           │    ├ 디스코드 어댑터·코어·페르소나·한도·기록 (지금 그대로)        │
                           │    ├ 인증 프록시  127.0.0.1:P /llm/v1/*  작업 토큰 → 진짜 자격증명 │
                           │    ├ MCP 허브     127.0.0.1:P /mcp/<이름>  비밀 필요한 도구 대행    │
                           │    ├ 파일 수신    127.0.0.1:P /files      산출물 → 디스코드 첨부   │
                           │    └ 워커 허브    127.0.0.1:P /worker     (지금 그대로) + turn.*   │
                           │   자격증명 전부 여기(A 의 프로필 폴더 .env, NTFS 권한)             │
                           │                       ▲ 루프백                                 │
                           │  계정 B  asahi (표준 사용자, 지금의 워커 계정)                    │
                           │   세션 러너(agent/src/worker.ts, WORKER_MODE=harness)             │
                           │    ├ turn.start → 그 부원 폴더에서 Agent SDK query()             │
                           │    │   ANTHROPIC_BASE_URL=http://127.0.0.1:P/llm                 │
                           │    │   ANTHROPIC_AUTH_TOKEN=작업 토큰, CLAUDE_CONFIG_DIR=부원별   │
                           │    ├ 내장 도구·플러그인·스킬·서브에이전트가 이 기계에서 실행       │
                           │    ├ 로컬 MCP(브라우저·캡처) + 허브 MCP(봇이 노출, 신원별)          │
                           │    └ 부원 워크스페이스 C:\asahi-workspace\<userId>\ (지금 그대로)  │
                           │   자격증명 없음. 워커 토큰 하나                                  │
                           └────────────────────────────────────────────────────────────────┘
```

**한 턴에 세션은 하나다.** 도구가 열리는 턴은 계정 B 의 세션 러너에서만 돌고, 봇은 그 턴에 모델 세션을 열지
않는다 — 디스코드 중계·정책·프록시(전달)·허브(도구 대행)만 한다. 봇이 자기 세션을 여는 경우는 지금과 같은
둘뿐이다: 워커가 없어 도구 없이 답하는 턴, 그리고 정기 게시·유휴 요약.

한 턴의 흐름:

1. 디스코드 메시지 → 봇의 `ingest`·한도·직렬화·컨텍스트 조립은 지금과 같다.
2. 원격 도구가 열리는 턴이면 봇은 `runTurn` 대신 **`turn.start`** 를 워커 허브로 보낸다: 시스템 프롬프트,
   프롬프트, `resume` 세션 id, 작업 폴더, 도구·MCP·플러그인 **프로필**(§6), 모델·effort·maxTurns, **작업 토큰**(§4).
3. 세션 러너가 그 폴더에서 `query()` 를 돌린다. 진행 이벤트는 `turn.event` 로 흘려 지금의 진행 표시·`actions`
   기록을 그대로 탄다. 모델 호출은 루프백 프록시를 거쳐 Anthropic 으로 간다.
4. `turn.result` 로 최종 텍스트와 세션 id 가 온다. 세션은 B 의 부원별 `CLAUDE_CONFIG_DIR` 에 남아 다음
   턴의 `resume` 이 된다. 없으면 기존 `isSessionNotFound` 폴백이 새 세션으로 재시도한다.
5. 워커가 없거나 도구가 닫힌 턴은 지금의 봇 쪽 `runTurn` 으로 돈다.

두 계정이 필요한 이유는 §9 하나다 — 표준 사용자 B 는 A 의 파일(NTFS)과 프로세스 환경(관리자 권한 필요)을
못 읽는다. 지금 미니PC 가 워커를 `asahi` 표준 계정의 작업 스케줄러로 돌리는 방식 그대로, 봇을 다른 계정의
작업으로 하나 더 등록한다. 부원별 계정이 아니라 **역할별 계정 둘**이라 성능 부담은 없다.

**DB** 는 Supabase 를 그대로 쓴다(접속 문자열이 A 에만 있으면 "미니PC 는 `DATABASE_URL` 을 갖지 않는다" 는 규칙이
"부원 계정은 갖지 않는다" 로 바뀌는 것뿐이다). 로컬 Postgres 로 옮기는 것은 이 설계와 무관한 별도 결정으로 남긴다.

**운영자 개인 PC 워커**는 빠진다. 미니PC 의 허브가 루프백에만 묶이므로 밖에서 붙을 수 없고, 그 워커는 등록만
되고 쓰인 적이 없다(`allowed_dirs` 0행). 소유자 DM 은 공유 워커의 관리자 스코프로 간다(§6).

## 4. 자격증명 — 프록시와 작업 토큰

### 4.1 원칙

세션이 도는 계정 B 에는 진짜 자격증명이 **없다.** Claude Code 는 `ANTHROPIC_BASE_URL` 을 루프백 프록시로,
`ANTHROPIC_AUTH_TOKEN` 을 **작업 토큰**으로 받는다. 봇(계정 A)의 프록시가 그 토큰을 검증하고 진짜 자격증명으로
바꿔 Anthropic 에 전달한다. MCP 허브(§6)와 파일 수신(§8)도 같은 토큰으로 인증한다.

| | 값 | 어디에 | 수명 |
|---|---|---|---|
| Claude 구독 OAuth(`claude setup-token`) | A 의 `.env` | 봇 계정만 | 재발급까지 |
| 디스코드 토큰·`DATABASE_URL`·깃허브 App 키 | A 의 `.env` | 봇 계정만 | 재발급까지 |
| 작업 토큰 | 봇이 `turn.start` 마다 발급(HMAC: 작업 id·부원·만료·모델) | 그 세션의 환경변수 | 턴 + 여유(2시간) |
| 워커 토큰 | `WORKER_TOKEN` | B 의 `.env` | 지금과 같다 |

작업 토큰이 새면 그 만료까지 **루프백 프록시를 통한 고정 모델 호출**만 가능하다 — 그리고 프록시는 `127.0.0.1`
에만 묶여 있어 **미니PC 밖에서는 쓸 수 없다.** 진짜 자격증명은 못 보고, 한도는 그 부원 몫으로 센다.

### 4.2 프록시가 하는 일

- 바인드: `127.0.0.1` 만. 경로 허용 목록: `/llm/v1/messages` 계열만, 나머지는 404.
- 작업 토큰 검증(서명·만료·작업 id 가 진행 중인지). 실패는 401.
- Authorization 교체, 베타 헤더 보정(구독 OAuth 는 `oauth-2025-04-20` 이 있어야 한다).
- 모델 고정: 본문의 `model` 이 그 작업의 프로필 모델이 아니면 400. 부원이 프롬프트로 모델을 바꾸는 경로를 막는다.
- 사용량 기록: SSE 의 `message_start`/`message_delta` 에서 `usage` 를 읽어 부원·작업별로 남긴다.
- 스트리밍 그대로 통과(SSE). 타임아웃은 SDK 의 것을 따른다.

### 4.3 자격증명은 구독 OAuth 다 (운영자 결정, 2026-09-05)

API 키는 비용상 선택지가 아니다(운영자). 구독 하나를 여러 사람이 쓰므로 프록시의 역할은 비용 계산이 아니라
**5시간 창(과 주간 한도)을 부원끼리 나누는 공정 분배**다.

- **프로필별 모델·effort** 가 첫 지렛대다. 운영자 세션은 Opus 5, 부원 세션은 기본 Sonnet 5 에 낮은 effort.
  프록시가 본문의 `model` 을 프로필에 고정하고, effort 는 세션 러너의 `query()` 옵션으로 준다.
- **부원별 상한**(창 안의 토큰 또는 턴)을 걸어 한 사람이 창을 비우지 못하게 한다. 지금의 시간당 턴 한도
  (`turns.reserve`)가 출발점이다.
- **한도에 닿았을 때**(업스트림 429): 프록시가 한국어 사유로 바꾸고 봇은 "구독 한도, N분 뒤" 로 안내한다.
  운영자 세션은 마지막까지 열어 둔다 — 부원 몫이 소진되면 부원 턴부터 거절한다.
- **확장 경로 — 부원 각자의 구독**: 부원이 자기 `claude setup-token` 을 봇에 DM 으로 등록하면(Railway 아닌
  A 의 DB 에 암호화 저장, B 에는 절대 가지 않는다) 프록시가 그 사람 세션에는 그 사람 토큰을 끼운다. 창을 나눌
  필요가 없어지고 "한 구독으로 여러 사람" 문제도 사라진다. 지금은 자리만 둔다.

약관: 2026년 초 Anthropic 이 서드파티 하네스의 구독 사용을 금지·차단했다. 이 구조의 클라이언트는 여전히
Claude Code 지만, 한 구독으로 여러 사람을 서비스하는 것은 지금 봇이 이미 안고 있는 회색지대다 — 새로 생기는
위험은 아니고, 없어지는 위험도 아니다.

### 4.4 스파이크(2026-09-05, 운영자 PC)

`agent/src/scripts/llmProxyProbe.ts` — 루프백 프록시를 띄우고, 로컬 로그인을 못 보게 한(`CLAUDE_CONFIG_DIR`
빈 폴더) Agent SDK 세션을 `ANTHROPIC_BASE_URL`=프록시, `ANTHROPIC_AUTH_TOKEN`=더미로 한 턴 돌린다.

실측(진짜 토큰 없이, 두 모드):

- **passthrough**(로컬 OAuth 로그인은 그대로 두고 base URL 만 프록시로): `~/.claude/.credentials.json` 이 있는데도
  CLI 는 `HEAD /` 만 보내고 "Not logged in" 으로 끝냈다. **base URL 을 바꾸면 CLI 는 로컬 OAuth 로그인을 쓰지
  않는다** — 자격증명은 프록시가 끼워야 한다. 이 설계의 방향과 같다.
- **inject**(빈 `CLAUDE_CONFIG_DIR` + `ANTHROPIC_AUTH_TOKEN=worker-dummy`): CLI 는 `HEAD /` 뒤
  `POST /v1/messages?beta=true` 를 `authorization: Bearer worker-dummy-token` 과 `anthropic-beta` 헤더로 프록시에
  보냈다. **전송 계층은 교체 가능하다.** 업스트림 401 을 돌려주면 SDK 는 예외 없이 `result(success)` 안에
  "Not logged in" 을 싣고 끝난다.

아직 못 본 것은 하나 — 프록시가 끼운 **구독 OAuth 토큰을 업스트림이 받는지.** 프록시가 보내는 요청은 CLI 가
직접 보낼 때와 같은 모양이고 OAuth 토큰은 IP 에 묶이지 않으므로 받아들여질 가능성이 높지만, 실측이 2단계
착수의 전제다. 이 스크립트는 운영자의 자격증명을 스스로 읽지 않으므로 운영자가 직접 돌린다. 토큰은 봇이
Railway 에서 실제로 쓰는 `CLAUDE_CODE_OAUTH_TOKEN` 값이 가장 정확하다(같은 종류·같은 값). 운영자 PC 의
`~/.claude/.credentials.json` 에는 계정 로그인이 없다는 것을 실측했다(데스크톱 앱 로그인은 거기 저장되지 않고
MCP 서버 OAuth 항목만 있다) — 그래서 `ASAHI_PROBE_USE_LOCAL_LOGIN` 은 CLI 로 `claude login` 한 기계에서만
뜻이 있다. PowerShell 에서는 토큰이 쉘 히스토리에 남지 않게 `Read-Host` 로 받는다:

```powershell
cd agent
$s = Read-Host "토큰" -AsSecureString
$env:ASAHI_PROBE_TOKEN = [Runtime.InteropServices.Marshal]::PtrToStringAuto([Runtime.InteropServices.Marshal]::SecureStringToBSTR($s))
npx.cmd tsx src/scripts/llmProxyProbe.ts
Remove-Item Env:ASAHI_PROBE_TOKEN
```

`verdict` 가 "성공" 이면 §4.1 이 실측된 것이다. 토큰은 메모리에만 있고 스크립트는 헤더 값을 기록하지 않는다.

**실측 결과(2026-09-05 저녁, 운영자 PC, Railway 의 `CLAUDE_CODE_OAUTH_TOKEN` 값으로): 성공.** 로컬 자격증명이 없는
세션(빈 `CLAUDE_CONFIG_DIR`, 더미 `ANTHROPIC_AUTH_TOKEN`)이 루프백 프록시를 거쳐 `POST /v1/messages?beta=true`
두 번 모두 200 을 받고 "OK" 로 답했다(모델 `claude-sonnet-5`, 2.3초). 즉 **구독 OAuth 토큰은 프록시가 끼워도
받아들여진다** — §4.1 의 구조가 성립하고 2단계 착수의 전제가 채워졌다. 토큰은 108자·`sk-ant-oat` 접두였다.
붙여 넣기 과정에서 두 번 실패한 원인은 가려진 표시 값을 복사한 것이었다(길이 40~48, 헤더에 못 쓰는 문자) —
스크립트가 그 경우를 검사해 사유를 말하게 했다.
"실패(401)" 이면 구독은 프록시 뒤에서 쓸 수 없다는 뜻이고, 그때는 이 설계를 다시 봐야 한다 — API 키는 선택지가
아니므로 남는 길은 토큰을 세션 계정에 두는 것(§9 가 거부하는 것)이거나 얇은 워커 유지다.

## 5. 격리 대신 자원 관리 (운영자 결정, 2026-09-05)

부원별 OS 계정·컨테이너는 채택하지 않는다 — 다섯 명만 동시에 써도 하이엔드 PC 가 감당하기 어렵다고 운영자가
판정했다. 그리고 격리를 두려던 이유의 대부분(자격증명 보호)은 §4 로 해소됐다: 세션 계정 B 에 자격증명이 없다.
남는 위험 — 부원끼리 파일을 볼 수 있다, 기계를 무겁게 쓸 수 있다 — 는 지금 `sh_exec` 에서 이미 받아들인 것과
같다([위험 등록부](../../security/risk-register.md) §2·§5).

기준은 **같은 계정 B, 부원별 작업 폴더(`C:\asahi-workspace\<userId>\`, 지금 그대로) + 부원별 `CLAUDE_CONFIG_DIR`**
이다. 격리 대신 다음을 둔다.

- **동시 실행 상한**: 워커당 동시 세션 N(기계 사양으로 정한다 — 시작은 2). 넘치면 봇이 대기열에 두고
  "앞에 M명, 잠시 기다려 주세요" 를 진행 표시로 낸다. 같은 대화의 재진입 금지는 지금 `turnChains` 그대로.
- **유휴 비용 0**: Claude Code 프로세스는 턴이 끝나면 내려간다. 세션은 전사 파일일 뿐이라 대기 중인 부원은
  자원을 쓰지 않는다.
- **공유 브라우저**: 브라우저 MCP 는 기계에 하나(Playwright 서버 하나)만 띄우고 세션별 컨텍스트로 나눈다.
  Chromium 을 사람마다 띄우는 것이 가장 무거운 부분이라 여기서 줄인다.
- **부원 프로필의 기본값**: 서브에이전트 끔(또는 1), effort 낮음, Sonnet 5. 운영자만 전부 연다.
- **개발서버 1인 1개** 상한은 지금(`proc_*`) 그대로 세션 안의 규칙으로 옮긴다.
- 뒷날의 선택지: 윈도우 잡 오브젝트로 세션 프로세스 트리의 메모리 상한, 또는 리눅스 호스트로 옮기면 cgroups.
  둘 다 지금은 하지 않는다.

## 6. 도구·MCP·플러그인 — 프로필

능력은 봇이 `turn.start` 에 싣는 **프로필**로 정한다. 지금 `allowedToolsFor` 가 하는 일이 프로필 계산이 된다.

| 프로필 | 모델·effort | 내장 도구 | MCP | 플러그인·스킬 | 서브에이전트 |
|---|---|---|---|---|---|
| 소유자(DM·서버) | Opus 5 · 기본 | 전부, 관리자 스코프(워크스페이스 루트) | 허브: Supabase(읽기)·Railway·GitHub / 로컬: 브라우저 | 전부 | 열림 |
| 손님(DM·서버) | Sonnet 5 · 낮음 | 전부 — 작업 폴더가 그 부원 스코프 | 로컬: 브라우저 / 허브: 부원용으로 연 것만(이미지 생성 등) | 개발·문서 스킬 | 끔 |
| 무인 턴 | 지금 그대로 | 없음(봇 안) | 없음 | 없음 | 없음 |

- **소유자 DM 의 워커**: 개인 워커가 빠지므로 소유자 DM 도 공유 워커로 간다 — 관리자 스코프(폴더 제한 없음).
  `workerSelect.ts` 의 "소유자 DM 은 개인 워커" 규칙을 "개인 워커가 없으면 공유 워커" 로 바꾼다. 소유자
  서버 채널은 이미 공유 워커 관리자다.
- **MCP 허브(봇, 계정 A)**: 비밀이 필요한 서버(Supabase·Railway·GitHub·이미지 생성 API)는 A 에서 stdio 로 띄우고
  루프백 HTTP MCP 로 노출한다. 세션의 `mcpServers` 에 `http://127.0.0.1:P/mcp/<이름>` 을 작업 토큰 인증으로
  붙인다. **비밀은 A 를 떠나지 않는다.** 어느 서버를 어느 프로필에 여는지는 봇의 표 하나다.
- **로컬 MCP(계정 B)**: 브라우저·화면 캡처(Playwright 류). 비밀이 없다. §5 의 공유 서버 하나.
- **플러그인·스킬**: 지금은 `agent/skill-plugin/` 에 복사해 커밋한 문서형 스킬만 돈다. 풀 하네스에서는 B 계정에
  설치된 Claude Code 플러그인이 그대로 쓰이므로 리포 밖 공개 플러그인도 프로필로 열 수 있다. 라이선스가 재배포를
  막는 스킬은 리포에 넣지 않고 기계 설치로만 다룬다.
- **git 자격증명**: 지금의 셸 토큰 주입(`shellGitArgs`)을 세션 환경변수로 옮긴다 — `turn.start` 에 `GIT_CONFIG_*`
  와 헬퍼를 얹으면 Bash 의 git 이 그대로 인증한다. 수명·범위는 지금과 같다.

## 7. 봇↔세션 러너 프로토콜

`remote/protocol.ts` 에 프레임 넷을 더한다. 기존 도구 호출 프레임은 전환 기간 동안 공존한다.

| 프레임 | 방향 | 내용 |
|---|---|---|
| `turn.start` | 봇→러너 | 작업 id, 부원 id, 작업 폴더, 시스템 프롬프트, 프롬프트, resume, 프로필(도구·MCP·플러그인·모델·effort), 작업 토큰, git 환경 |
| `turn.event` | 러너→봇 | SDK 스트림 요약(도구 호출·결과·답변 시작) — 지금 `ProgressUpdate` 와 같은 모양 |
| `turn.result` | 러너→봇 | 최종 텍스트, 세션 id, 성패, 사용량 요약 |
| `turn.cancel` | 봇→러너 | 대화 리셋·타임아웃 때 세션 중단 |

- 러너는 부원별로 세션 하나, 전체는 §5 의 동시 상한. 초과분은 봇이 대기열에 둔다.
- 루프백이라 지연·프레임 상한 걱정이 없지만 큰 것(파일)은 §8 의 HTTP 로 간다 — 두 배치에서 같은 코드다.
- 러너 재시작·자동 갱신: 진행 중 작업이 있으면 센티넬이 기다리는 지금 규칙(`workerShutdown.ts`) 그대로.

**구현(2026-09-06, 2단계):** 프레임은 `remote/protocol.ts`(hello 에 `mode` 추가 — `harness` 인 워커에게만 봇이 `turn.start`
를 보낸다), 허브 쪽은 `hub.startTurn`(이벤트 콜백 + 결과 프로미스 + `cancel`, 30분 상한, 끊김·재연결·종료 때 실패로 정리),
워커 쪽은 `workerClient.ts` 가 `remote/sessionRunner.ts` 에 위임한다. 러너는 부원별로 세션 하나(같은 부원의 두 번째 turn.start
는 즉시 실패), `permissionMode: bypassPermissions`, 서브에이전트가 꺼진 프로필은 `disallowedTools: ["Task"]`. 봇의 디스패치는
`core/agent.ts` 의 `decideHarnessDispatch`(플래그·소유자·harness 워커·이미지 없음·무인 아님·토큰 발급기·채널·작업 폴더) —
하나라도 빠지면 옛 경로라 되돌리기가 플래그 하나다. 세션 없음(resume 실패)은 옛 경로와 같은 문구로 던져 core.ts 의 재시도
경로를 그대로 탄다. 이미지 턴·손님 턴·무인 턴은 2단계에서 새 경로를 타지 않는다.

## 8. 파일 반환

산출물(이미지·PDF·캡처)을 디스코드로 돌려주는 경로 — 로드맵 7번. 배치와 무관하게 먼저 만든다.

- 봇에 `POST /files`(작업 토큰 인증, 크기 상한)를 둔다. 세션의 `send_file(path)` 도구가 그 부원 폴더 안 파일을
  올리고, 봇이 그 대화 채널에 첨부로 보낸다. 디스코드 첨부 상한을 넘으면 그 사실을 말한다.
- 얇은 워커 기간에는 `send_file` 을 원격 도구로 하나 더 만들어 같은 엔드포인트를 쓴다. 풀 하네스에서는 세션
  쪽 인프로세스 MCP 도구가 된다 — 엔드포인트는 같다.

**구현(2026-09-05 저녁, 0단계):** 작업 토큰은 `core/jobToken.ts`(HMAC-SHA256·부팅마다 난수 비밀·2시간·클레임은
작업 id·부원·대화·채널·만료). `POST /files` 는 `core/fileReturn.ts` — 토큰 없으면 본문을 읽기 전에 401, 상한(8MB,
첨부 올리기와 같은 `FILE_LIMITS.maxBytes`)은 `content-length` 와 스트림 양쪽에서 413, 성공 시 `assistant_file`
이벤트(다섯째 이벤트 — 유일하게 바이트를 나른다). 첨부를 보낼 채널은 요청이 아니라 토큰의 `channelRef` 가 정한다.
어댑터는 첨부만 보내고 진행 표시는 끝내지 않는다. 워커의 `send_file` 은 경로 게이트 뒤 `stat` 으로 상한을 먼저
거르고, 토큰은 `upload.token`(봇 주입 — 모델이 끼운 값은 덮어쓴다), 주소는 `HUB_URL` 에서 `fileReturnUrlOf` 로 유도한다
(`wss://h/worker` → `https://h/files`). 이 토큰 형식은 2단계의 `ANTHROPIC_AUTH_TOKEN` 에 그대로 쓴다.

## 9. 위협 판단 — 토큰 탈취를 중심으로

| 경로 | 결과 |
|---|---|
| 부원의 셸·세션(계정 B, 표준 사용자) | A 의 파일은 NTFS 권한으로, A 프로세스의 환경·메모리는 관리자 권한이 없어 못 읽는다. **토큰에 닿지 않는다** |
| 프롬프트 인젠션으로 세션이 환경변수를 밖으로 보냄 | 세션 환경에 있는 것은 2시간짜리 작업 토큰뿐이고, 그건 `127.0.0.1` 프록시에만 통한다. **미니PC 밖에서는 쓸 수 없다** — Railway 배치보다 오히려 좁다 |
| B 에서 관리자로 올라가는 윈도우 취약점 | A 의 환경을 읽는다. 지금 설계에서도 그 순간 워커 신원과 부원 전원의 파일이 넘어가므로 새 종류의 구멍은 아니지만, **노출되는 것에 구독 토큰이 더해진다** |
| 물리 접근 + 관리자 암호, USB 부팅 | 디스크의 모든 것. 오늘도 워커 토큰은 이렇게 넘어가지만, 새 설계에서는 구독 토큰도 함께 |

Railway 배치와 정확히 하나 다르다: **미니PC 의 관리자 권한이나 물리적 통제가 뚫리면 구독 토큰도 넘어간다.**
부원 다섯이 셸을 쓰는 위협은 두 배치가 같다. 그 차이를 줄이는 것:

- A 도 관리자가 아닌 표준 계정. 봇은 관리자 권한이 필요 없다. 관리자 계정은 따로, 강한 암호, 로그인 상태로 두지 않기.
- A 의 `.env` 는 A 프로필 폴더 안(NTFS 기본 권한 = 그 사용자와 관리자만). 공유 폴더·코드 체크아웃에 두지 않는다.
  BitLocker 를 켜면 USB 부팅으로 디스크를 읽는 길이 막힌다. DPAPI 사용자 범위 암호화는 뒷날의 선택지.
- 윈도우 업데이트 자동 — 권한 상승 취약점은 대부분 패치 지연에서 온다.
- **탐지**: 프록시가 부원별 사용량을 기록하므로, 구독 한도가 봇의 기록보다 빨리 닳으면 토큰이 밖에서 쓰이는
  신호다.
- **회수 절차**를 `deploy/incident-runbook.md` 에 둔다 — 새 `setup-token` 발급, 옛 토큰 무효화, A 의 `.env` 교체,
  봇 재시작. 몇 분이면 끝나야 한다.

그 외:
- **프롬프트 인젠션의 도달 범위는 넓어진다** — 내장 Bash·WebFetch·서브에이전트가 손님 세션에서도 돈다. 종류는
  지금 `sh_exec` 와 같다. 완화는 페르소나의 신뢰 경계 규칙, 손님 프로필의 서브에이전트 끔, 그리고 무인 턴은
  여전히 도구 없이 봇 안에서 돈다는 것.
- **MCP 허브**는 신원별 허용 목록이 유일한 경계 — 손님 프로필에 Supabase·Railway 를 열지 않는다. 서버를 추가하는
  커밋이 곧 승인 절차다(스킬 하네스와 같은 원칙).
- **미니PC 가 꺼지면 봇도 꺼진다.** 지금은 워커가 꺼져도 대화·정기 게시는 됐다. 미니PC 가 실제로 24시간 도는
  것이 이 배치의 전제고, 그렇지 않은 날은 봇 전체가 없다 — 운영자가 받아들인 대가다.

## 10. 고르지 않은 것

| B | 세션 계정(B)에 구독 토큰을 둔다 | 셸 한 줄로 읽히고, 에이전트가 읽는 텍스트의 인젠션 한 줄로도 나간다. 봇을 거치지 않고 쓸 수 있어 부원별 한도·모델 고정·기록이 전부 무력해진다 |
| C | 부원마다 API 키 | 비용상 API 키 자체가 선택지가 아니다(운영자) |
| D | Railway 를 계속 둔다(봇만 클라우드, 세션은 미니PC) | 기계 두 대의 함정이 그대로 남고, 작업 토큰이 인터넷에서 통하는 주소로 발급된다. 얻는 것은 "미니PC 가 통째로 뚫려도 토큰은 남는다" 하나 — 운영자가 단일 호스트를 택했다 |
| E | 부원별 OS 계정·컨테이너 | 성능 부담(운영자 판정). 자격증명이 B 에 없으므로 격리의 주된 이유도 사라졌다 |
| F | OpenClaw·Hermes 로 교체하고 구독제로 개조 | 게이트웨이가 도구 기계에서 도는 구조라 자격증명 문제가 같고, 구독 개조는 약관 위험의 정면. 신원·스코프·단기 토큰·브랜치 정책을 남의 코드에 다시 심고 포크를 유지해야 한다. 부품·아이디어로만 참고 |
| G | 웹훅·실시간 UI | 채널의 몫. 나중에 어댑터로 |

## 11. 단계

각 단계는 독립적으로 병합·배포되고 되돌릴 수 있다. 순서를 이렇게 잡은 이유: **봇 이사(1단계)를 먼저** 해서 기계
두 대의 함정을 없애고, 그 위에서 하네스를 바꾼다 — 한 기계에서 디버그하는 편이 훨씬 싸다.

| 단계 | 내용 | 완료 기준 | 되돌리기 |
|---|---|---|---|
| 0 | **파일 반환**(§8): `POST /files` + 얇은 워커의 `send_file` | 부원이 만든 이미지가 디스코드 첨부로 돌아온다 | 도구 하나 제거 |
| 1 | **봇 이사**: 미니PC 계정 A 에 봇을 작업 스케줄러로 등록, 허브를 `127.0.0.1` 에 묶고 워커의 `HUB_URL` 을 루프백으로, 자동 갱신을 A 도 갖게. 코드 변경은 최소(허브 바인드 설정, 봇 커밋을 Railway 변수 대신 git 에서 읽기). **컷오버**: Railway 서비스 정지 → A 작업 시작(디스코드 토큰이 하나라 둘을 동시에 띄우지 않는다) | 미니PC 봇이 지금과 같은 기능을 하고, `runtime_info` 의 봇 커밋과 워커 커밋이 같은 갈래가 된다 | A 작업 정지 → Railway 재개 |
| 2 | **프록시 + 세션 러너**: 인증 프록시·작업 토큰·`turn.*`·`WORKER_MODE=harness`·프로필 계산. 소유자 턴만 새 경로(플래그) | 소유자가 디스코드에서 내장 도구·서브에이전트·resume 이 도는 턴을 실사용으로 확인. B 에 자격증명이 없다 | 플래그 끄기 → 얇은 도구 경로 |
| 3 | **프록시 운영화**: 모델 고정·사용량 기록·부원별 상한·429 안내·소유자 우선 | 거절·만료·한도가 사용자 문구로 나오고 표에 남는다 | — |
| 4 | **MCP 허브·브라우저·플러그인·파일 반환 로컬화**: 소유자 프로필에 Supabase·Railway·GitHub 허브 MCP, B 에 공유 브라우저 MCP, 공개 플러그인 설치 절차 | 운영자가 디스코드에서 DB 를 조회하고 localhost 화면을 캡처해 첨부로 받는다 | 프로필에서 빼기 |
| 5 | **부원 개방 + 자원 관리**: 동시 실행 상한·대기열 안내·손님 프로필. 격리 실검증(B 에서 A 의 `.env`·프로세스 환경에 닿지 않는 것). **Railway 종료** | 두 부원이 동시에 각자 폴더에서 세션을 돈다. 스모크 통과 | Railway 재개 절차를 문서에 남긴다 |
| 6 | **얇은 도구 은퇴**: 원격 `fs_*`·`sh_exec`·`proc_*`·발행 실행기·1차 필터 제거. ADR 0002·0006 대체 ADR. 능력 모델·위험 등록부·온보딩 함정 절 재작성 | 모든 도구 턴이 새 경로. 옛 프레임 삭제 | — |

## 12. 운영자가 해야 하는 것(코드 밖)

1. **§4.4 프로브**를 미니PC 나 운영자 PC 에서 구독 토큰으로 한 번 돌린다 — 2단계 착수의 전제.
2. **미니PC 준비(1단계 전)**: 표준 계정 `asahi-bot` 생성, Node 22 확인, **A 의 프로필 폴더 안**
   `C:\Users\asahi-bot\asahi-bot` 에 리포 클론(B 의 `C:\asahi-worker` 와 별개 — `C:\` 루트에 두면 윈도우 기본 ACL 로
   B 가 `.env` 를 읽는다), 같은 곳에 `.env`(Railway 변수 이관: 디스코드·DB·깃허브 App·구독 토큰, `HUB_BIND=127.0.0.1`,
   `BOT_SENTINEL`), 작업 스케줄러에 `asahi-bot`(시작 시)·`asahi-bot-update`(5분) 등록. 절차는
   `deploy/minipc-단일호스트-셋업.md`(2026-09-05 밤 작성).
3. **컷오버**(1단계): Railway `asahi` 서비스 정지 → A 작업 시작 → 디스코드에서 `runtime_info` 확인. 문제면 역순.
4. **기계 보안**(§9): A·B 모두 표준 계정, 관리자 계정 분리, 윈도우 업데이트 자동, BitLocker 권장.
5. **동시 실행 상한** 값(5단계) — 미니PC 사양(RAM·CPU)을 보고 정한다. 시작은 2.
6. 4단계 때 허브 MCP 에 쓸 서비스 키(Supabase 읽기 전용 등)를 A 의 `.env` 에 둔다.

  `query()` 로, 프레임은 `remoteProtocol.test.ts` 관례로, 프로필 계산은 `allowedToolsFor` 테스트를 확장.
