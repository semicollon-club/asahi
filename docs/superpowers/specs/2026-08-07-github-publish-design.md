# 깃허브 발행 — 설계

## 1. 무엇을 고치는가

**부원이 만든 것을 볼 방법이 없다.**

지금 아사히는 채팅으로 프론트엔드를 만들 수 있고, `proc_start` 로 개발서버를 띄울 수도 있다.
그런데 그 서버가 **무엇을 렌더링하는지 확인할 경로가 없다.** 개발서버는 미니PC 의
`localhost` 에 떠 있고, 봇은 Railway 에 있으며, 부원은 디스코드 창만 보고 있다. 아무리 잘
만들어도 만든 사람이 결과를 못 본다.

같은 뿌리에서 두 번째 문제가 나온다. **작업한 파일을 돌려줄 수 없다.** 올리기(디스코드 →
워커)는 2026-08-01 에 됐지만 그 반대 방향은 없다(`docs/status/STATUS.md` — "내려받기(워커 →
디스코드)는 아직 없다").

이 문서는 그 둘 중 **발행**만 다룬다. 왜 그렇게 잘랐는지는 §2 다.

## 2. 왜 파일 내려받기가 아니라 발행인가

먼저 검토한 것은 파일 내려받기였다. 워커가 파일을 읽어 봇으로 보내고 봇이 디스코드에 첨부로
올리는 경로다. **하드 제약에 걸린다.**

`MAX_FRAME_CHARS = 1_000_000`(`agent/src/remote/hub.ts`)이 허브 로직과 전송 계층
(`index.ts` 의 `maxPayload`) 양쪽에서 강제된다. 기존 `result` 프레임에 base64 로 실으면 실효
상한이 약 750KB 다. 그런데 `agent/src/core/attachments.ts` 의 8MB 상한은 이렇게 정당화돼 있다.

> 이 값은 내려받기 방향의 디스코드 첨부 한도와 짝을 맞춘 것이다. … 두 방향의 상한이 다르면
> "올라갔는데 못 돌려받는" 파일이 생긴다.

즉 가장 단순한 구현이 그 주석이 막으려던 상태를 정확히 만든다. 상한을 지키려면 청크 분할이나
외부 스토리지 경유가 필요하고, 둘 다 이 문서 하나에 담기엔 크다.

**그리고 발행이 원래 문제를 더 잘 푼다.** 스크린샷은 정지 화면 한 장이지만, 깃허브에 올라간
프로젝트는 CI/CD 를 붙이면 실제로 도는 주소가 된다 — 만든 사람도 남도 클릭해 볼 수 있고,
결과물이 대화가 끝나도 남는다.

**대체가 아니라 보완이라는 점은 분명히 한다.** 발행 → 배포는 피드백 루프가 분 단위다. UI 를
몇 번씩 고쳐가며 다듬을 때는 초 단위로 보이는 스크린샷이 여전히 빠르고, 생성한 PDF 한 장
같은 산출물은 깃허브에 올릴 성격이 아니다. 스크린샷과 범용 파일 내려받기는
[로드맵](../../status/ROADMAP.md)에 별도 항목으로 남는다.

## 3. 자격증명 모델 — 이 설계의 중심

가장 자연스러워 보이는 구현("미니PC 에 동아리 깃허브 계정을 연결한다")은 채택하지 않는다.
**문서화된 전제조건을 정면으로 깬다.**

[deploy/worker-셋업.md](../../../deploy/worker-셋업.md)는 권장이 아니라 "이 설계가 요구하는
전제조건"으로 이렇게 적는다.

> 그 계정 프로필에 SSH 키·`.env`·저장된 브라우저 자격증명을 두지 않는다. `sh_exec` 는 그
> 계정이 읽을 수 있는 모든 것을 읽을 수 있다.

부원은 누구나 `role='allowed'` 면 `sh_exec` 를 받고, 폴더 격리는 셸에 적용되지 않는다
([risk-register](../../security/risk-register.md) §2·§5). 미니PC 에 깃허브 토큰이나 SSH 키를
두면 부원 한 명이 셸 한 줄로 그것을 읽어, **디스코드 밖에서 아사히를 거치지 않고 영구히**
동아리 조직에 푸시할 수 있다. 봇이 강제하는 소유권 검사(§5)도 함께 무의미해진다 — 그건
아사히를 통할 때만 걸리는 제약이기 때문이다.

**그래서 자격증명은 봇이 든다.** 봇은 Railway 에 있고 부원의 셸이 닿지 않는다.

- 봇이 **GitHub App 개인키**를 환경변수로 보유한다(`GITHUB_APP_ID`·`GITHUB_APP_PRIVATE_KEY`·
  `GITHUB_APP_INSTALLATION_ID`·`GITHUB_ORG`).
- 발행 요청마다 설치 액세스 토큰을 **그 요청에만 맞춰** 발급한다 —
  `repositories` 로 **대상 리포 하나**, `permissions` 로 **`contents: write` 하나**, 만료는
  GitHub 이 강제하는 **최대 1시간**.
- 그 토큰만 워커로 넘긴다. 미니PC 디스크에는 아무것도 남지 않는다.

토큰이 새더라도 피해가 한 시간·한 리포·쓰기 한 종류로 갇힌다. 이것은 완화이지 차단이
아니다 — 남는 구멍은 §11 에 적는다.

## 4. 리포 배치

**프로젝트마다 리포 하나**(`<org>/<프로젝트명>`), **비공개 기본**.

프로젝트별 리포를 고른 이유는 CI/CD 다. 한 리포에 `<회원번호>/<프로젝트명>` 폴더로 쌓으면
배포 연결이 프로젝트별로 갈라지지 않아, 이 설계의 목적(만든 것이 도는 주소가 된다)이
반쪽이 된다.

비공개를 기본으로 둔 이유는 §6 의 제외 규칙이 뚫렸을 때의 피해 크기다. 부원 폴더에 API 키가
남아 있는 채로 발행되면, 공개 리포에서는 그 순간 유출이 확정된다. 비공개면 되돌릴 여지가 있다.

**대가를 적어 둔다**: 무료 조직은 비공개 리포에서 GitHub Pages 를 쓸 수 없다. 배포는
Vercel·Netlify 처럼 비공개 리포를 무료로 받는 곳을 쓴다. 이 선택은 CI/CD 단계에서 다시 본다.

### 4.1 조직이 필수인 이유 — 개인 계정으로는 자동 생성이 안 된다

리포 자동 생성은 **조직에서만 된다.** 설치 액세스 토큰(IAT)으로 부를 수 있는 엔드포인트가
갈린다([permissions-required-for-github-apps](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps),
2026-08-07 확인).

| 엔드포인트 | IAT 로 가능? | 권한 |
|---|---|---|
| `POST /orgs/{org}/repos` | **가능** | Administration (write) |
| `POST /user/repos` | **불가** — 사용자 액세스 토큰(UAT)만 | — |
| `Contents` (git push) | 가능 | Contents (write) |

즉 개인 계정에 발행하려면 사용자 액세스 토큰이 필요한데, 그건 사람의 OAuth 동의를 거쳐야
하고 만료·갱신 모델이 달라 §3 의 "요청마다 짧은 토큰" 구조가 성립하지 않는다. **조직을 쓰는
것이 이 설계의 전제다.**

### 4.2 확정된 대상

**조직: `semicollon-club`**(2026-08-07 생성, Free 플랜). 소유자는 `semicollon-git`(동아리 계정)과
`wwoosshh`(운영자) 둘이다 — 소유자가 하나뿐이면 그 계정을 잃었을 때 조직 전체가 잠긴다.

기존 `semicollon-git` 개인 계정의 리포 3개(`semicollon_backend`·`semicollon_db`·
`semicollon_frontend`)는 이 설계의 대상이 아니다. 조직으로 옮길지는 별개 판단이다.

**남은 수동 절차**: GitHub App 생성·설치는 사람이 한 번 해야 한다(§14).

## 5. 소유권 — 누가 어느 리포를 발행할 수 있는가

**모델이 리포를 고르지 않는다.** 모델은 프로젝트 이름만 말하고, 봇이 그 이름을 소유권
기록에 대조해 실제 대상을 정한다. 파일 올리기에서 저장 위치를 봇이 정한 것
(`uploadDirFor`, `attachments.ts`)과 같은 원칙이다 — 모델이 정하면 부원이 남의 리포에
푸시할 수 있다.

새 테이블 `projects` 를 둔다.

```
projects(
  id, repo_name, owner_user_id, created_ts, last_push_ts
)
```

**발행 소스 경로는 저장하지 않는다.** 매번 요청자의 신원에서 계산한다(§6) — 저장해 두면 그
사람의 작업 폴더가 바뀌었을 때 기록과 실제가 갈리고, 그 갈림이 곧 "남의 폴더를 발행"으로
샐 수 있는 자리가 된다. 계산값 하나만 두면 갈릴 것이 없다.

**공개 여부도 컬럼으로 두지 않는다.** 전부 비공개로 고정했고(§4) 부원이 고르지 않으므로,
컬럼은 항상 같은 값만 갖는다. 공개 선택을 실제로 열게 되면 그때 더한다.

- `repo_name` 은 조직 안에서 유일하다(GitHub 자체 제약과 같다).
- 요청한 이름이 **없으면** 리포를 만들고 요청자를 소유자로 기록한다.
- **있고 소유자가 요청자면** 그 리포에 푸시한다.
- **있고 소유자가 다르면 거부한다.** 이름 충돌로 남의 리포를 덮어쓰는 경로를 여기서 끊는다.

소유자(운영자)는 이 검사를 우회하지 않는다 — 관리가 필요하면 DB 를 직접 고치는 편이,
"소유자는 아무 리포나 덮어쓸 수 있다"는 분기를 코드에 남기는 것보다 안전하다.

## 6. 무엇을 올리는가

**발행 소스도 봇이 정한다.** 모델은 프로젝트 이름만 주고, 봇이 절대경로를 계산한다 —
`<그 사람의 scopeDirs[0]>/<프로젝트명>`. 손님은 이미 자기 폴더로 좁혀져 있으므로
(`workerSelect.ts` 의 `scopeDirs`) 남의 폴더를 발행할 방법이 없다.

**제외 규칙은 편의가 아니라 방어선이다.** 부원 폴더에 남은 비밀이 그대로 발행되는 것을
막는 유일한 장치다.

기본 제외: `node_modules/`, `.git/`, `.env`·`.env.*`, `dist/`, `build/`, `.next/`, `*.log`,
`*.pem`, `*.key`.

- 제외는 **워커가 집행한다** — 파일이 실제로 있는 기계다.
- 제외 후 총 용량 상한을 둔다(초기값 50MB). 넘으면 발행하지 않고 무엇이 컸는지 알린다.
- **잘렸으면 명시한다.** 조용히 빼면 부원이 "올렸는데 왜 안 도나"로 오해한다 — `fs_tree`
  가 상한에 걸렸을 때 명시하기로 한 것과 같은 원칙이다.

비밀 스캔은 이 단계에서 만들지 않는다. 비공개 기본(§4)이 그 자리를 대신하고, 스캔을
어설프게 넣으면 "검사했으니 안전하다"는 잘못된 신뢰가 생긴다.

## 7. 도구와 게이팅

도구 하나를 더한다 — `publish_project(name, message?)`.

- **워커 연결이 전제다.** 다른 원격 도구와 같은 축(`allowedToolsFor`)을 쓴다.
- **소유자·손님 모두 쓴다.** 등록된 부원(`role='allowed'`)이 만든 것을 발행하는 것이 이
  기능의 목적이다.
- **사람이 지켜보지 않는 턴에서는 닫는다** — 유휴 요약 턴과 정기 게시 턴. `remember` 를 그
  턴에서 막은 것과 같은 이유다: 웹 검색 결과나 이전 세션에 심긴 지시가 조직 리포에 푸시를
  일으키면 안 된다. 발행은 되돌리기 어려운 바깥 방향 동작이라 이 축이 특히 중요하다.

## 8. 귀속

커밋의 `author` 는 발행한 부원(`users.display_name`), `committer` 는 App 이다. 누가 만들었는지
기록에 남아야 동아리 활동으로 의미가 있다. `display_name` 이 비어 있으면 디스코드 userId 로
폴백한다 — `recall` 의 작성자 표시가 "(작성자 미상)" 으로 폴백하는 것과 같은 자리다.

이메일은 GitHub 의 `noreply` 형식을 쓰고 부원의 실제 이메일은 묻지도 저장하지도 않는다.

## 9. 워커 쪽 실행

봇이 `hub.call(workerId, "git_publish", {...})` 로 부른다. `file_fetch` 와 같이 **모델에게
노출되지 않는 봇 전용 도구**다 — 모델이 URL 이나 토큰을 정하게 하면 그 표면 자체가 생긴다.

워커가 받는 것: 소스 절대경로, 리포 clone URL, 1시간 토큰, 커밋 메시지, author 정보.

워커가 하는 것: 경로를 `checkPath` 로 최종 판정 → 제외 규칙 적용 → `git init`(없으면) →
`add`/`commit --author` → `push`.

**토큰을 디스크에도 명령줄에도 남기지 않는다.** `git remote add` 로 토큰이 든 URL 을 박으면
`.git/config` 에 평문으로 남아 그 부원이 `fs_read` 로 바로 읽는다. 명령줄 인자로 주면 윈도우
에서 같은 계정의 프로세스 목록(`Get-CimInstance Win32_Process` 의 `CommandLine`)에 노출된다.
환경변수로 넘기고 `credential.helper` 가 그 값을 읽게 한다.

## 10. 테스트 전략

**유닛으로 고정할 것** — 순수 함수로 떼어낸다.

| 대상 | 무엇을 |
|---|---|
| 소유권 판정 | 없는 이름·내 것·남의 것 세 갈래(§5) |
| 발행 소스 경로 계산 | 손님이 자기 폴더 밖을 못 가리키는 것(§6) |
| 제외 규칙 | 기본 목록·용량 상한·잘림 표시(§6) |
| 도구 게이팅 | 유휴 요약 턴·정기 게시 턴에서 닫히는 것(§7) |
| 커밋 author 조립 | `display_name` 없을 때 폴백(§8) |
| `projects` 리포 | pg-mem — 기록·조회·중복 이름 |

**유닛이 못 잡는 것 → 스모크로 옮긴다.** GitHub API 왕복(토큰 발급·리포 생성·푸시)은
`runGit`(`gitCommit.ts` 의 패턴)처럼 주입 가능한 이음매로 두고, 실제 왕복은
`deploy/smoke-test.md` 항목으로 검증한다.

- 토큰이 실제로 1시간·단일 리포·`contents:write` 로 발급되는가(발급 응답으로 확인)
- 푸시 후 `.git/config` 와 프로세스 목록 어디에도 토큰이 없는가 — **§9 의 주장을 실제로 확인
  하는 항목이라 빠뜨리면 안 된다**
- 남의 프로젝트 이름으로 발행을 시도했을 때 도구 원문으로 거부되는가(음성 테스트)

## 11. 남는 위험

- **푸시가 도는 동안의 토큰 관찰.** 같은 OS 계정의 `sh_exec` 로 진행 중인 git 프로세스의
  환경을 들여다볼 여지는 남는다. 1시간·단일 리포·`contents:write` 가 피해를 가두는 완화책
  이고 원천 차단이 아니다. 실질 경계는 여전히 미니PC 의 OS 계정이다(risk-register §2·§5).
- **App 개인키의 권한 폭.** 리포 생성을 위해 조직 수준 권한이 필요하다. 이 키가 새면 조직
  전체가 노출된다 — 키는 Railway 환경변수에만 두고 리포에 넣지 않는다.
- **제외 규칙은 목록 기반이다.** 목록에 없는 이름의 비밀 파일은 걸러지지 않는다. 비공개
  기본(§4)이 이 위험의 크기를 줄이지만 없애지는 않는다.
- **되돌리기.** 잘못 발행한 것을 아사히가 지우는 경로는 만들지 않는다(`contents:write` 로는
  리포 삭제가 안 된다). 사람이 GitHub 에서 직접 지운다 — 되돌리기를 자동화하면 그 경로가
  곧 파괴 경로가 된다.

## 12. 고르지 않은 선택지

| | 방식 | 왜 아닌가 |
|---|---|---|
| A | 미니PC 에 동아리 깃허브 계정 연결 | §3 — 문서화된 전제조건을 깬다. 부원 한 명이 셸 한 줄로 영구 자격증명을 가져간다 |
| B | 워커가 파일을 봇에 넘기고 봇이 GitHub API 로 커밋 | 자격증명은 안전하지만 §2 의 전송 문제가 그대로 돌아온다 |
| C | 부원마다 자기 GitHub OAuth 연결 | 귀속은 가장 정확하다. OAuth 흐름·토큰 저장·갱신·동의가 전부 새로 필요해 이 문서 하나에 안 들어간다. 부원이 늘고 귀속이 실제로 문제가 되면 그때 본다 |
| D | 한 리포에 `<회원번호>/<프로젝트명>` 폴더 | 가장 단순하지만 프로젝트별 CI/CD 연결이 갈라지지 않아 목적이 반쪽이 된다(§4) |

## 13. 이 문서가 다루지 않는 것

- **CI/CD 연결** — 발행이 먼저 돌아야 무엇을 배포할지가 실물로 정해진다. 다음 단계다
- **스크린샷·범용 파일 내려받기** — §2. 로드맵의 별도 항목
- **브랜치·PR 흐름** — 첫 판은 기본 브랜치에 직접 푸시한다. 부원이 협업하기 시작하면 그때 본다
- **발행 취소·리포 삭제** — §11
- **비밀 스캔** — §6

## 14. 수동 절차 — GitHub App 생성·설치

코드로 대신할 수 없는 부분이다. 조직(`semicollon-club`)에서 사람이 한 번 한다.

1. 조직 Settings → Developer settings → GitHub Apps → **New GitHub App**
2. **Webhook 을 끈다.** 봇은 웹훅을 받지 않는다 — 켜두면 쓰지도 않는 공개 표면이 생긴다
3. 권한: Repository → `Contents: Read and write`, `Administration: Read and write`
   (Administration 은 리포 자동 생성에만 쓰인다 — §4.1)
4. 설치 범위는 **Only on this account**
5. Private key 를 생성해 `.pem` 을 받는다
6. 조직에 App 을 설치한다. 설치 후 URL 의 `/settings/installations/<숫자>` 가 Installation ID 다
7. Railway 환경변수에 등록한다(§15)

**개인키 취급.** `.pem` 은 **리포에 커밋하지 않고, 미니PC 에 두지 않는다.** 미니PC 에 두는
순간 §3 의 근거가 통째로 무너진다 — 부원이 `sh_exec` 로 읽어 조직 전체 권한을 영구히 가져간다.
Railway 환경변수에만 둔다.

## 15. 환경변수

봇 쪽에만 추가된다. 워커 `.env` 는 **한 줄도 바뀌지 않는다** — 그것이 이 설계의 요점이다.

| 변수 | 값 |
|---|---|
| `GITHUB_ORG` | `semicollon-club` |
| `GITHUB_APP_ID` | App 설정 페이지의 숫자 |
| `GITHUB_APP_INSTALLATION_ID` | 설치 URL 의 숫자(§14-6) |
| `GITHUB_APP_PRIVATE_KEY_B64` | `.pem` 전체를 base64 로 인코딩한 한 줄 |

**개인키를 base64 한 줄로 넣는 이유**: PEM 은 여러 줄이고 `-----BEGIN...` 헤더를 갖는다.
줄바꿈이 든 값은 환경변수 경로마다 다르게 다뤄져(`.env` 파서·배포 플랫폼·셸) 조용히 망가지기
쉽다 — 깨진 키는 "인증 실패" 한 줄로만 드러나 원인을 엉뚱한 곳에서 찾게 된다. base64 는 한
줄이라 그 변수가 사라진다. 봇이 읽을 때 디코드한다.

넷 중 하나라도 비어 있으면 발행 도구를 아예 노출하지 않는다 — 스킬 폴더가 없을 때 `plugins`
를 넘기지 않는 것과 같은 원칙이다(부가 능력이 본 기능을 인질로 잡지 않는다).
