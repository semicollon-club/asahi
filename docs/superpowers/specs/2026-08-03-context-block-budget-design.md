# 컨텍스트 블록 — 예산과 경계

## 1. 무엇을 고치는가

새 세션이 열릴 때 주입되는 컨텍스트 블록(`agent/src/core/turnPrep.ts` 의 `buildContextBlock`)에
두 가지 문제가 있다. 둘 다 같은 함수를 고쳐야 해서 한 스펙으로 묶는다.

### 1.1 기억 섹션만 상한이 없다

블록의 다른 섹션은 전부 상한이 있다.

| 섹션 | 상한 |
|---|---|
| 캐릭터 설정 | `CHARACTER_FACT_LIMIT = 40` + 초과 경고 |
| 이전 대화 요약 | 최근 3건 |
| 최근 대화 기록 | 최근 20건 |
| **기억** | **없음** |

`memoriesRepo.sharedOnly()` 와 `forUser()` 에 `LIMIT` 이 없다. 지금은 공용 기억 7건
1,409자라 무해하지만, 2026-08-02 에 "동아리 문서를 주제별로 나눠 저장하라"를 프롬프트에
넣었고 실제로 그렇게 쓰이기 시작했다. 기억 1건 상한이 4,000자이므로 50건이면 최대 20만 자다.

### 1.2 `/새세션` 이 이름과 다르게 동작한다

`/새세션` 은 `conversations.session_id` 를 `null` 로 만들 뿐이다(`core.ts:282`). SDK 세션은
정말로 새로 열린다 — 그 점에서 겉보기 흉내는 아니다.

문제는 그 새 세션이 무엇을 들고 시작하느냐다. `buildContextBlock` 이 **직전 메시지 20개를
원문 그대로** 다시 싣는다(`messages.recent(conv.id, 21)`). 요약이 아니라 전문이다. 이전 요약도
최근 3건 실린다.

즉 **말투는 리셋되고 내용은 이어진다.** 원래 의도가 그랬다 — 그 명령은 *"활발한 DM 이 같은
SDK 세션을 계속 resume 해 페르소나 변경이 반영되지 않는 걸 소유자가 직접 끊는 용도"* 로
만들어졌고(코드 주석), 블록에 "이전 답변 말투를 흉내내지 마라"는 안내까지 있다.

그런데 **사용자가 `/새세션` 에 기대하는 것은 주제를 갈아타는 것**이다. 지금 동작은 그 기대와
어긋나고, 이름과 확인 문구("새로 대화하자")가 그 어긋남을 감춘다. 지금의 동작은 오히려
"정리해서 넘기기"에 가깝다.

## 2. 설계

### 2.1 컨텍스트 바닥선

`conversations` 에 `context_floor_ts BIGINT` 를 더한다. *"이 시각 이전의 대화 내용은 새 세션에
싣지 않는다"* 는 표시다. `NULL` 이면 지금 동작 그대로다.

`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 는 이 리포의 기존 방식이다(`schema.ts:170-171`).

`buildContextBlock` 이 두 섹션을 이 값으로 거른다.

| 섹션 | 필터 |
|---|---|
| `## 최근 대화 기록` | `ts > floor` |
| `## 이전 대화 요약` | `created_ts >= floor` |

**부등호가 다른 것이 의도다.** 요약은 경계 시점에 만들어져 그 이전을 **대신하는** 것이므로
포함되어야 하고, 그 시점 이전의 원문 메시지는 그 요약으로 대체됐으므로 빠져야 한다.

**메시지 id 가 아니라 시각을 쓰는 이유**: id 로 하면 요약(범위를 가진 것)과 메시지(점인 것)를
서로 다른 규칙으로 걸러야 해서 경계가 어긋난다. 시각 하나면 둘 다 같은 축에서 갈린다.

### 2.2 `/새세션` — 끊고 새로 시작

```
session_id = null
context_floor_ts = 지금
```

요약하지 않는다. 이전 대화도 이전 요약도 실리지 않는다.

**기억(`memories`)과 캐릭터 설정은 그대로 간다.** 그것은 "이 대화"가 아니라 아사히가 아는
것이다 — 동아리 회비가 얼마인지는 주제를 갈아탄다고 잊을 일이 아니다. Claude Code 의
`/clear` 가 `CLAUDE.md` 를 유지하는 것과 같은 선이다.

**데이터는 지우지 않는다.** 바닥선은 "컨텍스트에 안 싣는다"는 뜻일 뿐이고 `messages`·
`summaries` 행은 그대로 남는다. 소유자는 `db_query` 로 언제든 볼 수 있다.

### 2.3 `/기억정리` — 요약해서 넘기기

Claude Code 의 `/compact` 에 해당한다.

```
1. 지금 세션을 요약 → summaries 에 저장
2. session_id = null
3. context_floor_ts = 지금
```

요약이 다음 세션에 실리고 원문 20개는 빠진다.

기존 유휴 요약(`core.ts` 의 `summarizeAndClose`)의 기계를 재사용하되 **유휴 검사만 건너뛴다**
(그 함수는 `now - lastActiveTs < idleMs` 면 그냥 돌아간다 — 방금까지 말하던 대화가 정확히 그
경우다). 손님이면 시간당 한도도 똑같이 잡는다 — LLM 턴을 하나 쓴다.

**실패하면 아무것도 바꾸지 않는다.** 요약 턴이 실패했는데 세션과 바닥선을 밀면 **대화를 잃고
대신 받은 것도 없는 상태**가 된다. 실패하면 그대로 두고 그 사실을 말한다. 이것이 유휴 요약과
다른 점이다 — 그쪽은 "요약은 있으면 좋은 것"이라 실패해도 세션을 반드시 닫지만(주석에 근거가
있다), 이쪽은 사용자가 **요약을 받으려고** 부른 것이다.

**요약할 세션이 없으면**(`session_id` 가 `null`) 그렇게 말한다. 조용히 성공한 척하지 않는다.

### 2.4 타임스탬프 하나로 정한다

`/기억정리` 는 `const t = now()` 를 한 번 구해 **바닥선과 요약의 `created_ts` 에 같은 값**을
쓴다. 그러면 `created_ts >= floor` 로 방금 만든 요약만 걸리고 이전 요약은 빠진다. 두 번 시각을
구하면 순서에 따라 방금 만든 요약이 스스로 걸러지는 경합이 생긴다.

### 2.5 자연 만료는 바뀌지 않는다

유휴로 세션이 끊긴 뒤 다시 말을 걸면 지금처럼 최근 대화가 실린다. **"이어서 하기"가 기본이고
끊는 것은 명시적으로 시킬 때만**이다. 유휴 요약이 만든 요약도 그대로 실린다(그 시점에
바닥선을 건드리지 않으므로).

### 2.6 기억 섹션의 문자 예산

기억 섹션에 문자 예산을 둔다. 예산 안에서는 지금처럼 **내용까지** 싣고, 넘치면 나머지는
**제목만** 싣고 "자세한 것은 `recall` 로 물어보라"는 안내를 붙인다.

- 지금 규모(7건 1,409자)에서는 **동작이 전혀 바뀌지 않는다**
- 커졌을 때 뒷부분이 색인으로 degrade 한다 — 잘려서 사라지는 것이 아니라 **제목이 남으므로
  모델이 "그 주제가 있다"는 것을 알고 `recall` 할 수 있다**

**그냥 `LIMIT N` 으로 자르지 않는 이유**: 잘린 기억은 모델에게 존재 자체가 안 보인다. 아는
것이 있는데 없는 줄 아는 상태이고, 그것은 이 프로젝트가 반복해서 피해온 조용한 실패다.

예산은 **6,000자**로 둔다. 기억 1건 상한이 4,000자이므로 큰 기억 한 건이 예산을 통째로
먹지 않으면서, 지금 규모(1,409자)의 네 배까지는 지금과 똑같이 동작한다. 정렬은 지금과 같은
`id` 순(오래된 것 먼저)이라 **먼저 등록된 동아리 기본 정보가 우선 보존**된다.

### 2.7 문구

- `/새세션` 확인: 무엇이 빠지고(이전 대화·요약) 무엇이 남는지(기억·캐릭터 설정)를 말한다
- `/기억정리` 확인: 요약해서 넘겼다는 것을 말한다
- `/help` 예약어 목록에 `/기억정리` 를 넣는다

## 3. 고르지 않은 선택지

| | 방식 | 왜 아닌가 |
|---|---|---|
| A | 기억 섹션을 `LIMIT N` 으로 자름 | 잘린 기억이 모델에게 안 보인다 — 조용한 실패(§2.6) |
| B | 블록에 제목만 싣고 내용은 항상 `recall` | 프롬프트는 확실히 작아지지만 모든 질문에 도구 호출이 하나 붙고, 지금 잘 되는 즉답이 사라진다. 2026-08-03 실측에서 `recall` 호출이 0건이었던 것은 블록이 다 보여줬기 때문이다 |
| C | `/새세션` 의 동작을 그대로 두고 문구만 고침 | 사용자가 원하는 "주제 갈아타기" 수단이 여전히 없다 |
| D | 바닥선을 메시지 id 로 | 요약(범위)과 메시지(점)를 다른 규칙으로 걸러야 해 경계가 어긋난다(§2.1) |

## 4. 오류 처리

- `/기억정리` 의 요약 실패 → 세션·바닥선 그대로, 실패를 알린다(§2.3)
- `/기억정리` 할 세션이 없음 → 그 사실을 알린다
- 바닥선이 `NULL` → 지금 동작(전부 싣기). 기존 대화 전부가 이 상태이므로 **배포 직후 아무것도
  바뀌지 않는다**
- 기억이 예산을 넘음 → 자르지 않고 제목만. 사용자에게 보이는 실패가 아니다

## 5. 테스트 전략

**유닛으로 고정할 것**

- 바닥선 필터: 바닥선 이전 메시지가 빠지고 이후는 남는 것. 바닥선 시점의 요약은 **남는** 것
  (`>=` 와 `>` 의 차이를 직접 단정한다)
- 바닥선이 `NULL` 이면 지금과 동일한 것(회귀 방지)
- `/새세션`: 세션과 바닥선이 둘 다 설정되고 **요약은 만들어지지 않는** 것
- `/기억정리`: 요약이 만들어지고 세션·바닥선이 설정되는 것
- `/기억정리` 실패: **세션도 바닥선도 안 바뀌는** 것 — 이 갈래가 이 명령의 핵심 안전장치다
- 기억 예산: 예산 안이면 내용까지, 넘으면 나머지가 제목만 + 안내가 붙는 것. 잘려서 **사라지지
  않는** 것

**스모크로 넘길 것**

- DM 에서 `/새세션` 후 이전 주제를 물으면 모른다고 하는 것(기억은 아는 것)
- DM 에서 `/기억정리` 후 이전 주제를 물으면 요약 수준으로 아는 것

## 6. 이 문서가 다루지 않는 것

- 기억 검색 품질(임베딩·순위) — 지금은 부분 문자열 일치다. 기억이 쌓여 실제로 문제가 되면 그때 본다
- 바닥선의 되돌리기 — 한 번 그은 선을 무르는 수단은 만들지 않는다. 데이터는 남아 있고
  소유자는 `db_query` 로 볼 수 있다(§2.2)
- 대화방별 기억 분리 — 공용 기억은 지금대로 전 대화방 공통이다
