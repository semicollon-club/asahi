# 0010. DB 읽기를 전 부원에게 연다 — 신원이 아니라 읽기 전용이 경계다

## 맥락

`db_schema`/`db_query` 는 2026-07 자기인지 기능부터 **소유자 DM 전용**이었다
(`isOwnerDm = isOwner && isPrivate`, `agent/src/core/tools.ts`). 하네스 경로의
Supabase 허브 MCP 도 소유자 프로필에만 열렸다(`core/profiles.ts` 의 `OWNER_MCP_HUB`).

2026-09-17, 공개 채널에서 부원이 스레드·대화 번호를 확인하려고 DB 조회를 요청했고
아사히는 "그 도구가 없다"고 거부했다. 도구가 그 턴에 애초에 등록되지 않으므로 이 거부
자체는 설계대로 동작한 결과였다. 원인을 좁히는 과정에서 두 가지가 같이 드러났다.

1. **두 경로의 축이 어긋나 있었다.** 봇 세션 경로는 "소유자 + DM" 을 요구하는데, 하네스
   경로의 프로필은 `isPrivate` 를 보지 않아 **소유자라면 서버 채널에서도** Supabase 허브가
   열렸다. 같은 사람이 같은 채널에서 물어도 그 턴이 어느 경로로 갔느냐에 따라 답이 갈렸다.
2. **게이트의 전제가 이 프로젝트에서 성립하지 않는다.** ADR 0009 가 이미 "아사히는 부원별
   비서가 아니라 동아리 작업을 총괄하는 하나의 에이전트" 라고 정했다. 그 전제 위에서
   "DB 안의 것"은 대부분 이미 부원 전부가 볼 수 있는 재료다.

## 결정

**`db_schema`/`db_query` 에서 신원·채널 게이트를 제거한다.** 등록된 부원이면(role 이
`owner` 또는 `allowed`) DM·서버 어디서든, 소유자든 손님이든 같은 도구를 받는다.

- 봇 세션 경로 — `canReadDb(ctx) = role in {owner, allowed}` 하나만 본다. 도구 노출
  (`allowedToolsFor`)도 네 계층 전부에 `db_schema`/`db_query` 를 넣는다.
- 하네스 경로 — 손님 프로필에도 `mcpHub: ["supabase"]` 를 준다(`GUEST_MCP_HUB`). 5단계
  (부원 하네스 개방) 전까지 실제로 도는 경로는 없지만, 두 경로의 축을 지금 맞춰 둔다.
- **`manage_access` 는 그대로 소유자 DM 전용이다.** 신원 표(`users`)를 바꾸는 일은 DB 를
  읽는 일과 다른 권한이다. ~~`runtime_info` 도 그대로 소유자 전용이다.~~

  > **정정(2026-09-17, [0012](./0012-runtime-info-for-all-members.md))** — `runtime_info` 를
  > 유보한 위 한 줄에는 근거가 붙어 있지 않았다. 이 도구의 소유자 게이트는 애초에 이 ADR 이
  > 푼 두 도구와 **한 묶음으로** 걸린 것이었으므로(2026-07-12 자기인지 계획), 묶음을 풀 때
  > 같이 풀렸어야 했다. 0012 가 그 잔재를 제거했다 — 이 ADR 의 나머지 결정에는 영향이 없다.

- **읽기 전용 보장은 손대지 않는다**(ADR 0004): `assertReadOnlySql`(1차) + `SET TRANSACTION
  READ ONLY`(2차, 핵심 방어선) + `maxRows`·`statement_timeout`.

## 근거

**이 DB 에 신원으로 가려야 할 것이 실제로 없다**(운영자 2026-09-17).

- **대화·기억·작업 기록** — 아사히가 도는 곳은 동아리 공개 채널이고 그 대화는 이미 전
  부원에게 보인다. 손님 DM 은 아예 받지 않으며(`decideRoute` 의 `dm-declined`), 소유자 DM 도
  미니PC 작업 지시만 하기로 했다. 게다가 세션 전사는 이미 공용 PC 의 파일로 남는다(ADR 0009)
  — 대화 기록을 가리는 것은 **DB 게이트로 달성되지 않는 목표**였다.
- **신원 표(`users`)** — 담긴 값은 디스코드 ID 와 표시명이다. 둘 다 공개 채널에서 온 값이고,
  사용자 등록 자체가 공개 채널에서 ID 를 복사해 넣는 절차이며, 표시명은 매 턴 그 채널의
  이름으로 갱신된다. DB 가 그 위에 더하는 식별 정보가 없다.
- **자격증명** — 진짜 비밀은 DB 가 아니라 환경변수에 있다(`DISCORD_TOKEN`·`DATABASE_URL`·
  `GITHUB_APP_PRIVATE_KEY_B64`, `agent/src/config.ts`). 표에 남는 유일한 자격증명은
  `workers.token_hash` 이고 평문은 저장하지 않는다(`agent/src/store/schema.ts`). 그리고 봇이
  쓰는 깃허브 자격증명은 개인 것이 아니라 **동아리 계정의 것**이다 — 부원은 이미 공개 채널에서
  명령 한 줄로 그 자격증명으로 커밋·푸시할 수 있다. 모두가 쓰는 자격증명을 조회만 막는 것은
  경계가 아니라 장식이다.

**그리고 완전하지 않은 격리는 없는 것보다 나쁠 수 있다**(ADR 0009 의 같은 논거). 이 게이트는
"부원은 봇의 데이터를 못 본다"는 인상을 주지만 실제로는 공용 PC 의 전사·워크스페이스·공개
채널 스크롤이 같은 내용을 그대로 준다. 지켜지지 않는 경계를 문서에 남겨 두면 운영자가 그
경계를 믿고 확인을 멈춘다.

배제한 선택지:

- **테이블·뷰 화이트리스트로 부분 개방** — 검토했다(소유자 DM 전사·`workers`·`users` 만 제외).
  위 근거대로 제외할 대상이 실제로는 없어서, 남는 것은 관리 비용과 "가려진다"는 잘못된 신호뿐이다.
- **스레드 조회 전용 도구 하나 추가** — 이번 요청은 풀리지만 다음 질문에서 같은 벽을 다시
  만난다. 아사히가 실측으로 답하게 하려는 원래 목적(ADR 0004 의 맥락)과도 어긋난다.

## 결과

- **부원 누구나 봇의 DB 를 SELECT 로 읽을 수 있다.** 이것은 알려진 상태이며 안내에도 적는다 —
  `persona.ts` 의 `DB_READ_LINE` 이 네 계층 모두에 들어가고, 손님 안내의 "소유자만" 목록
  (`GUEST_OWNER_ONLY_LINE`)에서 DB 가 빠졌다.
- **쓰기는 여전히 불가능하다.** ADR 0004 의 두 겹이 그대로다 — 이 ADR 은 "누가 읽는가"만 바꾼다.
- **ADR 0004 는 개정**했다(소유자 DM 게이팅 서술 → 이 ADR 로 이관). **ADR 0009 의 근거 한 줄**
  ("손님에게는 봇 허브 MCP(DB 읽기 등)가 열리지 않는다")도 더 이상 참이 아니어서 정정했다 —
  다만 0009 의 결론은 이 변경으로 오히려 강해진다(가리지 않기로 한 것을 한 겹 더 실제로 맞춘다).
- **후속(별도 PR)**: 소유자 DM 도 개인 워커가 아니라 공유 미니PC 워커로 보내는 변경이 예정돼
  있다(`resolveWorkerSelector`). 그러면 ADR 0009 의 결정 2(소유자 전사 분리)도 함께 정리된다.
- 되돌리려면 `canReadDb` 를 `isOwnerDm` 으로 되돌리고 `GUEST_MCP_HUB` 를 비우면 된다. 다만
  되돌리기 전에 "그때 무엇을 가리려는 것인지"를 먼저 적어야 한다 — 이 ADR 이 기록한 대로, 가릴
  대상이 실제로 있는지가 이 결정의 전부다.
